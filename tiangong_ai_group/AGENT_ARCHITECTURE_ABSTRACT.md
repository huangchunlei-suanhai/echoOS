# Agent 架构总纲（领域无关版）

> 本文讨论 Agent 的抽象结构，不依赖编程语言、模型厂商、软件框架或具体行业。
> 它用于统一产品、架构、交互和治理语言；具体系统的接口、字段和实现契约，应在
> 各自的专项文档中定义。

## 1. 一句话定义

Agent 是一个在明确目标、现实环境和治理约束下，能够理解意图、组织行动、获取反馈、
接受修正并持续推进结果的协作系统。

它的最终产物不是一段回答，而是一个可解释、可验证、可恢复的结果推进过程。

## 2. Agent 不等于什么

| 容易混淆的对象 | 它解决的问题 | 与 Agent 的区别 |
| --- | --- | --- |
| 对话助手 | 生成或理解语言 | 可以没有行动、状态和结果责任 |
| 自动化流程 | 按预设步骤重复执行 | 通常不能处理开放目标和不确定反馈 |
| 知识库 | 保存和检索知识 | 不负责把目标推进为行动和结果 |
| 工具集合 | 提供若干操作手段 | 不负责判断何时使用以及是否有权使用 |
| 工作流 | 描述步骤和依赖 | 不一定具备理解、澄清、调整和恢复能力 |
| Agent | 在约束下推进目标 | 同时连接理解、决策、行动、反馈和治理 |

因此，只有“会生成文字”或“能调用工具”都不足以构成完整 Agent。

## 3. 架构的六类要素

Agent 的要素可以分成六类。分类用于划清职责，不要求每个要素必须由独立的软件模块承载。

### 3.1 目标与事实来源

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 参与者 | 提出目标、补充信息、确认或否决行动的人或外部主体 | 谁希望发生什么变化？ | 不等于系统事实源 |
| 目标 | 希望达成的结果、改善或判断 | 最终想得到什么？ | 不等于具体步骤 |
| 当前情境 | 当前时刻可用的事实、环境和对象状态 | 现在是什么情况？ | 不记录全部历史 |
| 记忆 | 对后续任务仍有价值的历史事实和未完成事项 | 之前发生过什么？ | 不覆盖本轮明确目标 |
| 外部环境 | Agent 可以观察或影响的现实对象 | 行动作用于哪里？ | 不自动接受 Agent 的解释 |

### 3.2 理解与决策

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 意图解释 | 把自然表达转换为目标、问题、约束和待确认事项 | 参与者到底想做什么？ | 不授权副作用行动 |
| 任务分流 | 把目标交给适合的能力范围 | 由谁或哪类能力处理？ | 不生成最终方案 |
| 规划 | 把目标拆成有顺序、有依赖的候选行动 | 应怎样推进？ | 不证明方案一定正确 |
| 推理与生成 | 在不完整信息下提出解释、方案或候选内容 | 有哪些可能的做法？ | 不把候选变成事实 |

### 3.3 方法与能力

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 知识 | 关于对象、规律、事实和适用条件的可复用认识 | 世界通常是怎样的？ | 不决定本轮是否获准行动 |
| Skill | 针对某类目标的做法、判断经验、约束和步骤原则 | 这类问题通常怎样处理？ | 不替代权限和状态控制 |
| 能力 | Agent 可以对某类目标承担的完整结果职责 | Agent 能负责什么结果？ | 不等于某一个具体操作 |
| 行动手段 | 让外部环境发生观察或变化的具体方式 | 具体怎样做？ | 不自行决定使用时机 |

### 3.4 治理与控制

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 策略 | 权限、风险、合规、资源和确认要求 | 什么情况下可以做？ | 不替代事实观察 |
| 状态 | 当前任务已经达到的阶段和条件 | 任务现在走到哪里？ | 不表示用户已经同意下一步 |
| 确认门 | 在高风险或不可逆行动前取得明确授权 | 是否允许继续？ | 不负责生成行动方案 |
| 责任边界 | 对结果、事实、建议和解释的归属划分 | 谁对什么负责？ | 不等于技术实现边界 |

### 3.5 反馈与事实

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 观察 | 行动后从环境获得的原始现象、数据或状态变化 | 实际发生了什么？ | 不直接解释原因 |
| 校验 | 按规则、合同、目标或证据判断观察是否满足要求 | 结果是否合格？ | 不凭空补造观察 |
| 产物 | 可被人或其他系统继续使用的持久结果 | 留下了什么？ | 不代表产物已经被批准使用 |
| 提交 | 把经过允许和校验的结果写入稳定事实或正式状态 | 什么结果正式生效？ | 不等于生成候选 |

### 3.6 交互与运行

| 要素 | 抽象定义 | 直接回答的问题 | 不负责什么 |
| --- | --- | --- | --- |
| 呈现 | 向参与者说明当前判断、候选方案、进度、风险和结果 | 应该让人看到什么？ | 不改变后台事实 |
| 澄清 | 请求足以继续推进的缺失信息 | 还缺什么关键信息？ | 不把猜测当答案 |
| 编排 | 维护一次或多次交互的顺序、并发、恢复和超时 | 何时做下一步？ | 不替代领域判断 |
| 审计 | 保留关键输入、决策、授权、行动和结果的可追踪记录 | 为什么这样做？ | 不把记录变成事实本身 |

## 4. 最容易混淆的边界

### 4.1 当前情境、记忆、知识、Skill 和策略

| 对象 | 时间范围 | 内容性质 | 对本轮的作用 | 能否覆盖用户当前明确要求 |
| --- | --- | --- | --- | --- |
| 当前情境 | 现在 | 当前事实和现场 | 说明当前可见条件 | 不能 |
| 记忆 | 过去到现在 | 历史事实、未完成事项 | 帮助续接任务 | 不能 |
| 知识 | 跨任务 | 一般事实、规律和边界 | 提供认识依据 | 不能 |
| Skill | 跨任务 | 方法、步骤原则和经验约束 | 提供处理方式 | 不能 |
| 策略 | 持续有效 | 权限、风险和治理规则 | 决定能否行动 | 不能替用户改变目标 |

核心原则是：**情境说明“现在有什么”，记忆说明“以前发生过什么”，知识说明“通常
是什么”，Skill 说明“通常怎么做”，策略说明“什么情况下允许做”。**

### 4.2 能力、行动手段与产物

能力描述 Agent 对某类结果承担的职责；行动手段只是完成能力时可以采用的具体方式；
产物是行动后留下的结果。

例如，“形成一份可审阅方案”是能力，“查询资料、计算、修改和提交”是行动手段，
“方案文件和审阅记录”是产物。行动手段可以变化，能力的结果契约不能因此消失。

### 4.3 计划、状态、观察、结论与事实

这五类对象必须分开：

- 计划是尚未执行的候选安排；
- 状态是系统当前确认已经达到的阶段；
- 观察是环境返回的现象或数据；
- 结论是对观察进行解释后的判断；
- 事实是经过来源、校验和提交边界认可后可供后续使用的内容。

模型提出的计划、工具返回的观察、人的确认和系统提交的事实，不能互相冒充。

## 5. 要素之间的关系

Agent 不是单向的“输入—输出”函数，而是由以下关系连接起来的闭环：

![Agent 要素关系图](assets/agent-architecture-relationships.png)

图中顺时针主链表示“从目标到可验证结果”的行动闭环；左上角的参与者负责提出目标、
补充信息和授权，右下角的记忆只提供历史连续性并接收经过校验和提交的稳定事实。中心的
治理边界横向约束状态、编排、呈现和审计，因此它不是一个额外步骤，而是每个阶段都必须
遵守的控制面。

| 起点 | 关系 | 终点 | 关系含义 |
| --- | --- | --- | --- |
| 参与者 | 提出 | 目标 | 表达希望改变或判断什么 |
| 目标 | 受当前情境约束 | 意图解释 | 结合现场事实理解目标 |
| 记忆 | 辅助 | 意图解释 | 提供历史连续性，但不覆盖当前表达 |
| 知识 | 支撑 | 推理与生成 | 提供事实、规律和适用边界 |
| Skill | 约束并指导 | 规划 | 提供做法、顺序和检查重点 |
| 意图解释 | 选择 | 任务分流 | 决定进入哪类能力范围 |
| 任务分流 | 交给 | 能力 | 确定由哪类职责承接目标 |
| 能力 | 产生 | 规划 | 把职责转换为可评审的候选行动 |
| 规划 | 请求 | 策略 | 检查风险、权限和确认要求 |
| 策略 | 允许或拒绝 | 确认门 | 决定是否还需要参与者授权 |
| 确认门 | 放行 | 行动手段 | 允许具体行动进入外部环境 |
| 行动手段 | 作用于 | 外部环境 | 产生观察或环境变化 |
| 外部环境 | 返回 | 观察 | 提供行动后的原始结果 |
| 观察 | 进入 | 校验 | 判断是否满足目标和约束 |
| 校验 | 形成 | 产物或失败原因 | 产生可用结果或可恢复问题 |
| 产物 | 经过提交 | 稳定事实 | 使结果成为后续可引用内容 |
| 稳定事实 | 更新 | 记忆 | 保存对后续任务仍有价值的部分 |
| 状态 | 驱动 | 编排 | 决定允许的下一步和恢复方式 |
| 编排 | 驱动 | 呈现 | 向参与者说明进度、风险和下一步 |

其中最重要的依赖方向是：

```text
目标 + 当前情境 + 记忆
        ↓
意图解释 → 任务分流 → 能力 → 规划
                         ↓
                    策略 / 确认
                         ↓
                      行动
                         ↓
                    观察 → 校验
                         ↓
               产物 / 稳定事实 / 记忆
```

这段关系不是固定步骤表。根据任务风险和确定程度，Agent 可以在规划、澄清、确认、行动
和校验之间多次往返，但不能跳过其适用的治理和事实门槛。

## 6. Agent 的三个循环

### 6.1 理解循环

```text
表达 → 意图解释 → 缺口识别 → 澄清或形成目标
```

理解循环的输出是“当前应该解决什么”，不是“已经解决了什么”。当关键事实缺失时，
澄清优先于猜测。

### 6.2 行动循环

```text
目标 → 规划 → 策略判断 → 确认 → 行动 → 观察 → 校验 → 修正或提交
```

行动循环允许失败和重试，但每次重试都必须基于新的观察或明确修正，不能无限重复同一
个失败行动。不可逆或高风险行动必须在行动前通过确认门。

### 6.3 协作循环

```text
呈现候选 → 参与者审阅 → 补充 / 修改 / 确认 / 否决 → 继续或终止
```

参与者不是只在开始和结束出现的审批人，而是 Agent 在不确定性和风险处的共同决策者。
确认的是明确的对象、范围、版本和动作，不能把“看到了页面”或“没有提出异议”当成
对不可逆行动的授权。

## 7. 不确定性与确定性的分工

Agent 的核心原则不是“全部交给智能模型”，而是让不同性质的工作由合适的机制承担。

| 工作性质 | 适合由推理与生成承担 | 必须由确定性控制承担 |
| --- | --- | --- |
| 理解 | 解释表达、识别可能意图、提出澄清问题 | 输入是否完整、身份是否可信 |
| 方案 | 生成候选、比较路径、解释取舍 | 方案格式、范围、依赖和冲突检查 |
| 行动 | 提议可用的行动手段 | 权限、风险、确认、重复执行控制 |
| 结果 | 组织说明、提出可能原因 | 观察真实性、校验规则、事实提交 |
| 交互 | 调整表达、总结和教育 | 状态迁移、终止、取消、审计 |

推理结果在通过结构、语义、权限和领域校验前，始终是候选，不是系统事实。

## 8. 状态与阶段原则

一个通用 Agent 任务可以使用以下状态集合；具体任务可以合并或拆分，但必须保持语义
可辨认：

```text
received
  → understood
  → awaiting_information
  → planned
  → awaiting_confirmation
  → executing
  → observing
  → validating
  → committed
```

异常分支至少包括：

```text
awaiting_information → cancelled
planned               → rejected
executing             → failed_recoverable
validating            → failed_recoverable
任意可取消阶段        → cancelled
```

状态设计必须满足：

1. 每个状态都有进入条件、可执行动作和离开条件。
2. 状态表示已经确认的事实，不表示模型的猜测。
3. 需要人确认时，系统必须停在可恢复的等待状态。
4. 失败要说明是输入、策略、行动、外部环境还是校验失败。
5. 恢复必须引用原任务、原版本和新的观察，不能悄悄开启另一项任务。
6. 提交后产生的事实不可由后续模型回答直接改写，必须经过新的受控变更流程。

## 9. 一项能力的最小架构声明

新增一种 Agent 能力时，至少要明确以下内容：

| 声明项 | 必须回答的问题 |
| --- | --- |
| 目标范围 | 这项能力为哪类目标负责？明确不负责什么？ |
| 输入事实 | 需要哪些当前情境、记忆、知识和参与者确认？ |
| 结果契约 | 成功时留下什么产物或稳定事实？ |
| 阶段 | 目标如何从开始推进到结束？ |
| 方法 | 使用哪些 Skill、知识和行动手段？ |
| 风险 | 哪些行动可能造成损失、泄露或不可逆变化？ |
| 确认 | 哪些动作必须由谁在什么范围内确认？ |
| 校验 | 怎样判断候选方案和实际结果是否合格？ |
| 失败恢复 | 失败后能重试、修正、回退还是只能终止？ |
| 记忆 | 哪些事实值得保留，保留多久，谁可以使用？ |
| 审计 | 如何追踪输入、决策、授权、行动和结果？ |

如果一项能力无法回答这些问题，它通常还只是一个想法、一个行动手段或一段内部提示，而不是
可以被治理的 Agent 能力。

## 10. 扩展原则

### 10.1 增加能力

增加能力时，不应把新规则堆到总 Agent 中。应为它定义自己的目标范围、阶段、输入、结果、
风险和校验，并通过统一的任务分流和执行边界接入。

### 10.2 增加 Skill

Skill 应声明适用目标、适用阶段、适用条件、冲突对象、版本和失效边界。Skill 提供方法
约束，不取得权限，也不直接改变稳定事实。多个 Skill 冲突时，由确定性策略决定是否拒绝、
降级或请求人工判断，不能让生成器自行覆盖冲突。

### 10.3 增加行动手段

行动手段必须声明输入、输出、风险、权限、超时、失败语义和可观察结果。它不能因为被
Agent 看见就自动获得执行资格。

### 10.4 增加记忆

记忆只保存未来仍有价值的事实、决定、未完成事项和失败原因；不应无边界保存全部交互、
全部内部推理或未经确认的猜测。

## 11. 常见架构错误

1. **让推理机制直接决定权限**：把“提出行动”误认为“行动已经获准”。
2. **让页面或当前情境充当授权**：可见不代表允许修改、执行或提交。
3. **把记忆当成当前事实**：历史结论可能已经过时，必须重新核验。
4. **把知识、Skill 和策略混为一层**：知道怎么做不等于有权做。
5. **把工具当成能力**：能调用某个手段不代表能对某类结果负责。
6. **把计划当成结果**：方案生成成功不等于行动成功。
7. **把观察当成结论**：环境返回数据不等于原因已经得到证明。
8. **把展示当成事实写入**：前端看到候选，不等于平台已经提交。
9. **用关键词代替理解**：关键词只能作为低可信辅助，不能替代结构化意图判断。
10. **用异常文本推动状态**：状态应由明确的错误类别和条件驱动。
11. **为兼容而维护两套事实**：同一对象只能有一个当前权威来源。
12. **跳过确认和校验追求流畅**：交互更快不等于结果更可靠。

## 12. 架构评审清单

评审一个 Agent 设计时，可以按以下顺序检查：

1. 它服务的目标和不服务的目标是否明确？
2. 当前情境、记忆、知识、Skill 和策略是否被区分？
3. 意图解释、任务分流、规划、行动和校验是否各自有清晰责任？
4. 计划、状态、观察、结论、产物和事实是否没有互相冒充？
5. 哪些步骤由推理与生成负责，哪些步骤由确定性控制负责？
6. 高风险或不可逆行动是否有明确的确认门？
7. 每个状态是否有进入条件、离开条件和可恢复路径？
8. 失败是否可以定位到输入、策略、行动、环境或校验层？
9. 结果是否可验证、可追踪、可解释，而不是只返回一段话？
10. 新能力、新 Skill 和新行动手段是否可以独立扩展而不污染主 Agent？

## 13. 最终判断标准

一个健康的 Agent 架构，应当让人能够回答：

```text
参与者想达成什么？
系统现在知道什么？
还缺什么？
谁负责理解和规划？
谁决定能不能行动？
```
