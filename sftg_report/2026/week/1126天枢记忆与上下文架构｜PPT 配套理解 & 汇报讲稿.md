# 天枢记忆与上下文架构｜PPT 配套理解 & 汇报讲稿

> 对应 [22 页 HTML 演示稿](TS_LONG_TERM_MEMORY_CONTEXT.html)。依据现行阶段三[联调协议](天枢长期记忆与上下文管理基础版-正式前端联调协议v1.0.0.md)和当前源码整理；本讲稿帮助理解与汇报，不是生产验收报告。

## 汇报前先记住的三个口径

1. **目标设计**回答“最终必须是什么样”。外部系统掌握工程真值；天枢掌握 AI 会话、记忆治理和上下文；Java 掌握平台登录身份。目标机制不等于已经上线。
2. **当前已实现**回答“源码和现有联调实际证明了什么”。已能通过 Java 用户详情核验身份，天枢有本地 SQLite 会话账本、一次性 WS ticket、显式记忆候选及确认、有限召回、上下文裁剪和部分会话清理；正式前端、网关、WS、完整聊天与删除的三方端到端验收仍未完成。
3. **讨论基线**“实施前建议先按什么数值讨论”：相关指标属于方案暂定草稿，供各方评审商议，不是已落地、可承诺的正式指标；需业务、安全、合规、运维共同确认并实测通过后，才生效。

我们全程可以用这个例子串整个架构：有一个零件方案版本 1，之前验证通过，之后资产升级到版本 2。版本 1 验证通过的权威记录保存在外部权威系统里面。天枢可以记住我们当时的讨论过程、以及当时批准 V1 通过这个结论；但是天枢不能凭着自己存的这条记忆，默认新版本 V2 也自动通过验证。这个例子仅用于讲解架构边界，不是真实业务数据。

## 开篇总故事（约 3 分钟，对应第 01 页）

> “领导您好。我想先用一个工程任务说明这套系统到底解决什么。假设我们上周讨论过一个零件方案，当时版本 1 经过验证，大家也定下了后续处理偏好。今天用户继续问同一个任务，天枢既不能像第一次见面一样忘掉过去，也不能照搬上周的结论，因为工程资产可能已经改成版本 2，权限也可能变化。
>
> 因此我们把信息分成四层。第一层是外部工程系统，它保存资产版本、验证结果和权限，是工程事实的正本。第二层是天枢的会话档案，它记录谁在什么时候说了什么、做了什么，给后续判断留下证据。第三层是受治理的记忆和知识：从记录中发现可能值得复用的内容，但先作为候选，确认来源、适用范围和责任人以后才生效。第四层是本轮上下文：用户再次提问时，天枢核验身份和工程权限，复查证据是否仍然有效，再把真正相关的少量信息送给模型。
>
> 这里有两个最重要的边界。天枢可以持有工程工作的副本、过程记录和引用，但它不生产也不替代外部系统的工程真值；记忆只是帮助理解和决策的材料，不是业务写入权限。真正修改工程资产仍要经过当前身份、资产权限、版本校验和外部系统的写入确认。
>
> 目前我们落地的是这套架构的一部分：会话账本、平台身份查询、显式记忆候选和有限的上下文处理已有代码。外部权威源联动、变更失效、冲突治理、生产级恢复与完整删除还需要分阶段建设。今天的汇报先讲清楚目标和不能突破的约束，再讲已完成的部分与下一步门槛。”

如果只有 30 秒，压缩为：**工程真值在外部，交互证据在天枢，记忆须确认并持续复核，上下文每轮重新鉴权组装；当前已做基础闭环，生产治理还待建设。**

## 逐页讲稿

**串场路线**：第 01 至 06 页先回答“信息从哪里来、谁说了算”；
第 07 至 13 页沿一条记忆的生命周期回答“怎样形成、使用、更新和删除”；
第 14 页解释“借鉴了什么、为什么还要自己定治理边界”；
第 15 至 17 页回到“目前做到哪里、分几步到目标”；
第 18 至 22 页用于展开领导追问的生产细则与切换条件。
时间有限时可先讲 01、05、07、09、15 至 17，其余按提问跳转。

### 01｜天枢记忆与上下文目标架构

**本页核心**：这是一条“外部真值 → 会话留痕 → 记忆治理 → 本轮组装”的流水线。它描述目标架构，不能当作当前完成清单。

**口头讲解**：“可以把外部工程系统看作正式台账，把天枢会话看作会议记录，把记忆看作核对过的备忘录，把当前上下文看作这次开会带进房间的资料。会议记录证明有人说过‘版本 1 通过’，但版本 2 是否通过，必须重新看正式台账。记忆也不会自己去改资产。”随后用上面的三分钟故事引出下一页术语。

**领导可能问：协作证据和工程事实有什么区别**？答：协作证据证明交互或操作曾发生，可能包含错误陈述；工程事实是外部权威系统对资产版本和验证结果的当前记录。天枢可以引用后者，不能把前者自动升级成后者。

### 02｜先统一术语：来源、衍生物、运行时视图各不相同

**本页核心**：会话档案、工程现场是不同来源；记忆和知识是受治理的衍生物；任务状态、当前上下文是供运行时使用的视图。

**口头讲解**：“这页最容易混的是‘任务状态’和‘工程现场’。任务状态像快递进度，回答流程走到哪；工程现场像仓库里的实物和正式检验记录，回答现在实际是什么。会话是会议纪要，记忆是经确认的个人备忘，知识是经过发布的做法。上下文则只是本次提问临时挑出来的资料包，用完不能把资料包当新正本。”

**领导可能问：为什么候选不能直接算记忆**？答：候选可能是模型误读、用户随口一说或仅对旧版本成立。先让适格的人确认，并写清适用范围与证据，才能避免一次猜测在以后反复影响工程决策。

### 03｜对象各有归属；关键约束不随技术选型改变

**本页核心**：对象必须有明确主人；数据库、检索方式可以换，真值归属、权限、用户隔离和可删除性不能换。

**口头讲解**：“正式 Java 后端管平台登录和用户身份查询；天枢收到平台 token 后向 Java 核验身份，由天枢签发一次性 WebSocket 建连票据。AI 会话、聊天记录、记忆和删除属于天枢。资产与验证结论属于外部现有工程系统。首期团队知识不自动跨用户共享，目标范围锁在‘用户加场景’，工程结论要能找到该场景的责任人。底层是 SQLite 还是 PostgreSQL，是实现选择；谁有权说版本 2 通过，不是实现选择。”
ACL：Access Control List（**访问控制列表**）就是一套权限规则：谁能看哪条记忆、哪份证据、哪个工程资产；谁不能看。
SLA ：Service Level Agreement（**服务等级协议**）约定这个服务要达到什么样的服务质量标准，是双方的服务承诺指标。

**领导可能问：天枢不管工程真值，是否连工程文件都不能存**？答：可以保存工作副本、任务产物和引用，但这些不自动成为正式权威版本。只有外部系统确认的资产版本和验证回执可作为当前工程事实；工作副本还须按权限和个人信息分类管理。

### 04｜评审红线：任何阶段都不能突破

**本页核心**：这里集中列的是会造成错误工程结论、越权或删不干净的禁止行为。

**口头讲解**：“这页不是功能愿望清单，而是评审时的底线。最常见的误区是把‘曾经讨论过’当‘现在仍然正确’，把‘检索到了’当‘有权限注入’，把‘模型觉得两条结论差不多’当‘冲突已裁决’。这些动作可能看起来省事，但会让旧版本结论、错误偏好或无权内容进入后续推理。删除也不能只删聊天页面，背后的候选、索引和记忆证据要一起处理。”

**领导可能问：红线是否会拖慢首期交付**？答：首期可以少做自动抽取、图谱和跨用户共享，但已上线的路径必须满足身份隔离、候选不自动生效、权限未知不注入等底线。复杂能力可以分期，禁止行为不能分期放开。

### 05｜每次任务先汇总“本轮该知道什么”

**本页核心**：天枢在每轮请求中把多个来源汇入一个受控上下文，结果再回到各自有权保存的地方。

**口头讲解**：“可以把这页看作一个门卫加资料员。用户进来，先由平台身份确认他是谁；再看会话中的任务进度；需要工程资产时向外部系统读取当前版本和权限；最后从已确认的记忆与知识中找相关内容。天枢只把这次确实需要、确实有权、确实有效的信息交给模型。模型处理后，聊天进账本，值得沉淀的内容进候选，正式工程结果仍由外部系统确认。”

**领导可能问：任务状态和工程现场会不会重复存一份事实**？答：任务状态是续接进度，例如“等待版本 2 复核”；工程现场是当前资产和验证记录。任务状态可引用工程记录 ID，但不能自己改写外部事实。

### 06｜先定外部权威系统必须提供什么，不预设服务名称

**本页核心**：先定义天枢需要外部提供的四类能力：查版本与验证、查权限、得知变化、确认写入结果。具体由哪个现有服务承载，后续对接时确定。

**口头讲解**：“我们现在不必猜某个服务名字，也不打算先新建一套工程真值服务。要先把业务问题说清楚：天枢问‘版本 2 是什么’，必须拿到稳定编号和版本；问‘这个人能不能看’，必须得到当前权限；旧结果被撤回，要能通知或补查；发起工程写入后，外部系统要给出明确回执。请求超时不能算写入成功，也不能盲目重复执行。”

**领导可能问：外部系统如果没有变更事件怎么办**？答：上线前至少需要可查询当前版本和可补偿的变化发现机制；可以先按游标或定期对账实现，再逐步接事件。发现变化有延迟时，召回前仍要回源核版本，来源不可核验就不把旧结论当当前事实。

### 07｜会话记录、记忆与知识：三类信息按规则流转

**本页核心**：记录先留痕，再提出候选，再由对应人确认，最后才允许在适用范围内复用；知识发布是另一道门。

**口头讲解**：“用户说‘请记住我在这个场景偏好先看验证摘要’，这句话先留在会话中。天枢提取出一个候选让用户确认；确认后，它才可能在以后相关提问中被找到。工程结论更严格，还要回看外部验证证据并交场景责任人。跨用户共享的知识不能因为某个用户确认了个人记忆就自动发布。现行基础版只支持明确以‘请记住：’开头的成功请求生成个人偏好候选，通用异步抽取还没有落地。”
Outbox（事务发件箱模式）正确目标流程：
保存会话证据到会话账本（同一个数据库事务里，顺便往 Outbox 表插入一条待抽取任务记录）
直接返回给用户，聊天响应结束，不卡用户
后台单独的 worker 进程，不断扫 Outbox 表，拿到这条任务，异步去调用 LLM 做记忆抽取，生成记忆候选
抽取成功之后，标记 Outbox 这条记录为已完成；失败了可以重试，不会丢任务

**领导可能问：为什么不直接把整段聊天永久塞给模型**？答：聊天冗长、有噪声，可能含错误、过期和敏感内容；模型窗口也有限。把可复用结论做成带来源、范围和状态的对象，才能复核、撤回、删除，并让上下文保持精简。

### 08｜工程现场一变更，依赖它的候选和记忆就要复核

**本页核心**：目标机制是“外部变化 → 找到引用它的候选、记忆和知识 → 先停止旧结论召回 → 复核新版本”；这条全链路目前待建。

**口头讲解**“：沿用版本 1 到版本 2 的例子：我们要记录哪条记忆依据了哪个资产版本。这种‘谁依赖谁’的清单就是依赖索引。外部系统说版本改变了，天枢便反查所有引用版本 1 的内容，先标记待复核并清掉可检索副本，再请责任人确认版本 2 是否还能使用同一结论。如果通知丢了，定期对账补回来；通知还在路上时，真正召回前再查一次当前版本。”

**领导可能问：有了变更事件，为什么还要读取时复核**？答：事件可能延迟或丢失，权限也可能刚被撤销。事件负责快速批量触达，读取时复核负责守住传输窗口；两者结合才能减少旧记忆继续“挂着有效”的风险。

### 09｜准确、有效、持续更新：把证据和状态都存下来

**本页核心**：准确性靠来源和确认，有效性靠适用范围与读取复核，持续更新靠变更联动和可追溯版本；无法保证模型提议绝对正确。

**口头讲解**：“记忆不是写进去就永远真。它从证据引用开始，以待确认候选进入系统；确认后有生效时间、适用范围和负责人；每次使用还要看权限、有效期和所依赖的工程版本。来源改了，记忆进入复核；被取代或删除，退出召回。相比‘给模型一个永久笔记本’，这里更像有有效期、可撤销的工程备忘录。”

**领导可能问：人工确认能保证百分之百准确吗**？答：不能。它降低模型误记被长期放大的风险；证据版本、权限复核、冲突隔离、纠错和撤回共同降低剩余风险。衡量时还要看误记率、过期召回率和越权注入是否为零。

### 10｜冲突如何收敛：按冲突类型交给对应责任人

**本页核心**：算法可去重和发现冲突，不能自行裁决矛盾工程结论；工程事实回权威源，工程结论交场景责任人，个人偏好交用户。

**口头讲解**：“如果两个记录都说同一零件版本的结论不同，先把它们放到同一个冲突组，整组暂停召回，不能让模型随机选一条。若是资产版本或验证结果本身冲突，去外部权威源核对；若是在同一证据上得出不同工程判断，由场景绑定的一位责任人轻量裁决；若是用户自己的偏好变了，让用户确认。合并用于结论兼容，覆盖用于确认的新版本替旧版，冻结用于证据未明，归档用于不再适用。”

**领导可能问：会不会变成复杂审批流**？答：目标是轻量绑定一位场景结论责任人，给他一个可追溯的单次裁决待办。管理员只补责任人或处理流程故障，不代替工程判断；没有裁决时先隔离而不是卡住所有无关任务。

### 11｜ACL 同时约束来源、记忆和知识的检索与注入

**本页核心**：至少有两层权限：外部工程资产的访问权，以及天枢记忆／知识对象自身的 owner、场景和发布范围；两层都要过。

**口头讲解**：“知道资料存在，不表示可以打开，更不表示可以让模型读到。天枢先核对平台身份，再向外部系统确认这个用户能否访问该资产；找到记忆或知识后，还要看它是不是属于这个用户、当前场景能否用、知识有没有发布给他。即使检索命中，最后组装上下文前仍要拦一次。个人记忆里写着‘我常看某项目’，不会因此给用户增加该项目的权限。”

**领导可能问：ACL 是管工程资产，还是管记忆和知识**？答：两者都管，但权威不同。外部系统决定资产权限；天枢决定个人记忆和知识适用范围。只要任一层未知或拒绝，受限正文和摘要都不能注入上下文。

### 12｜长任务上下文：预算不足时按规则压缩和舍弃

**本页核心**：先守住当前请求、规则、任务焦点与必要证据，再对历史和低相关内容做摘要、降级或舍弃；必要信息放不下就暂停调用模型。

**口头讲解**：“模型一次能看的内容有限，长工程任务会不断积累消息、工具输出和旧结论。不能简单按时间截断，否则可能把安全约束或当前资产版本截掉。目标做法是先去重和压缩工具观察，再保留本轮请求、未完成阻塞与当前有权的工程证据；已发布知识、个人记忆、历史摘要按相关性依次取舍。预算仍不够，就拆成下一步任务或停止，而不是让模型带着缺失的关键条件继续判断。代码已有一定的 token 估算、裁剪和长对话压缩，跨来源的统一排序还待建设。”

**领导可能问：为什么工程证据比个人记忆优先**？答：工程任务首先要知道“现在这个资产是什么、验证到哪一步”，个人偏好只能影响呈现或工作方式，不能覆盖当前工程事实。这个优先级只在都已授权、有效的内容之间排序，权限检查永远先于排序。

### 13｜会话删除：默认清除由该会话衍生的个人信息

**本页核心**：目标是删除会话时一并处理其衍生个人信息；多来源记忆不能仅删一条引用后就默认继续有效。

**口头讲解**：“用户删除一段会话时，先把会话置为删除中，阻止新写入，再找出由它产生的候选、记忆证据、摘要、任务状态、索引和缓存，逐一清理并留下回执。如果一条记忆同时来自被删会话和另一段独立会话，目标规则是先去掉被删证据、隔离该记忆，确认剩余证据独立且合规后才恢复；已发布知识若引用该会话，也要先下架复核。备份中的旧数据要靠删除墓碑在恢复时再次清理。当前代码已有 `deleting` 重试和本地证据清理，但剩余证据存在时记忆可能仍保持 active，这个隔离复核环节尚未完成。”

**领导可能问：为什么不把相关的所有工程资产也一起删掉**？答：会话删除处理天枢控制范围内的会话及个人衍生信息，不越权删除外部系统的正式工程资产。工作区产物若含个人信息，需要分类和清理；外部资产按其权威系统的规则处理。

### 14｜借鉴成熟范式；工程真值与治理边界由天枢自己补齐

**本页核心**：借鉴成熟方案中的分层记忆、候选操作、可管理对象和时态关系，但工程真值、权限、失效与责任链仍须按韶峰天工的业务契约设计。

**口头讲解**：“LangGraph 帮我们理解会话短期状态和长期记忆的分层；Mem0 提供抽取、去重、更新等思路；Letta 提醒我们把记忆做成可见可编辑的对象；Graphiti 对时间和关系建模有启发。它们解决的是记忆机制的一部分。我们这个系统还要回答‘资产谁说了算、谁有权看、版本变了怎样失效、工程结论谁负责、用户删除后怎样清理’。首期用显式候选和人工确认，是为了先建立可信基线；自动抽取要在真实工程样本上证明质量后再增加。”

**领导可能问：Mem0 等方案会不会过时**？答：架构不绑定某一个项目或检索技术。我们借鉴的是仍有价值的操作范式，是否引入具体组件取决于维护状况、误记与漏记评测、越权风险、更新延迟和运维成本；目标边界不随产品流行度变化。

### 15｜目标架构／当前实现／差距（一）：权威来源与会话底座

**本页核心**：这一页从“真值在哪、账本谁管、身份怎么进入”三方面对照目标、当前代码、上线必建和后续优化。

**口头讲解**：“先看工程真值：目前有本地目录和验证工具辅助开发，但生产权威源的能力接口尚未接入。再看账本：正式路由已经使用天枢自己的本地 SQLite 账本，并有单写者约束；这证明责任归属已经转到天枢，不代表高可用和备份完成。身份方面，天枢现在会在线查询 Java 用户详情，并用内存中的随机票据建立 WS 连接；多实例的一次性消费、登录撤销和长任务续连还要建设。已经用两个真实账号直连读取会话列表，但正式前端到网关到天枢的完整链路尚未验收。”

**领导可能问：既然 production 路由已经启用，为什么不能说生产完成**？答：路由能工作只说明接口已接通。本页的生产基线还包括权威源、故障接管、恢复演练、完整删除、三方真实链路和安全目标的验证；这些不能由一次接口返回 200 代替。

### 16｜目标架构／当前实现／差距（二）：记忆、知识与投影

**本页核心**：当前已做基础记忆候选、有限召回和裁剪；与目标相比，最大缺口是场景隔离、工程来源治理、冲突失效、知识发布边界和删除闭环。

**口头讲解**：“记忆现状要特别诚实：代码中明确前缀‘请记住：’会生成待确认候选，用户确认后生效；但当前显式候选的范围是 `user`，目标首期要收紧到‘用户加场景’，不能把目标隔离说成已经实现。知识已有本地工作流，但还没有完整的权威证据、ACL 与发布治理闭环。上下文已有估算和裁剪，却还没把外部资产、知识、记忆统一做权限和版本复核。删除会移除会话证据，但混合来源记忆可能继续 active。右侧‘必须建设’是上线可信基线，最右列的自动抽取、图谱等是效果优化。”

**领导可能问：这页最容易被误认为已完成的是哪一项**？答：用户加场景隔离和混合来源记忆复核。它们是已确定的目标规则，当前代码分别还有 `user` 范围候选和保留 active 的情况，必须作为差距跟进。

### 17｜先交付可信基线，再按证据升级自动化与检索能力

**本页核心**：A 是真实入口基础联调，B 是目标架构的生产治理底座，C/D 才增加自动抽取、复杂检索和受控共享；每阶段按验收门槛推进。

**口头讲解**：“我们不需要等图谱和全自动抽取完备才交付基础版，但基础版也不能被称为完整生产目标。阶段 A 先把真实前端、平台身份、天枢账本、候选确认、场景隔离与删除跑通并验收。阶段 B 补外部权威源、ACL、工程变化联动、责任人、可靠账本和删除审计，形成可信生产底座。阶段 C 用评测驱动自动抽取、摘要和分层召回；阶段 D 才根据真实收益考虑时态图、向量检索和跨用户知识共享。每一步都守住外部真值和候选确认的边界。”

**领导可能问：为什么先做人确认，后做自动抽取**？答：先有可核对的候选、确认、撤回和错误统计，才知道自动抽取提升了覆盖率还是放大了误记。自动化应替代低价值的人工筛选，不应替代对高影响工程结论的责任确认。

### 18｜票据撤销与账本恢复：先给出可讨论的服务目标

**本页核心：**身份票据证明“谁来建连”，不证明“能访问哪项工程资产”；生产撤销和恢复指标是待评审目标，现行代码未达到完整 SLA。

**口头讲解：**“当前平台登录由 Java 管，天枢通过 Java 用户详情核验身份，然后发一个默认 120 秒、一次性消费的 WS ticket。这个票据只用于建立连接，不能替代工程 ACL。长任务可能跑很久，不能让建连票据无限期充当通行证；重连或到安全检查点要复核登录态、会话归属、资产权限和版本。账本如果故障，不能一边丢记录一边继续做有副作用的动作。页面上的 60 秒撤销、RPO 五分钟、RTO 一小时只是讨论起点，要由实际部署和恢复演练定值。”

**领导可能问：RPO、RTO 分别是什么意思？**答：RPO 是故障后最多可接受丢失多久的数据；RTO 是最多多久恢复服务。两者不是数据库参数，必须结合备份、复制、故障域和演练结果才能承诺。

### 19｜按数据类型设置保留规则，不用一个期限覆盖所有数据

**本页核心：**聊天、临时任务状态、候选、个人记忆、知识、审计和备份有不同保留逻辑；表中期限是讨论值，不是批准政策。

**口头讲解：**“一个待确认候选可能 30 天没人处理就该失效，已发布知识则应按期复核；会话正文、审计日志和备份也不该用同一个期限。更重要的是，正常到期和用户主动删除是两条同时存在的路径：用户删除不能等 180 天后才处理。如果记忆只依赖已到期会话，而我们又没有合规的最小证据回执，那条记忆也应停用。具体天数还要看合同、法律、客户要求和运维能力。”

**领导可能问：备份不能立刻逐条擦掉，删除如何算完成？**答：在线副本先清理；记录覆盖备份周期的删除墓碑，任何旧备份恢复时先重放删除清单，防止已删除信息复活。备份自身到期后再清墓碑。实际完成定义要写进删除与恢复规范。

### 20｜外部依赖不可用时，降级到安全状态并明确告诉用户

**本页核心：**外部系统不可用时要明确“当前状态未知”，不能把缓存、旧验证或开发替身当权威结果继续使用。

**口头讲解：**“如果资产或权限系统超时，可以把有权限展示的旧引用标成历史，不能据此说当前资产仍是旧版，更不能继续写入。如果验证服务故障，任务可以停在检查点，结果必须写‘验证状态未知’，不能宣布通过。如果天枢账本无法可靠写入，连用户输入都不能假装已经受理。对可重试的读取设次数和熔断；工程写入超时要拿操作编号去查结果，不能盲目重做。”

**领导可能问：故障时能不能切回 Fake Java 或本地验证？**答：开发替身只用于联调，不能接管生产真值。正式降级应当停注入、停相关副作用或只展示清楚标注的历史信息，等权威源恢复并复核后再继续。

### 21｜冲突待办只保留裁决所需信息，并能追溯决定

**本页核心：**一个冲突待办只需让责任人看懂差异、来源与可选动作；决定后留下“谁、何时、依据什么、改了什么”的记录。

**口头讲解：**“责任人收到的不是一堆原始聊天，而是两条结论的摘要、各自证据版本、影响范围和合并、采用新版、冻结、归档几个明确动作。首期可以放在天枢站内待办：用户偏好冲突给本人，工程结论冲突给场景责任人。裁决记录保存前后状态和理由，不把受限正文复制进通知和审计日志。无人绑定责任人时提醒管理员补绑，但管理员不代替工程人员下结论。”

**领导可能问：责任人不处理会怎么样？**答：冲突组继续隔离，不进入模型上下文；依赖这一结论的高影响写操作可被阻止。可按影响等级提醒或升级补绑责任人，不自动选边。

### 22｜开发替身逐步退出：先契约对齐，再启用正式数据

**本页核心：**本地目录、Fake Java、本地验证先用于接口开发；接正式外部源时依次做契约测试、影子对照、单场景灰度和扩大范围。

**口头讲解：**“切换不是改一个地址就算完成。先确认正式系统能按约定返回身份、权限、版本、验证结果、错误和操作回执；再影子读取，与现有过程对照，但暂不影响回答；然后在责任人明确的单个场景，让正式数据进入受控上下文，观察越权、版本差异、失效传播和删除；最后逐步扩大。灰度失败时的回退是停止使用不可信数据，绝不是让 Fake Java 顶替正式工程系统。”

**领导可能问：怎么证明可以扩大灰度？**答：至少要证明权限越界为零、版本和验证状态可追溯、变化事件可补偿、删除可核验、故障能熔断，且正式前端和网关链路经过真实账号验收。指标的统计窗口与负责人在实施计划中确定。

## 附录 A｜领导高频问题统一回答库

**1. 这套系统到底要解决什么？**让天枢在长期工程任务中记得有价值的交互与偏好，同时每次仍以当前外部工程事实和权限为准；既能续接，又不会让过期或越权信息误导模型。

**2. 什么是工程真值？谁生产它？**资产当前版本、正式验证结果与权限等由外部现有工程系统负责。天枢保存引用、工作副本和协作证据，不自行宣布正式版本或验证通过。具体服务名可后定，但能力和责任必须先定。

**3. 会话、任务状态、记忆、知识和上下文是什么关系？**会话是原始交互记录；任务状态是从结构化事件归纳出的续接进度；记忆是确认后的个人可复用信息；知识是经受控发布的可复用结论；上下文是本轮从这些来源中筛出的临时资料。它们不是同一张“聊天记录表”的不同名字。

**4. 为什么记忆候选要人工确认？**模型可能误解、遗漏限定条件或把讨论性话语当决定。确认让可持续影响后续任务的内容有明确责任主体。自动抽取可逐步帮助提出候选，但候选仍不能自动进入召回。

**5. 记忆如何保证准确、有效和持续更新？**没有绝对保证，靠一组可检验机制降低风险：稳定来源引用、类型与范围校验、适格确认、冲突隔离、读取时 ACL/版本/时效复核、源变更触发失效、纠错与删除回执。

**6. 工程资产改了，旧记忆如何找到并失效？**记忆记录所依赖的外部资产 ID 和版本；外部事件或周期对账发现变化，依赖索引定位对象并暂停召回；复核新版本后更新或归档。事件到达前的窗口由召回时回源复核守住。此为目标能力，当前链路尚待建设。

**7. 记忆会直接改业务吗？**不会。记忆只可能作为本轮模型输入的一部分；业务写入需经过当前身份、外部资产 ACL、版本检查、工具契约和外部权威系统确认。个人偏好不能增加工程权限。

**8. 谁裁决冲突？**权威资产或验证记录冲突回外部系统；工程结论冲突交场景绑定的工程责任人；个人偏好冲突交用户。算法只做去重、发现和归组；无人裁决时整组隔离。

**9. ACL 到底管哪一层？**外部系统管资产与验证结果的访问权；天枢管个人记忆、知识发布范围及用户加场景隔离。两层都通过后，才允许检索结果进入模型上下文；未知即拒绝。

**10. 为什么不直接用 Mem0 或图数据库？**可以借鉴其抽取和检索能力，但它们不能代替本业务对工程权威源、ACL、责任人、失效、删除和审计的定义。先做可验收的治理基线，再用真实样本证明自动抽取、向量或图检索带来的净收益。

**11. 当前已经完成到哪里？**代码已有天枢本地 SQLite 账本、Java 用户详情核验、天枢内存一次性 WS ticket、显式候选确认、关键词召回、上下文裁剪与部分删除清理。两个真实账号直连读取会话列表成功；正式前端、网关、WS、完整聊天与删除的三方端到端验收未完成。外部工程权威源联动与治理基线尚待建设。

**12. 当前最大的已知差距是什么？**外部权威资产/验证适配尚未接入；首期目标要求用户加场景隔离，但当前显式候选仍为 `user` 范围；混合来源记忆在删除会话证据后可能保持 active；冲突裁决、依赖失效、完整删除和生产恢复仍待建设。

**13. 基线和二期优化怎样划分？**基线回答“能否安全、可信地用于规定范围”，包含权威源、权限、隔离、来源失效、可靠账本和删除；优化回答“能否更智能、更快、更广”，包含自动抽取、向量/图检索和自适应摘要。高风险约束不能被归到可选优化。

**14. 60 秒撤销、RPO/RTO 和保留期限能否直接承诺？**不能。这些是供评审的建议默认值，需由业务、安全、合规和运维按威胁模型、故障域、客户合同与实测演练确定。汇报时明确说“建议值”，不说“现行 SLA”。

**15. 为什么会话删除还要管备份和混合来源？**因为仅删除页面正文会留下摘要、记忆和索引中的个人信息；旧备份恢复还可能让已删数据复活。混合来源对象要先移除被删证据并隔离，确认剩余证据独立合规后才恢复。

**16. 外部系统不可用时能否照常回答？**只能继续不依赖未知工程状态且已完成鉴权的部分。涉及当前资产、验证或权限的判断必须显示“未知”并停止相关写入；不能用开发替身或旧缓存冒充当前事实。

**17. 有限召回怎么理解**现在天枢的记忆召回不是全量、智能、按业务优先级召回；只做了一个受限、简化版本的召回能力，所以叫有限召回（当前运行路径默认最多召回 8 条、约 1200 字符，采用确定性关键词匹配）。目标是完整召回：
1. 先过 ACL 权限过滤 → 只拿这个用户有权看的记忆 / 知识
2. 按语义相关性、业务优先级、记忆生效状态（激活 / 失效 / 待复核）综合打分
3. 还要区分：用户记忆、团队知识、关联协作证据
4. 再配合 Token 预算做裁剪，选出最应该放进本次上下文的一批记忆

> 
> 特点：智能筛选、多维度判断、和权限 + 生命周期强绑定

| fencing / 单写者栅栏 | “旧进程失去写入资格后不能继续改账本，避免两个人同时记不同版本” |
| 删除墓碑 | “给备份恢复留下的删除清单，防止旧备份把已删信息带回来” |
| RPO / RTO | “最多可丢多久的数据 / 最多多久恢复服务” |

## 汇报结束时的收束话术

> “所以这套架构的重点不是让模型‘记住更多’，而是让它只在有权、有效、有来源的条件下复用信息。当前代码已经证明了部分基础链路，但离工程生产可信底座仍有明确差距。下一步先完成真实三方联调，再接外部权威源和治理闭环；自动抽取、图谱和更高级的上下文优化，等基线可靠且评测证明有收益之后分期建设。”
