## 1. 双方要完成什么

前端在当前页面采集用户原文和页面现场，发送给 AI 网关；网关通过 WebSocket 连续返回接收确认、运行进度、最终回答或错误。用户讨论需求、补充条件、要求实施、修改结果、申请发布，均使用自然语言 `chat_start`。只有后端产生了需要用户确认的**场景文件写入**时，前端才发送结构化的 `approve_scene_write` 命令。自然语言中的“发布申请”只表示用户提出了发布意图，不代表资产已经写入或发布成功；写入状态以确认事件为准，资产是否可被产品页面读取还需场景资产服务核实。

```text
用户输入/点击确认
    → 前端：复用当前会话的活动 WebSocket，顺序发送本轮请求
    → 网关：校验信封，交给 Runtime Coordinator
    → AI 运行时：回复、调用工具、校验、生成任务事实
    → 网关：chat_ack / agent_progress / 可选 agent_debug / chat_final 或 chat_error
    → 前端：展示对话、进度、结果、待确认操作
```

当前协议不要求固定的工作流研发阶段数、文件数、工具调用次数或模型文案。前端根据每次真实响应中的事实更新页面，不按旧版合同 Lock 流程硬编码按钮。

### 1.1 本次正式联调的范围

| 范围 | 前端应实现 | 事实来源 |
| --- | --- | --- |
| 普通对话和工程需求 | 用户输入、澄清、修订、最终回复 | `chat_start` 与 `chat_final.response` |
| 运行过程 | 有节制地展示当前阶段、工具状态、测试或运行进展 | `agent_progress` |
| 工程任务状态和验证 | 区分“本轮回答结束”和“工程任务完成”；展示实际验证结果 | `response.status`、`response.payload.task_status`、`completion_check`、工具结果 |
| 场景写入确认 | 每个待确认 `operation_id` 单独预览和确认 | 真实任务产生的 `write_scene_file` 结果、`approve_scene_write` |
| 页面现场 | 每轮自然语言请求携带当前页面的结构化快照 | 前端实时采集的 `ui_context` |

完整会话历史查询、场景资产列表/详情/画布读取、待确认大文件的完整差异读取，**不是当前 AI 网关已经提供的接口**；见第 8 节。

## 2. 服务地址、身份和连接前提

### 2.1 唯一正式聊天入口

```text
ws://<后端可访问地址>:<部署端口>/ws/sessions/{session_id}
wss://<后端域名>/ws/sessions/{session_id}     # 页面采用 HTTPS 时由部署方提供
```

本轮联调约定使用 **8091**，即前端填写 `ws://<服务器 IP>:8091/ws/sessions/{session_id}`。部署地址由环境配置注入，产品代码不要把服务器 IP 写死。`session_id` 位于 URL 路径，不放在 `chat_start` 或 `agent_command` 顶层 JSON 中。

<span style="color: #c00000;">8093 回放使用旧版 <code>37467f4</code> 录制帧，只用于界面演示；新版字段验收以更新后的 8091 真实响应为准。</span>

服务端必须在前端能访问的网卡上监听 8091；仅启动在 `127.0.0.1:8091` 时，其他电脑上的浏览器无法通过服务器内网 IP 连接。后端启动示例：

```bash
PYTHONPATH=src .venv/bin/python -m uvicorn \
  shaofeng_ai_backend.presentation.fastapi_gateway.application:app \
  --host 0.0.0.0 --port 8091
```

启动前先确认 8091 没有旧进程占用；一个端口只能由一个监听进程使用。`0.0.0.0` 是**服务端监听地址**，不是浏览器填写的目标地址；浏览器应填写实际服务器 IP 或域名。

### 2.2 四种 ID 的含义

| 字段 | 谁生成 | 使用规则 |
| --- | --- | --- |
| `user_id` | 前端提供 | 同一用户的连续交互保持稳定。当前代码不能证明该字段与登录凭据绑定，也不能单凭该字段证明用户身份或场景权限 |
| `session_id` | 前端 | 一条真实对话保持稳定；新对话生成新值；放在 WS URL 路径 |
| `request_id` | 前端每次操作生成 | 每条新 `chat_start` 或 `agent_command` 使用新值，用于关联本轮事件；不能把 `task_id` 当作请求 ID |
| `task_id` | 后端 | 工程任务身份；从真实响应取得，不由前端推测或自造 |

同一工程任务的操作必须串行：收到上一条 `chat_start` 或 `agent_command` 的正常 `chat_final` 后，才能发送依赖其结果的下一条操作；尤其不能在看到待确认进度时立即并发发送批准命令。其他互不依赖的请求即使由网关并行处理，前端也必须分别关联状态。每次新操作使用全新的 `request_id`，不要重复提交同一 ID。在此约束下，关联本次操作的 `chat_error` 可按本次提交失败处理。重复提交同一 ID 时，错误帧可能只表示重复提交被拒，原请求仍可能继续，因此不能只凭错误帧中的 ID 判断原请求已结束。断线后重连可沿用同一 `user_id + session_id`，但旧 WebSocket 消息**不会自动重播**，未收到终态的操作结果需要另行核实。

### 2.3 鉴权与网络条件

当前设置默认 `ENABLE_AUTH=false`，此时前端传入的 `user_id` 不构成已认证身份。若部署方启用 `ENABLE_AUTH=true`，握手必须携带 `Authorization: Bearer <token>` 请求头；当前鉴权中间件**不读取 `?token=...` 查询参数**。浏览器原生 `new WebSocket(url)` 不能自行添加任意 Authorization 请求头，因此启用鉴权的浏览器联调需要先约定能注入该请求头的同源代理/网关，或由部署方在受控联调环境关闭该开关。不得把查询参数当成已实现的鉴权方式。

如果页面是 HTTPS，浏览器通常需要 `wss://` 地址和相应的 TLS 入口。连不上时先检查 TCP/WS 握手，再检查消息 JSON；没有握手成功就谈不上 `chat_start` 是否正确。

## 3. 前端向 AI 网关发送什么

### 3.1 自然语言：`chat_start`

<span style="color: #c00000;">允许的顶层字段为 <code>type</code>、<code>request_id</code>、<code>user_id</code>、<code>prompt</code>、<code>ui_context</code>，以及可选的 <code>access_mode</code>。</span> 示例只说明结构；场景 ID、页面数据和用户文字应来自**当前真实页面**：

```json
{
  "type": "chat_start",
  "request_id": "e76a4f1c5ef04755a019780c87606738",
  "user_id": "2113153353906343938",
  "prompt": "请先帮我梳理当前场景中这个工作流的输入、输出和需要确认的条件。",
  "ui_context": {
    "page": "workflow_list_page",
    "scene_id": "scene_demo_001",
    "visible": {
      "page_state": {"button": [], "title": [], "text": []},
      "workflows": []
    },
    "target": null
  }
}
```

<span style="color: #c00000;"><code>access_mode</code> 可取 <code>restricted</code> 或 <code>full</code>；不传时默认为 <code>restricted</code>。它只决定新建任务的权限，已有任务沿用已保存的权限。上面的示例未传该字段，因此使用默认值。</span>

例中的 `scene_demo_001` 只是符合格式的占位 ID，发送前必须替换为当前用户确实可访问的真实场景 ID。例中的 `user_id` 借用本次联调用户，**不是正式协议要求所有用户固定使用的值**。当前网关的 Bearer 凭据与消息中的 `user_id` 没有绑定，默认命令授权策略也不做细粒度权限判断，因此不能据此验收真实登录用户的细粒度权限不足场景。

`ChatStartMessage` 不允许额外顶层字段；不要在 `ui_context` 或请求顶层塞入机械命令。`ui_context` 是本轮用户所见的页面索引，不是工作流文件正文，也不是后端授权事实。它每轮都应重新采集：

- `page` 必须是当前支持的页面类型；工作流相关页面包括 `workflow_list_page`、`workflow_canvas_page`、`node_library_page`。
- 除 `scene_center_page`、`account_management_page` 外，页面必须有非空 `scene_id`。需要把它用于工程任务时，前端还必须校验格式：仅允许英文字母、数字、下划线、点和连字符，长度 1–128，且不能是 `.` 或 `..`。格式合法仍不代表该场景目录存在或用户有权访问。
- `visible.page_state` 必须存在；列表页上报本页可见的 `workflows`，画布页可上报 `library_nodes`、`canvas_detail`。不要把另一页面的非空业务分组混入当前页面。
- `target` 可为 `null`；若指向工作流、画布节点或按钮，`type` 必须适用于当前页，`id` 必须实际出现在对应 `visible` 项中。仅有一段标签文字不能代替对象 ID。

当前页面与可用的业务 `visible` 分组对应如下。各页面都要有 `visible.page_state`；不在本页范围内的业务分组应省略或保持为空：

| `page` | 当前页业务分组 | 是否需要 `scene_id` |
| --- | --- | --- |
| `scene_center_page` | `scenes` | 否 |
| `scene_app_list_page` | `apps` | 是 |
| `workflow_list_page` | `workflows` | 是 |
| `workflow_canvas_page` | `library_nodes`、`canvas_detail` | 是 |
| `node_library_page` | `library_nodes` | 是 |
| `task_center_page` | `tasks` | 是 |
| `report_page` | `reports` | 是 |
| `knowledge_base_page` | `knowledge_entries` | 是 |
| `scene_management_page` | `scene_packages` | 是 |
| `account_management_page` | `account_applications` | 否 |

在 `scene_center_page` 选中场景时，`target: {"type":"scene", ...}` 只表示页面焦点，不会自动填充 `ui_context.scene_id`。若本轮要在选中场景的工作区执行，应同时填写相同且符合上述格式的 `scene_id`，并由前端保证两者一致。仅提供 `target` 而不提供 `scene_id`，不能视为已绑定该场景。

信封字段合法但 `ui_context` 内容非法时，后端可返回 `chat_final.response.status="blocked"`，其 `response.payload.issues[]` 含 `code="UI_CONTEXT_INVALID"` 和可能的 `field_path`；这不是网络断开。

<span style="color: #c00000;">当前 UI 校验对 <code>scene_id</code> 只要求非空；若明确指定的场景无法解析或不可访问，当前网关返回关联的 <code>chat_error</code>，不会改为搜索其他场景。允许缺少 <code>scene_id</code> 的页面只进入普通对话，不创建工程任务或提供工具。</span>

### 3.2 文件确认：`agent_command`

<span style="color: #c00000;"><code>agent_command</code> 目前只接受 <code>approve_scene_write</code>。任务创建、续接、澄清、修订和发布申请均通过自然语言 <code>chat_start</code> 完成。</span>

| `command.command` | 必需的 `command` 字段 | 用途与限制 |
| --- | --- | --- |
| `approve_scene_write` | `task_id`、`operation_id` | 确认当前任务产生的一次性场景写入；不能带 `goal`、`scene_id`、`access_mode` |

<span style="color: #c00000;">有可访问场景时，<code>chat_start</code> 只查找相同 <code>user_id + session_id + scene_id</code> 的最近任务；未找到时新建。没有场景时只进行普通对话，不搜索或创建任务。新建独立对话应使用新的 <code>session_id</code>；普通 <code>chat_start</code> 不能指定 <code>task_id</code>。</span>

确认命令示意：

```json
{
  "type": "agent_command",
  "request_id": "0d41ac48e876442d83b83320a52fc27a",
  "user_id": "2113153353906343938",
  "command": {
    "command": "approve_scene_write",
    "task_id": "从当前真实任务的响应取得",
    "operation_id": "从当前待确认操作取得"
  }
}
```

上面两个中文值是**占位说明，不是可直接发送的 ID**。实际 `operation_id` 为后端发出的 32 位小写十六进制字符串；`task_id`、`operation_id` 必须来自同一请求上下文中的任务和操作，并与原 `user_id + session_id` 匹配。当前客户端 `user_id` 本身不等于经过认证的真实用户身份。本命令顶层只能有 `type`、`request_id`、`user_id`、`command`，不能附带 `prompt` 或 `ui_context`；确认命令也不能附带 `goal`、`scene_id` 或 `access_mode`。

### 3.3 其他已实现操作

| 请求 | 当前行为 | 前端处理 |
| --- | --- | --- |
| `{"type":"ping"}` | 返回 `pong` | 仅作应用层连接探测，不代表 AI 任务成功 |
| `chat_cancel`，前端应指定目标 `request_id` | 返回 `chat_cancel_ack`；`accepted=true` 时取消分支还会尝试发送顶层 `cancelled=true` 的 `chat_final` | ACK 与原请求结果可能交错；`accepted=true` 仅表示取消请求被受理或取消信号已发出，不证明原任务已停止，也不证明副作用已撤销。按目标 ID 汇总后续帧，遇到冲突结果时标为状态待核实。未指定 ID 时网关会尝试选择最近请求，不应依赖该回退行为 |

不要把 WebSocket 协议层 ping 与 JSON 消息 `{"type":"ping"}` 混为一谈。

## 4. AI 网关返回什么，前端如何归并

| 事件类型 | 关键字段 | 前端处理 | 是否结束本轮 |
| --- | --- | --- | --- |
| `chat_ack` | `request_id`、`session_id`、`status=accepted` | 显示“已受理”，继续等待 | 否 |
| `agent_progress` | `stage`、`message`、`payload`、`created_at` | 展示简短进度；按 `request_id` 归属，工具调用按 `call_id` 关联，不要仅按阶段名称去重 | 否 |
| `agent_debug` | `trace_id`、`seq`、`event`、`payload` | 开发调试抽屉/问题定位；真实部署可能不发送 | 否 |
| `chat_final` | `request_id`、`response`，取消时还可能有 `cancelled=true` | 正常请求保存正式回答并结束 loading；取消场景可能有重复或与正常结果冲突的终态，需按第 7 节处理 | 正常请求是；取消场景不保证唯一 |
| `chat_error` | `message`、有时含 `request_id` | 展示网关/信封/未捕获错误；按单次提交约束判断本次操作失败，不能把重复 ID 错误当作原请求终态 | 依错误场景而定 |
| `chat_cancel_ack` | `request_id`、`accepted`、`task_cancelled` | 展示取消受理情况；与同 ID 的终态可能乱序 | 否 |
| `pong` | `session_id` | 连接探测反馈 | 否 |

按 `session_id + request_id` 关联可关联的事件；`pong` 没有 `request_id`，`agent_progress.request_id` 可能为空，某些连接级 `chat_error.request_id` 也可能为空。不要把无请求 ID 的错误猜成某一轮的结果。过程事件和其他连接的进度可能交错，前端不能靠一个 `agent_progress` 判断本轮已结束。未取消的正常业务请求以本轮的 `chat_final` 为终态；取消请求须按第 7 节处理。前端保证本次操作只提交一次且 ID 唯一时，关联的 `chat_error` 可结束该次提交并显示失败；若可能存在同 ID 重复提交，则不能仅凭该错误结束原请求的 loading。

<span style="color: #c00000;"><code>chat_final.response</code> 的通用字段为 <code>status</code>、<code>message</code>、<code>payload</code>、<code>needs_clarification</code>、<code>clarifying_question</code>；不再返回 <code>route</code> 或 <code>task_type</code>。</span> 取消终态只保证部分字段，不能假定 `payload` 一定存在。`response.message` 是普通聊天区的正式文案；`workflow_agent.assistant_text` 过程事件可能与它重复，不要显示成两条相同回答。

### 4.1 两层状态必须分开

- `response.status` 是**这一轮**的状态，例如 `ready`、`completed`、`blocked`、`failed_resumable`；`ready` 可以只表示回复已经给出。
- `response.payload.task_status` 是**工程任务**状态，例如 `active`、`completed`、`blocked`、`failed_resumable`。一个已完成的工程任务接受后续只读问答时，本轮仍可能为 `ready`。
- `response.payload.completion_check` 在工作流响应中可能始终存在；本轮未运行工作区完成门禁时值为 `null`。只有该值为对象且 `data.valid=true`、结果状态为成功时，才可标“本轮工作区产物门禁通过”。这不是“CGraph 整图已成功运行”：当前正式网关未注入 CGraph 执行器，`run_cgraph_workflow` 不会注册，完成门禁也不会要求整图运行成功。整图运行结果必须另有真实的成功执行记录才能展示为通过。
- `response.payload.tool_results` 是**任务累计结果**，不是每次响应只新增的结果。单条结果没有所属 `request_id`，也没有通用的发生时间字段。不要因为新响应再次包含旧工具记录就重复显示旧确认弹窗，或把历史运行结果说成本轮重新运行。判断新结果需结合本地已见记录或本轮进度事件；无法判断时不要标注为本轮结果。展示单位时只使用结构化结果实际提供的单位，不要从文案推断。
- `task_status="completed"` 表示当前已配置的工作区完成门禁通过，不等于 CGraph 整图运行通过，也不等于场景资产已经发布。资产是否已应用或可被产品页面读取，需要相应确认事件及场景资产读取来源核实。

示例：一次真实录制中的讨论轮为 `response.status=ready`、`payload.task_status=active`；实施轮通过工作区完成门禁后为 `completed/completed`。这些是状态含义示例，不是所有任务必须依次达到的固定阶段，也不证明整图运行成功。

## 5. 页面应如何展示

| 区域 | 建议展示 | 依据与限制 |
| --- | --- | --- |
| 对话区 | 用户本轮输入、Agent 最终回答、必要的澄清问题 | 用户原文与 `chat_final.response.message`；不要把工具日志当聊天气泡 |
| 进度区 | 正在查找节点、编辑工作区、运行节点测试、校验工作区等实际阶段 | `agent_progress.stage/message/payload`；可折叠、去重；Debug 事件不向普通用户铺满页面 |
| 任务与结果区 | `task_id`、任务状态、当轮校验、实际运行输出及结构化结果提供的单位 | `response.payload` 中真实结构化工具结果；不能从模型文案反推权威数据或单位 |
| 确认区 | 待写文件路径、差异预览、哈希、截断提示、确认状态 | 前端保存已见 `operation_id`，结合带匹配 `request_id` 的本轮进度识别新操作；若进度没有请求 ID 且前端没有已见记录，仅凭一份最终响应不能判断记录是否本轮生成。确认卡以 `operation_id` 而非文件路径为单位。 |
| 节点库/工作流列表/画布 | 已发布的权威资产 | 需要场景资产读取来源；当前 AI Gateway 不能仅凭聊天响应提供完整列表与图文件。若产品前端没有其他场景资产服务，这部分不属于当前 Gateway 可验收能力 |

流程并非固定轮次：用户可以先讨论，再补充要求，再让智能体实际实施；验证失败可能继续修复；发布可能产生零个、一个或多个待确认写入操作。前端只根据真实返回建立卡片，不能按某个示例固定“必定四份文件”。一个文件路径也可能对应不同操作 ID。

## 6. 场景文件确认的准确时机

受限写入成功创建待确认操作时，工具 `write_scene_file` 返回 `status="requires_confirmation"`，数据包含 `operation_id`、`path`、`old_sha256`、`sha256`、`diff`、`diff_truncated`。`agent_progress` 中的 `workflow_agent.tool_completed` 可用于发现和关联本轮操作，并提供进度预览；最终响应可补充差异元数据，但其中的 `tool_results` 是任务累计列表，不能仅凭它判断某条记录是否本轮新建。过程事件可能没有 `diff_truncated` 等字段。

前端对每个真实操作 ID：

1. 只建立一张卡，显示文件路径、变更摘要和差异。如果 `diff_truncated=true`，明确标示“差异预览已截断”，不能把展示的片段说成完整文件。
2. 进度事件出现待确认操作时，可以先展示预览，但必须等产生该操作的原 `chat_start` 或 `agent_command` 收到正常 `chat_final` 后，才允许用户点击确认。若原请求断线、报错或终态未明，先将操作标为待核实，不直接发送批准命令。允许确认后禁用重复点击，使用**新的** `request_id` 发送第 3.2 节的 `approve_scene_write`；保持原 `user_id + session_id`，并使用原任务的 `task_id`。
3. 收到与本次 `request_id`、`operation_id` 匹配的 `workflow_agent.scene_write_approved`，表示该文件已应用；之后的 `chat_final` 表示 Agent 续跑结果。续跑失败不会撤销已应用的文件。并非所有确认失败都会返回 `SCENE_WRITE_REJECTED`；任务查找或场景检查先失败时可能返回 `chat_error`。
4. 后续 `tool_results` 仍可能包含历史 `requires_confirmation` 记录；已确认的操作不能重复弹出。若产品前端已接入场景资产读取服务，可用它核实资产及版本；当前 AI Gateway 没有该读取接口。无可用读取来源时，应如实显示无法核实，不能把任务完成状态当作资产已发布。

当前没有配套的“拒绝场景写入”命令；关闭弹窗只表示前端暂不确认。当前 AI Gateway 也没有按 `operation_id` 获取**完整待确认文件内容**的接口；遇到被截断的差异，正式审批页面若要求用户先看全文，需与后端补齐读取能力后再作为验收项。

## 7. 错误、取消与重连

| 现象 | 如何识别 | 前端处理 |
| --- | --- | --- |
| TCP/WS 握手失败 | 浏览器没有 WS `101 Switching Protocols`，没有 `chat_ack` | 核对服务器监听地址、端口、防火墙、代理、`ws/wss` 与鉴权；不要改 prompt 猜原因 |
| 请求信封非法 | 相关联的 `chat_error`，如多带顶层字段 | 按当前 Schema 改请求；新操作生成新 `request_id` |
| 页面快照非法 | `chat_final.response.status="blocked"`，`payload.issues[].code="UI_CONTEXT_INVALID"` | 根据 `field_path` 修正本轮 `ui_context`，不要把它当网络错误 |
| 机械命令未通过授权门禁 | `chat_final` 中 `status="blocked"`、`payload.error_code="COMMAND_NOT_AUTHORIZED"` | 仅在接入会拒绝命令的授权策略时可验收；当前默认策略放行所有命令，不能用于验收真实权限不足 |
| 场景确认被拒 | 批准流程中的特定拒绝会返回 `chat_final`：`status="blocked"`、`payload.error_code="SCENE_WRITE_REJECTED"`；更早的任务或场景检查失败可能返回 `chat_error` | 保留错误并停止自动重试，先核实拒绝原因和待确认操作状态；不要假定原操作仍可用或必定需要新操作。只有后端实际产生新的 `operation_id` 时，才按新操作展示和确认 |
| 用户取消 | `chat_cancel_ack` 与目标请求的 `chat_final` 按同一 `request_id` 关联；ACK 和原请求结果可能乱序，取消分支及原请求分支也可能各发一条 `chat_final` | `accepted=true` 只表示取消被受理或已发信号；即使收到 `cancelled=true`，也不能据此认定业务副作用未发生。若同 ID 还收到正常结果、重复终态或结果相互矛盾，保留全部帧并标为状态待核实；`accepted=false` 也不能反推原请求的最终状态。取消不会回滚已发生的副作用 |
| 页面刷新或 WS 断开 | 旧连接消失，旧帧不会重播；断开时正在运行的请求会被网关取消 | 无法核实的写入显示“状态未知”，列为接口缺口，不能自动再批准一次 |

前端对异常和超时必须区分：**尚无新事件**、**连接断开**、**关联请求收到业务阻断**、**请求终态已到**。模型回复长时间未结束时不能自行伪造 `chat_final`。

## 8. 当前尚缺的浏览器读取能力

当前 AI Gateway 对浏览器提供的主入口是 `/ws/sessions/{session_id}`。它没有通用的“按会话读取历史聊天帧”接口，也没有按 ID 读取正式节点 manifest、工作流 manifest、图文件的浏览器 HTTP API。因此：

- 同一个真实 `session_id` 有助于后端找到工作区与对话上下文，但**不等于**刷新后可重新获取此前所有聊天消息。前端若要避免开发时热更新清空页面，可暂存已展示消息；产品级跨设备历史需另设计服务端接口和权限。
- `workspace_files` 是任务工作区文件列表，不是已发布场景资产列表。最终画布不能从 `response.message` 或本机 `.var` 路径生成；应由场景资产服务提供授权读取数据。
- 当前聊天调试页及其观测服务有仅供研发使用的工作日志/DAG 读取接口；它们不是这份产品前端正式协议的一部分。

这些缺口应作为联调阻塞项或待联调接口明确记录，不能用静态演示数据冒充已上线能力。

## 9. 前端最小联调顺序与验收

1. **连接层**：前端通过实际服务器 IP 的 8091 完成 WS `101` 握手；记录 URL、时间、服务端监听地址。先验证 `ping`/`pong`，再验证聊天，避免把网络问题误判为模型问题。
2. **自然语言层**：发送有效 `chat_start`，检查相同 `request_id` 的 `chat_ack`、进度和 `chat_final`；展示最终文案、当轮状态和任务状态。真实 LLM 文案、耗时和进度条数允许变化。
3. **上下文层**：分别从工作流列表页和画布页发送真实 `ui_context`；测试一个合法 `target` 和一个非法对象引用，确认后者是 `blocked` 而不是连接失败。
4. **工程执行层**：在得到真实需求和场景授权后，检查工具进度、实际节点测试结果和工作区完成门禁，分别展示证据。当前正式网关未配置 CGraph 执行器，不能把 `task_status="completed"` 或门禁通过当成整图运行成功，也不能把整图运行列为此网关当前可完成的验收项；如项目要求整图运行联调，应记录为当前部署能力缺口。
5. **确认层**：仅在出现真实 `requires_confirmation`、且产生该操作的原请求已正常结束后发送 `approve_scene_write`；验证一次性操作 ID、确认后续跑、去重与错误反馈。没有待确认操作时不测试假确认。
6. **恢复层**：刷新页面后确认产品目前能恢复哪些本地展示数据，哪些仍需要未来历史接口；不得把同一会话 ID 误当作聊天历史接口。

最低通过标准：浏览器可达本次部署配置的 8091；两种输入信封严格正确；前端能解析已定义的 WS 类型，并按 `request_id` 关联带有该字段的事件。`agent_debug` 为可选事件，`pong` 和 `chat_cancel_ack` 仅在相应操作触发时验收；用户能理解澄清、处理中、完成、阻断、确认和状态未知；结果取自结构化事实；缺失的历史与资产读取接口被如实标记。当前默认授权策略不能作为真实权限不足的通过证明。
