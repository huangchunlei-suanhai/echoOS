# 工作流需求澄清

本 Skill 是工作流实现的前置门禁，不是可选建议。凡是目标、关键输入输出、工程结果含义、运行参数、交付范围或验收方式存在会实质改变实现的未决事项，必须先用自然语言向用户提问并结束本轮；得到具体答复前，不得开始实现或写入 DAG、节点代码、场景资产。把假设列出来、说明风险或提出推荐方案，不等于用户确认。

## 先查事实，不让用户替 Agent 查资料

在提问前，先按需检查当前工作区、现有 DAG 和节点、可复用节点、相关 Skill、CGraph 协议、运行时目录和执行工具。检查环境前置条件：实际 Python 解释器、CGraph import、NodeCatalog 扫描根目录、pytest、关键依赖、浏览器或外部服务。缺少依赖或权限是验证风险/阻断；不要偷偷缩减目标。

把信息明确分为：
- **已证实事实**：由工作区文件、可信节点接口或工具结果支持。
- **待验证假设**：可用默认继续且不会改变工程意义的细节；明确标注，不伪装成事实。
- **用户必须决定的事项**：不同答案会改变目标、结果解释、关键接口、单位/坐标含义、交付对象或验收标准。

不要要求用户替 Agent 设计 DAG、端口、分类、算法库或节点组合；这些应由 Agent 查证和规划。

## 必须暂停并提问的决策

只要答案不同会实质改变以下任一项，就先提问并暂停受影响的实现：
- 任务类别、实际目标或最终交付对象；
- 必需输入、输出、参数、文件格式、单位、坐标系/基准；
- 结果的工程含义、物理假设、材料/质量模型、算法或方法；
- 用户要求的复用范围、发布/写入位置或运行目标；
- 用户接受的完成标准、关键精度或验证方式。

工程工作流常见必须澄清项包括：诸如“重心”所指的体积几何质心还是按真实质量分布计算的质量重心；STL 等无单位文件的长度单位和坐标框架；输入是单个模型还是装配；最终需要的是数值、文件、报告还是可视化；交付应留在任务工作区还是写入场景。按任务相关性提问，不机械地把所有问题都问一遍。

用户没给材料属性、单位或坐标约定时，不能因为存在常用默认值就将其视为已确认。若该默认会改变结果的工程含义，必须征询用户；只有用户明确接受该假设后才按其执行。

## 明确的停止规则

- 提问必须在普通自然语言中简洁、具体，说明为什么答案影响实现；提出必要问题后立即结束当前回合，等待用户自然语言回答。
- 用户只说“继续”“开始”“照做”等泛化指令，而此前提出的关键问题仍未回答时，不得将其解释为对任何特定选项或假设的同意。应指出仍待回答的具体问题，并继续暂停实现。
- 多个问题中，用户明确回答的部分记为已确认；仍会改变结果或接口的未答项继续阻断相关实现。不能用“我会先按 X 假设”绕过阻断。
- 允许在等待时继续做不改变结果的资料查阅、库节点检索和方案说明；不允许把“继续查资料”变成写实现、创建 smoke 测试图或发布资产。
- 自然语言具体答复已经解决关键决策后，不再额外设置确认按钮或反复要求用户确认；复述已达成口径并按请求推进。

## 概览、决定记录与验收

向用户说明拟解决的问题、主要步骤、每次运行的关键输入、输出、已确认事实、待用户决定的关键事项、可接受的安全默认、风险和验收标准。只有在关键决策都足以确定可实施范围后，才可以落图和编码。

验收分层：节点业务测试、Catalog 发现、DAG 加载、整图执行、数值/物理验证、用户界面或浏览器验证。对 HTML/可视化必须区分静态结构存在、浏览器实际渲染、交互实际可用；没有浏览器工具时不能声称后两者通过。外部 CDN、网络、求解器和用户文件均应列为适用风险。

## 澄清完成后的闭环实施

关键需求清楚且用户已要求实施后，自主进行实现，不再等待额外“确认”按钮。实现过程中若出现会改变目标、关键接口、结果语义、复用范围或验收含义的新歧义，暂停受影响部分并重新提问；普通局部技术细节用可验证默认处理。

每个节点都需要真实源码和测试；测试布局必须适配真实 NodeCatalog 扫描目录。区分普通算法 smoke、Catalog 发现、正式 DAG 加载和真实整图执行；缺依赖或权限时如实说明，不能用 stub、固定输出或占位说明替代目标。smoke 文件只能标记为测试输入，不得当作用户模型结果。

用户已明确回答或确认的事实要加入当前需求，不重复询问；用户自然语言补充就是决策记录。

我先只梳理需求，不会写文件。按你目前的描述，目标是根据两齿轮齿数和主动轮转速，计算传动比与从动轮转速。

需要你确认的是会改变结果含义的定义：

  1. 传动比口径：采用齿数比 i=z从动z主动，还是 i=z主动z从动？不同工程资料对“传动比”的定义并不统一。
  2. 转速输出是否带方向：只输出从动轮转速的大小，还是同时表示旋转方向？若要方向，还需区分外啮合还是内啮合；当前输入里没有啮合类型。
  3. 单位：主动轮转速是否按 rpm（转/分钟）输入，输出也用 rpm？齿数则按无单位的整数处理。

一个可选的简化口径是：传动比定义为从动轮齿数除以主动轮齿数，输入和输出转速均用 rpm，只计算转速大小，不表示方向；仅适用于标准齿轮啮合关系下的转速比计算。你可以确认采用这套口径，也可以逐项给出其他定义。

我确认：采用外啮合；传动比 i 定义为从动轮齿数除以主动轮齿数。输入为主动轮齿数 20、从动轮齿数 40、主动轮转速 1200 rpm，齿数是无单位正整数，转速是非负的 rpm。输出传动比应为 2，从动轮转速幅值应为 600 rpm，并用单独的 relative_direction=-1 表示与主动轮方向相反。忽略效率、载荷和滑移；对零齿数、负齿数、负转速给出明确输入错误。现在请在当前任务工作区实施真正可由 CGraph 加载和执行的工作流、必要的可复用节点和每个节点的 pytest 测试；运行工作区校验、图加载和整图执行，并报告实际输出与证据。此轮不要发布或改写场景资产。

# CGraph 工作流设计

本 Skill 的需求澄清门禁是强制的：先读取 `workflow-requirements-clarification`，再查现有资产和协议。只要关键工程语义、输入输出、单位/坐标、交付范围或验收有会改变实现的未决项，必须向用户自然语言提问并结束当前回合。没有收到针对性答复前，只能查证和说明方案，禁止创建/改写 DAG、节点源码、节点测试或场景资产。把默认假设告诉用户不等于得到同意；“继续”也不是对未答问题的答案。

完成澄清后，交付可由真实 CGraph 编译执行的工作流 JSON、自包含可复用节点和逐节点测试。图不能是说明插图，不得以规划、固定数值或检查壳替代用户目标。工程事实以当前文件、可信节点查询、CGraph 源码及真实工具结果为准。

## 需求与复用

先查工作区、已有图、可复用节点、协议和运行环境；只让用户决定会改变目标、关键输入输出、物理解释、关键单位/坐标、交付位置或验收的事项。不要让用户替 Agent 设计 DAG、端口或库调用。用户回答关键问题后，复述已确认范围并立即按请求实施，不需要额外按钮。

工作流应面向一类需求设计参数；当前算例仅作运行时输入或 smoke 样例，清晰标注，不能伪装成用户业务算例。先查询节点再读可信接口，不凭空假设节点存在。节点库和 Skill 库是长期资产，优先稳定职责与可迁移性。

## 正式文件命名

正式入口统一为 `workflow/workflow.json`。DAG 是有向无环图的结构名称，不规定文件名。图校验、加载、执行和打包应使用同一个正式入口，不得维护两份各自演化的规格。

文件必须使用真实 `CGraphWorkflowSpec`，包含 `node_specs`、`nodes`、`edges`、`inputs`、`outputs`、`input_bindings`、`output_bindings` 及必要 metadata；不能改成自定义简化 DSL。规格文件和 CGraph 编译生成的低层执行 JSON 是不同产物；编译产物可存于 `artifacts/`。

## 图结构协议

- `node_specs[].id` 对应实例 `node_type_id`；`instance_id` 唯一；`kind` 使用适配器支持的 `execute`。
- 边引用实例 ID；DATA 边声明 `from_port`、`to_port` 和所需 `artifact_contract`；CONTROL 边表达顺序并按协议补字段。
- 必需输入有唯一绑定、上游边或明确默认值；工作流输出绑定真实节点输出。可选输入必须有具体默认或受支持的缺席策略。
- dtype 来自真实封闭枚举；复杂载体用 `semantic_type`、`unit`、`extensions.artifact_contract` 声明格式、单位和读取方式。
- 分类来自真实 taxonomy；节点源码 manifest 与图快照一致。
- `metadata.artifacts` 为每个实例声明节点源码和测试映射；`metadata.runtime_inputs` 为可复现且明确标记的 smoke 输入。
- DATA 依赖应有 CONTROL 可达路径；检查环、重复边、悬空字段、缺失输入和不可达节点。

## 节点必须独立交付

每个节点源码文件必须自身定义可注册的 `ExeNodeType` 类，提供合法端口输入后能独立导入、注册并执行。不得导入其他节点源码或另附不可注册 helper。节点间只通过 workflow 端口和文件契约协作；禁止动态导入或修改 `sys.path` 隐藏耦合。少量必要重复优先于隐式源码依赖。不得使用无独立工程含义的万能命令节点。

## 扫描布局

通过真实 NodeCatalog/执行器确认扫描根目录，不假定 `workflow/nodes/`。若扫描根目录为 `nodes/`，节点放 `nodes/`，测试放该扫描目录以外，例如 `workflow/tests/nodes/`。扫描目录只放可注册且自包含的节点源码。

## 验证与交付

按需边实现边测试：节点测试覆盖合法输入、错误边界、结构和关键数值；分别验证独立 Catalog 注册及业务行为；随后运行完整 pytest、Catalog 导出、正式文件加载、整图执行和全量门禁。

主动调用 `validate_workflow_workspace`、`load_cgraph_workflow`、`run_cgraph_workflow` 检查正式入口及真实结果。必须区分语法/导入、Catalog 发现、节点测试、正式 JSON 加载、整图执行和物理/数值验证。临时 API 组图不能代替正式入口整图运行。记录解释器、CGraph 来源/版本和依赖；缺依赖先核实并用授权工具安装，不以 stub、常量或模拟结果掩盖失败。

对 HTML/可视化区分静态产物、浏览器渲染和交互验收；没有浏览器工具时不能声称后两层通过。CFD 收敛与图成功不等于物理精度认证。失败时读取真实错误、最小修改并重测。最终报告交付路径、修改、真实测试证据和未完成原因。

# CGraph 节点实现

## 实施前的强制需求门禁

编写、修改节点源码或节点测试前，先读取 `workflow-requirements-clarification` 并查现有工作流和节点接口。节点算法、端口、数据格式或测试断言依赖用户尚未决定的工程事实时，必须先自然语言询问用户并结束当前回合，等待具体答复。不得把假设标注、常见默认、用户说“继续”或一般性的实施指令视为对某个具体选项的确认。澄清前可查证工作区和真实接口、报告方案；不得开始节点代码、冒烟实现或通过改端口绕过问题。得到回答后按已确定需求继续，不再要求重复确认。

可复用节点是工程资产。每个节点必须真实读取输入并生成输出，直接继承 `cgraph.library.ExeNodeType`，可被 NodeCatalog 发现、导出和执行；不得用固定答案、说明壳、fallback stub 或伪造基类替代。

## 自包含节点文件（强制）

- 每个节点源码文件就是一个可独立交付模块，必须在该文件定义一个可注册节点类；不能只交付 helper/utils/runtime。
- 单独取出节点文件，在安装声明的第三方依赖并提供合法端口输入后，必须能独立导入、注册、处理该输入；不得依赖其他节点源码、目录导入副作用或其他节点先执行。
- 环境探测、文件读写和子进程封装可留在节点文件内部。允许少量必要重复；不以动态导入、临时复制或修改 `sys.path` 隐藏耦合。
- 若步骤本身有独立工程含义，设计成可注册节点并通过 workflow DATA 边协作；禁止用任意命令万能节点规避自包含要求。
- 节点可以消费其他节点提供的网格、算例等数据产物；这是数据依赖而非源码依赖。标准库、真实 CGraph、明确声明的第三方依赖和外部求解器依赖允许。

## 实现前检查

在需求澄清完成后，查询并读取 `workflow/workflow.json` 的 node spec、端口、上下游及真实节点源码；读取真实 `DataPort`、`ExeNodeType`、`NodeCatalog` 与验证协议。不要猜测接口、封闭 dtype 或分类。用户算例仅作为运行时输入或 smoke 样例，不写死唯一合法文件、尺寸或工况。

## 节点声明

提供稳定小写唯一 ID、三段版本、展示名、描述、有效分类、tags、DataPort 元组、runtime_hints 和 extensions；run 参数名逐字匹配输入端口。源码 manifest 必须与 workflow 快照一致。

- dtype 使用当前受支持枚举；复杂结构通过 semantic_type、unit、artifact_contract 声明格式、单位、坐标系和边界标签。
- 节点 extensions 声明 semantic_role、合法 physics_domains 和 constraints。
- 当前 CGraph 运行时对 dict 原样按端口映射返回；单个 dict 业务输出应返回 `{输出端口名: 业务字典}`。以真实整图执行验证包装行为。
- 校验缺失、空输入、类型、文件格式、拓扑和物理范围并抛出可定位异常。真实计算依赖必须参与运算，保留真实失败与日志。
- 禁止未声明网络、任意命令、eval/exec 或越权路径。子进程调用限定工具、参数和工作目录，不拼接用户控制的 shell 程序。
- 注释解释算法、单位、错误边界和端口映射，并与实现一致。

## 目录和交付

# CFD 工作流实现约束

开始 CFD DAG、节点代码或场景资产写入前，必须先读取 `workflow-requirements-clarification` 并查证可查事实。流动目标、几何、关键结果、坐标/单位、边界条件、求解模式或验收标准存在会改变实现的未决决策时，先用自然语言具体提问并暂停；不能以常用 CFD 默认值、提出方案或“继续”泛化指令代替用户对决策的答复。等待期间可以查工作区和节点，不能写实现。获得具体答复后记录已确认口径并按请求推进。

本 Skill 提供会改变 CFD 工作流设计和节点实现的领域约束。CFD 工作流要沉淀可迁移能力，不围绕单个 STL 或固定工况写死。

## 需求与物理完整性

- 明确几何、流动类型、目标结果和运行时参数。速度、攻角/来流方向、密度、黏度、参考面积、边界条件、求解模式及质量/收敛门限应有单位和范围。
- STL 通常不带可信长度单位；进入网格前必须由运行时 `length_unit` 或受控来源确定单位。若单位含义会影响结果且用户未确认，先询问，不得默认为 mm。
- 外流场/旋翼链至少表达几何检查、计算域/边界、网格、物性工况、求解、收敛/守恒诊断、力后处理和必要可视化。省略会影响结果的步骤必须写明风险。
- 输出轴向推力或升力系数时必须关联旋转/升力方向、参考面积、来流、单位和坐标系；桨轴朝上时轴向推力才可近似称升力。

## CFD 节点组织（强制）

- 每个 CFD 节点源码文件必须自身定义一个可注册的 `ExeNodeType`，可单独导入、注册并处理合法端口输入；节点文件必须自包含，不得导入其他节点源码或不可注册共享 helper/utils/runtime。
- 环境发现、OpenFOAM bashrc 加载、受限子进程调用、日志保存、字典生成、格式解析等私有函数应内聚在各自节点文件中；允许少量重复，禁止源码辅助模块隐藏耦合。
- 节点间只通过 workflow/workflow.json 端口数据或文件产物契约协作；每个节点文件独立交付时不得需要兄弟节点文件。
- 不得把不可注册 Python 文件作为节点交付，也不得用万能命令节点替代职责明确的 CFD 节点。

## OpenFOAM 环境

- 不要仅凭 `shutil.which` 或当前 PATH 判断安装。检查可配置的 `OPENFOAM_BASHRC` 和已知安装根目录，并在节点自己的受控子进程中 source `etc/bashrc` 后调用 `foamVersion`，记录入口和版本。
- Python 节点不要修改父进程环境；通过受控 bash 子进程加载环境，限制工具、参数和工作目录，保存返回码、stdout、stderr 和 case 日志。
- OpenFOAM 13 常用 `foamRun -solver incompressibleFluid`；`simpleFoam`/`pimpleFoam` 可能只是兼容脚本。版本可用不等于算例、网格、边界和收敛有效。
- 区分未安装、环境未加载、二进制/架构不可运行、case 适配缺失和求解不收敛；不要统一称为求解器缺失。

## 网格、求解与验证

- Gmsh/OpenFOAM 网格必须保留单位、物理组、边界标签和坐标系；网格质量门禁、MRF/旋转区非空、残差、守恒和载荷波动须连接到下游结果。
- 不用固定数字、简化公式或未执行的力文件伪造推力。质量或收敛失败时保留失败状态并禁止发布推力。
- 通过网格加密、模型对比或实验/参考数据验证物理结果；CGraph 整图成功只证明流程和数据交接成功，不证明 CFD 精度。
- 正式入口为 `workflow/workflow.json`；metadata.artifacts 只映射各实例自己的源码和测试。

## 典型功能链

```text
几何与单位 -> 几何/拓扑检查 -> 计算域与边界 -> 体网格与质量
-> 物性/工况 -> 旋转区域与求解器 -> 残差/守恒/载荷稳定性
-> 推力/扭矩/功率及系数后处理 -> 可视化或报告
```

所有会影响结果且已确认的步骤必须在 DAG 中有真实节点和数据边，不能只写在 goal 或 risks。
