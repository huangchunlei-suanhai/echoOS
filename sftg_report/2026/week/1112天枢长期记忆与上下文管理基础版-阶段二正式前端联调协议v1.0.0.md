## 1. 文档目的与适用范围

本文供正式产品前端研发人员接入天枢“会话账本、上下文管理、TaskState 投影和用户长期记忆”基础版。本文描述前端调用的 Java 公共 API、天枢 WebSocket、调用时序、消息字段、错误处理和验收边界。

本文不替代[工作流研发前端正式联调协议 v3.1.0](工作流研发前端正式联调协议v3.1.0.md)。旧协议可用于理解工作流命令的业务字段、页面快照和操作顺序；已接入旧 WebSocket 入口的页面仍按其入口契约联调。但接入本文 `/ws/v1/sessions/{session_id}` 票据入口时，连接地址、顶层消息信封、身份字段和实际返回字段均以本文及当前 v1 代码为准，不能直接复用旧协议的帧示例或完整工作流结果展示。场景文件写入预览与知识发布结论在 v1 的当前输出限制见 4.3 节，相关前端验收须等待输出契约补齐。

本文中的 `/api/ai/...` 是 Fake Java 已实现并通过契约测试的公共接口路径。正式 Java 应完成真实身份核验、用户与会话归属控制，并提供相同语义的产品接口；若正式 Java 采用不同路径，应由 Java 与前端共同完成路径映射，不能把天枢 `/local/debug/...` 路由作为产品接口。

### 1.1 基础版场景约束

本次基础版前端每一条自然语言聊天都必须绑定已有场景 `uav_cax_scene`：

- 每个 `chat_start.ui_context.scene_id` 必须是 `uav_cax_scene`。
- 不显示场景选择、创建或切换到新场景的流程；不发送空 `scene_id`。
- 发请求的已认证用户必须已获准访问该场景。用户没有访问权限时，应显示错误，不应通过改用其他用户、其他场景或无场景模式重试。
- `uav_cax_scene` 是场景标识，不是场景目录路径。前端不拼装服务器文件系统路径。

这部分是本次前端联调的强制验收要求。**当前天枢通用运行时代码尚未全局强制 `scene_id == "uav_cax_scene"`**：它仍支持其他已授权场景，并保留特定页面的无场景普通问答行为。因此，不能把“后端会拒绝其他场景或空场景”当作已经实现的事实。若产品要求服务端也必须强制此基础版范围，需要天枢在正式部署模式增加相应校验并另行验证；前端必须先按本节固定发送 `uav_cax_scene`。

## 2. 链路与职责

```text
正式前端
  ├─ HTTPS REST ──> Java 公共 API
  │                   ├─ 核验平台登录凭证并确定 user_id
  │                   ├─ 管理用户会话及会话归属
  │                   ├─ 签发一次性 WebSocket 票据
  │                   └─ 代理历史、记忆和删除等公共操作
  └─ WSS ─────────> 天枢 /ws/v1/sessions/{session_id}
                      └─ 只接受 Java 签发的一次性票据；身份绑定在票据，不在业务帧

Java 内部服务 ──受保护的服务凭据──> 天枢内部账本、记忆与会话清理接口
```

前端向 Java 传递当前登录凭证。Java 是身份核验和用户身份映射的权威方；前端不得通过请求体或 URL 自报另一个 `user_id` 来决定数据归属。Java 向浏览器返回的会话令牌用于 Java 公共 API；Java 签发的短期、一次性 WebSocket 票据用于建立天枢连接。两种凭证用途不同。

WebSocket 握手完成后，天枢从已消费的票据取得可信用户和会话身份。`chat_start`、`chat_steer` 等业务帧不携带 `user_id`，不能在消息中切换用户或会话。浏览器不得获得或调用 Java 到天枢的内部服务令牌。

### 2.1 Fake Java 与正式实现的差异

直接访问 Fake Java 的 `POST /api/ai/debug-login` 可接受调用者填写的用户 ID 并生成内存态测试令牌；正式前端联调必须经过开发网关，由网关要求 `X-Dev-Access` 并覆盖身份字段。Fake Java 不验证平台凭证，不得把测试登录用于真实用户或部署到生产环境。

默认一键启动器的 Fake Java 三进程链路仍只监听回环地址，默认只允许简易调试页 `http://127.0.0.1:8112` Origin。另有显式 `--frontend-origin` 开发联调模式：启动器额外运行只转发 v1 公共 REST/WS 的网关，固定隔离测试身份，并将显式列出的一个或多个前端 Origin 同时配置给 Fake Java 与天枢。Origin 按 scheme、主机和端口精确匹配，不支持通配。该模式的当前地址、启动参数与前端测试登录方式见[正式前端 v1 开发联调入口](../../sftg_ai_backend/docs/FRONTEND_V1_DEV_INTEGRATION.md)。浏览器到开发网关的网络可达性仍须从正式前端使用者的浏览器确认。Fake Java 只接受自己签发的测试 token，不能验证产品平台 token；正式 Java 身份、票据和账本适配器及生产网络/TLS 配置仍需单独实施。

当前情况 1 的隔离登录身份中，SSH 场景目录名固定为 `huangchunlei`，对应场景仓库副本位于 `tian_shu_data/instances/frontend-v1-dev/scenes/huangchunlei/sftg_cax_scene/uav_cax_scene`。Fake Java 的测试 `user_id` 与 SSH 用户名分开；启动命令省略 `--user-id` 时会生成稳定的 `debug-...` 编号。前端应把该 `user_id` 当作不透明的平台测试主体，不自行改写或据此拼场景路径。

当前简易链路由后端研发人员在后端仓库启动：

```bash
PYTHONPATH=src .venv/bin/python scripts/debug/run_chat_stack.py mock_java \
  --ssh-user-name "<已有 uav_cax_scene 场景的 SSH 用户名>"
```

启动器用 `--ssh-user-name` 定位 `<SCENE_LIBRARY_ROOT>/<sshUserName>/sftg_cax_scene/uav_cax_scene`；当前启动器要求该目录名就是 `uav_cax_scene`。`--user-id` 仅是可选的 Fake Java 测试平台用户 ID，不参与场景路径定位；省略时启动器根据 SSH 用户名生成稳定的 `debug-...` ID。也可用 `--scene-root` 指定非默认的场景库根目录。上述参数只供本地调试，不是正式前端提交的身份字段。

默认 Fake Java 为 `127.0.0.1:8095`、天枢为 `127.0.0.1:8094`、简易调试页为 `127.0.0.1:8112`。这些地址供本机简易页/回环验证使用，不是正式前端配置值。当前 Fake Java 的测试登录入口见 3.1；正式产品代码不得依赖它。

## 3. 地址与公共接口

部署地址由联调环境提供，不能写死在产品代码中。前端至少配置两个逻辑地址：

| 配置项 | 指向 | 用途 |
| --- | --- | --- |
| `javaApiBase` | Java 公共 API 的 HTTPS 地址 | 登录态下的会话、票据、历史、记忆和删除请求 |
| `tianShuWsBase` | 浏览器可访问的天枢 WSS 地址 | 连接 `/ws/v1/sessions/{session_id}`；代理必须支持 WebSocket Upgrade |

当前 Fake Java 联调路径使用 `/api/ai/...`。受保护 REST 请求都带 `token: <Java-issued-token>` Header；Fake Java 还校验准确的 `Origin`。正式 Java 的 Header 名和凭证交换方式由正式 Java 接口实现确认，但前端必须统一从 API 客户端添加凭证，不能在组件里复制身份逻辑。

当前 Fake Java **不能直接复用产品登录后已有的 token**。研发联调时，正式前端页面通过开发网关调用测试登录；网关要求 `X-Dev-Access`，忽略请求体中的身份值，并将请求转换为 Fake Java 使用的固定隔离身份。入口地址、启动命令和密钥文件位置见[正式前端 v1 开发联调入口](../../sftg_ai_backend/docs/FRONTEND_V1_DEV_INTEGRATION.md)。前端须把此差异封装在仅开发环境启用的认证适配层中。产品构建必须使用正式 Java 的登录凭证，不能包含开发密钥或任意用户 ID 登录入口。

### 3.1 会话与账本 API

以下路径相对于 `javaApiBase`。除测试登录外，所有请求均须是已认证用户；所有 `{session_id}` 均使用 URL 编码后的服务端会话 ID。

| 方法与路径 | 用途 | 成功响应 |
| --- | --- | --- |
| `POST /api/ai/debug-login` | **仅 Fake Java 开发测试**；经正式前端开发网关调用时，body 为 `{}` 并携带 `X-Dev-Access`，网关固定注入隔离测试身份 | `{"user_id":"...","token":"..."}`；不可用于产品登录 |
| `GET /api/ai/sessions` | 列出当前认证用户的会话 | `{"items":[{"session_id":"...","state":"active"}]}` |
| `POST /api/ai/sessions` | 服务端新建会话；请求体为空 | `{"session_id":"...","state":"active"}` |
| `POST /api/ai/sessions/{session_id}/ws-ticket` | 为该会话签发 WebSocket 票据 | `{"ticket":"..."}` |
| `GET /api/ai/sessions/{session_id}/messages` | 读取历史消息页 | `HistoryPage`，见 3.2 |
| `GET /api/ai/sessions/{session_id}/events` | 按序号补拉账本事件 | `EventPage`，见 3.3 |
| `GET /api/ai/sessions/{session_id}/requests/{request_id}` | 查询单个请求账本状态 | `LedgerRequest`，见 3.4 |
| `GET /api/ai/sessions/{session_id}/deletion` | 查询会话删除状态 | `state` 为 `active`、`deleting` 或 `deleted`；`deletion_id` 可为 `null` |
| `DELETE /api/ai/sessions/{session_id}` | 删除当前用户的会话 | `204` 删除完成；`202` 清理尚未完成 |
| `POST /api/ai/logout` | 退出当前 Java 登录会话 | `{"logged_out":true}` |

Fake Java 内部的 `debug-login` 测试 `user_id` 必须符合 `^[A-Za-z0-9_-]{1,80}$`；后端可用 `ssh_user_name` 模拟正式 Java 已核验的 SSH 账号映射。当前正式前端开发网关不接受浏览器选择身份，而是固定传入 SSH 用户 `huangchunlei` 和启动器生成的测试 `user_id`。场景目录为 `<SCENE_LIBRARY_ROOT>/<ssh_user_name>/sftg_cax_scene/uav_cax_scene`，目录名也可不同于 `scene_id`，由场景元数据声明标识。正式前端在本 v1 票据会话链路中不得提交或自行选择 SSH 身份，也不能把此测试登录接口用于产品用户。

会话 ID 由 Java 创建。前端不要提交自造 `session_id` 请求新建，也不要把 `task_id`、`request_id` 当成会话 ID。会话列表仅返回当前用户的 `active`、`deleting` 会话；删除完成的会话不再出现在列表中。

### 3.2 历史分页

首次读取可使用 `GET .../messages?limit=100`。当前实现允许 `limit=1..100`，默认 `50`。响应按消息创建序号从旧到新排列：

```json
{
  "items": [
    {
      "message_id": "msg_...",
      "request_id": "request-1",
      "input_id": null,
      "role": "user",
      "content": "用户输入",
      "status": "final",
      "revision": 1,
      "created_sequence": 1,
      "updated_sequence": 1,
      "created_at": "2026-11-11T02:00:00+00:00",
      "updated_at": "2026-11-11T02:00:00+00:00",
      "display_view": {"version": 1}
    }
  ],
  "creation_watermark": 12,
  "next_before_sequence": null,
  "has_more": false
}
```

需要更早历史时，沿用首屏返回的 `creation_watermark`，并使用 `next_before_sequence` 请求：

```text
GET .../messages?before_sequence=<next_before_sequence>&creation_watermark=<creation_watermark>&limit=100
```

`role` 为 `user` 或 `assistant`。`status` 反映消息状态，可能包括 `pending`、`partial`、`final`、`failed`、`cancelled`、`interrupted`、`queued`、`consumed`、`unapplied`。更新中的同一消息可有更高 `revision`；前端用 `message_id` 识别消息、按更高版本更新，不能把每个 revision 都追加成新消息。`display_view` 是受限的历史展示摘要；当前 v1 执行链路仅填充已核验的 `task_id` 和澄清问题，不填充 `operation_id`。虽然 Schema 定义了 `operation_id` 字段，前端不能据此假设刷新历史后能恢复场景写入确认卡，也不能把展示摘要当作动作授权或完整任务事实。

追加输入也会作为带 `input_id` 的用户消息出现在本页：`queued` 表示已写入账本但尚未确认进入模型，`consumed` 表示已写入模型工作集并完成账本消费，`unapplied` 表示请求在它被模型消费前已经结束。`unapplied` 输入不会自动带入下一条请求。助手的模型工作集检查点、工具观察和内部恢复信息不通过本接口展示。

### 3.3 事件补拉

`GET .../events?after_sequence=<cursor>&limit=100` 查询 `sequence > after_sequence` 的事件；当前 `limit=1..200`，默认 `100`。响应结构：

```json
{
  "items": [{
    "event_id": "evt_...",
    "sequence": 3,
    "request_id": "request-1",
    "input_id": null,
    "event_type": "request_status",
    "message_view": null,
    "status": "completed",
    "created_at": "2026-11-11T02:00:02+00:00"
  }],
  "next_sequence": 3,
  "high_water_cursor": 3,
  "has_more": false
}
```

事件类型包括 `message_created`、`message_updated`、`request_status`、`input_status`。WebSocket 断线后，前端可用历史和事件接口核对持久状态；运行中的实时 `agent_progress` 不等同于持久账本事件，也不会因重连自动重播。

### 3.4 请求状态

`GET .../requests/{request_id}` 返回当前请求账本记录，字段包括：

```json
{
  "request_id": "request-1",
  "kind": "chat",
  "payload_digest": "...",
  "status": "completed",
  "user_message_id": "msg_...",
  "assistant_message_id": "msg_...",
  "created_sequence": 1,
  "task_id": null,
  "side_effect_status": "none",
  "error_code": null,
  "created_at": "2026-11-11T02:00:00+00:00",
  "updated_at": "2026-11-11T02:00:02+00:00"
}
```

`status` 可能为 `accepted`、`running`、`completed`、`failed`、`cancelled`、`interrupted`。该记录用于断线恢复或核对；当前连接的新请求仍以终态帧结束，断线重连或重复提交时则应以该记录及历史、事件确认持久状态，不能等待服务端补发旧终态帧。

### 3.5 用户长期记忆 API

| 方法与路径 | 用途 | 成功响应 |
| --- | --- | --- |
| `GET /api/ai/sessions/{session_id}/memory-candidates` | 读取当前用户的记忆候选 | `{"items":[MemoryCandidate,...]}` |
| `POST /api/ai/sessions/{session_id}/memory-candidates/{candidate_id}/confirm` | 确认候选 | `MemoryRecord` |
| `POST /api/ai/sessions/{session_id}/memory-candidates/{candidate_id}/reject` | 拒绝候选 | 更新后的 `MemoryCandidate` |
| `GET /api/ai/sessions/{session_id}/memories` | 读取当前用户状态为 `active` 的已保存记忆 | `{"items":[MemoryRecord,...]}` |
| `DELETE /api/ai/sessions/{session_id}/memories/{memory_id}` | 删除一条已保存记忆 | `204` |

候选的主要字段：`candidate_id`、`owner_user_id`、`kind`、`scope`、`scene_id`、`subject_key`、`claim`、`applicability`、`evidence_ref`、`evidence_session_id`、`evidence_request_id`、`status`、`created_at`。`kind` 当前取 `user_preference`、`scene_fact`、`decision`、`engineering_lesson`；`scope` 当前取 `user` 或 `user_scene`。候选列表接口最多返回当前用户最近 200 条候选，可能包含 `pending`、`confirmed`、`rejected`；前端待确认区域只展示 `status == "pending"`。

已保存记忆的主要字段：`memory_id`、`revision`、`owner_user_id`、`kind`、`scope`、`scene_id`、`subject_key`、`claim`、`applicability`、`evidence_refs`、`evidence_session_ids`、`status`、`created_at`、`updated_at`、`expires_at`。列表只按 `active` 状态筛选，最多 200 条；它不是本轮模型实际召回的记忆列表，召回还会检查场景、过期时间和相关性。`scope == "user_scene"` 时 `scene_id` 必须有值；`scope == "user"` 时 `scene_id` 为空。

记忆归属是用户级，不是当前会话级：同一用户在新会话中仍能看到其用户级记忆。记忆候选必须由用户显式确认后才成为已保存记忆并有机会进入模型上下文；候选本身不会进入模型上下文。确认时后端检查候选来源请求已完成；来源回合尚未完成通常返回 `409 memory_source_not_completed`。确认和拒绝后刷新候选、记忆列表以显示服务端状态。

当前候选生成范围有限：基础实现只对以准确前缀 `请记住：` 开头、且没有被敏感信息规则拦截的成功自然语言请求生成候选。它不是自动从所有对话提炼记忆的承诺；没有候选时前端应显示空态，不应自行生成或伪造候选。这里的长期记忆候选与工作流协议中的“场景知识候选”完全不同，不得混用接口、状态或按钮。

删除会话也会清理该会话来源的记忆候选和记忆证据。若一条已保存记忆没有其他会话的证据，删除来源会话后该记忆将不再出现在 `active` 记忆列表；若仍有其他会话证据，记忆保留并移除已删除会话的证据引用。会话清理未完成时，删除接口保持 `202`，完成后再按上述规则清理记忆数据。

## 4. WebSocket 连接与消息协议

### 4.1 握手

每次新建或重连按以下步骤执行：

1. 经 Java 公共 API 为当前活动会话请求新的 `ws-ticket`。
2. 在票据签发后尽快连接：

```text
<tianShuWsBase>/ws/v1/sessions/{session_id}
```

3. WebSocket 子协议必须包含且只包含一个票据：

```text
Sec-WebSocket-Protocol: tian-shu.v1, ticket.<ticket>
```

前端实际构造参数示例：

```javascript
new WebSocket(wsUrl, ["tian-shu.v1", `ticket.${ticket}`]);
```

票据由 Fake Java 的本地实现设置为 120 秒有效且只能消费一次；每次连接都重新领票，不能重放旧票据。生产票据的过期时长由正式 Java 和天枢部署契约确定，但仍须一次性、绑定目标 `session_id`，并支持登录撤销后失效。

握手必须来自配置允许的 Origin。票据缺失、格式错误、重放、过期、会话不匹配或 Origin 不允许时，当前实现拒绝握手，常见 WebSocket close code 为 `4403`；服务未就绪时可能以 `1013` 关闭。经当前开发网关连接时，上游握手拒绝或超时也可能被网关映射为 `4403`，因此不能只凭该 close code 判定为票据错误。浏览器 WebSocket 不能通过标准构造器添加任意 Authorization Header；不要把票据放进 URL query、localStorage、聊天 JSON 或日志。

### 4.2 自然语言请求 `chat_start`

```json
{
  "type": "chat_start",
  "request_id": "由前端为本次提交新生成的唯一 ID",
  "prompt": "用户当前输入",
  "access_mode": "restricted",
  "ui_context": {
    "page": "workflow_canvas_page",
    "scene_id": "uav_cax_scene",
    "visible": {
      "page_state": {"button": [], "title": [], "text": []},
      "canvas_detail": {
        "workflow_id": "当前工作流 ID；无则为空字符串或 null",
        "nodes": [],
        "connections": []
      }
    },
    "target": null
  }
}
```

字段要求：

- `type` 固定为 `chat_start`。
- `request_id` 每次新提交生成唯一值，长度 1–100；同一会话不能并发提交新的工作请求。前端生成的 ID 使用 `[A-Za-z0-9_-]{1,100}`；当前开发网关只允许此范围的路径段，超出范围的 ID 可能成功提交，但无法通过请求状态 REST 路径恢复。
- `prompt` 去除首尾空白后非空，最长 20,000 字符。
- `access_mode` 可选，值为 `restricted` 或 `full`，省略时为 `restricted`。它影响新任务权限；已有任务不会因前端下一轮改值而重置权限。
- `ui_context` 是当前页面实际可见状态，不是身份或授权凭证。基础版固定 `scene_id: "uav_cax_scene"`；`page` 必须如实反映当前页面，`visible.page_state` 必须存在，并且只上报该页面允许且实际可见的数据组，不把其他页面的数据组混入。上面的 `workflow_canvas_page` 示例对应当前简易前端；正式前端接入其他已支持页面时，应按真实页面和《工作流研发前端正式联调协议 v3.1.0》的 `ui_context` 页面契约构造。
- 不发送 `user_id`、`session_id`、Java token、WebSocket ticket 或自定义身份字段。`session_id` 已在 WebSocket URL 中，用户身份来自票据。
- 顶层未知字段会被拒绝。画布节点、工作流状态或目标对象 ID 只能来自前端真实页面快照，不能从模型回答反向构造。

**基础版发送前校验：** 若当前用户没有已选定的 `uav_cax_scene` 工作上下文，或当前页面无法提供符合 Schema 的 `ui_context`，前端应阻止提交并提示用户回到有权限的该场景页面；不得删除 `scene_id` 后降级成普通聊天。

需要发送工作流结构化命令时，v1 顶层只允许 `type`、`request_id` 和 `command`，例如：

```json
{
  "type": "agent_command",
  "request_id": "本次命令新生成的请求 ID",
  "command": {
    "command": "summarize_knowledge",
    "task_id": "当前真实任务的 ID"
  }
}
```

命令名称及 `command` 内的必需字段仍按工作流协议和后端命令 Schema 校验；上述中文 ID 只是占位说明。v1 顶层不能携带旧协议示例中的 `user_id`，也不能携带 `prompt`、`ui_context` 或 `session_id`。运行中追加输入使用 4.4 节的 `chat_steer`，必须由前端提供新的 `input_id`，同样不能携带 `user_id`。旧协议中的 `/ws/sessions/{session_id}` 路径及其身份字段规则不适用于本 v1 入口。

### 4.3 服务端事件与请求结束规则

| 帧 | 主要字段 | 前端行为 | 是否表示本轮结束 |
| --- | --- | --- | --- |
| `pong` | `session_id` | 连接保活反馈 | 否 |
| `chat_ack` | `request_id`、`session_id`、`status`、`created`、消息 ID | `created=true` 表示新建；`created=false` 表示同 ID 同内容的已有请求，应查账本状态 | 否 |
| `agent_progress` | `request_id`、`stage`、`message`、`payload`、`created_at`、`transient` | 展示进度并按请求 ID 归属；只展示实际收到的字段 | 否 |
| `chat_steer_ack` | `request_id`、`input_id`、`accepted`、`status`、可选 `code` | 展示追加输入是否入队 | 否 |
| `chat_cancel_ack` | `request_id`、`accepted` | 展示取消请求是否被接受 | 否 |
| `chat_final` | `request_id`、`response`，取消时可能有 `cancelled` | 展示正式终态，结束该请求 loading | 是；按对应请求 ID 处理 |
| `chat_error` | 可选 `request_id`、`code`、`message` | 展示错误；只在能唯一关联本次提交时结束该请求 | 可能；连接级错误未必属于某条请求 |

当前连接上新建并开始执行的请求，以对应 `request_id` 的 `chat_final` 为正常终态。重复提交相同 `request_id` 和内容时，服务端返回 `chat_ack(created=false)`，不会因此重新执行或补发旧 `chat_final`；原执行若仍在同一连接上，仍可能发出自己的终态。重连后收到 `created=false`，前端应查询 `/requests/{request_id}`、`/messages` 和必要的 `/events`，按账本状态结束或继续等待本地展示，不要只等终态帧。`agent_progress` 的自然语言 `message`、工具状态或 `payload.status` 不代表请求已完成，也不代表工程任务已经完成。收到相同正文的过程说明和 `chat_final.response.message` 时避免重复显示正式回复。

`chat_final.response` 是 `AgentResponse`，通用字段有 `status`、`message`、`payload`、`needs_clarification`、`clarifying_question`。当前 v1 的 `payload` 是受限展示摘要，主要包含 `version`、可核验的 `task_id` 和澄清问题；符合条件的知识命令还可能带 `candidate`。不能按旧工作流入口的完整工程任务 `payload` 解析。`response.status` 是本轮状态，和 TaskState 中持久化的工程任务状态不是同一概念。

当前 v1 不在 `chat_final.response.payload` 中返回 `task_status`、`tool_results`、`completion_check`、`publish`、场景写入差异或哈希。`agent_progress` 也只转发标量白名单字段：写入工具的 `operation_id` 和状态可能出现，但差异、哈希等预览资料不会出现，绝对路径还会被过滤。历史 `display_view` 不记录该操作 ID。因此，仅凭本 v1 前端接口无法安全完成旧协议要求的场景写入预览与跨刷新恢复，也不能按旧协议的 `payload.publish.status` 判定知识发布成功。相关功能需要后端先补充经过审查的结构化输出、恢复来源与契约测试，再纳入本 v1 前端验收；前端不得从模型文案推断操作内容或发布事实。

业务阻断可能通过 `chat_final` 返回，例如 `response.status == "blocked"`；这不是 WebSocket 协议错误。当前 v1 会裁剪原始业务 `payload`，不保证返回 `payload.issues` 或业务错误码。前端可展示安全文案和本轮状态；需要按具体原因提供操作按钮时，须等待后端补充稳定的结构化字段，不能解析文案猜测。`chat_error` 表示信封校验、请求受理或未预期执行错误，应使用其 `code` 分类。

### 4.4 运行中追加输入与取消

运行中追加输入只向同一 WebSocket 发送，沿用原 `chat_start` 的 `request_id`，并使用新的 `input_id`：

```json
{
  "type": "chat_steer",
  "request_id": "正在运行的原请求 ID",
  "input_id": "本次追加输入新 ID",
  "prompt": "补充条件"
}
```

`chat_steer_ack.accepted == true` 且 `status == "queued"` 只表示追加输入已按 `input_id` 持久写入会话账本；后端会尝试投递到活动请求的输入队列。若活动通道不存在、已关闭或容量不足，当前实现不会自动补投，ACK 仍可能为 `queued`。它既不保证队列已收到，也不表示模型已经使用。后端先把带 `input_id` 的用户消息写入模型工作集，再将账本状态推进为 `consumed`，随后发布 `workflow_agent.user_input_applied`；前端核对 `payload.input_id` 或账本 `consumed` 后才能显示“已应用”。若原请求先结束，账本会把仍为 `queued` 的输入改为 `unapplied`，不会带入下一条请求。相同 `input_id` 重试时 ACK 也可能返回已有的 `consumed` 或 `unapplied` 状态。请求已经结束、ID 冲突或当前状态不允许追加时，新输入的 ACK 返回 `accepted: false`、`status: "rejected"` 和错误码。

同一个 `request_id + input_id` 搭配相同正文可以安全重试，服务端返回原追加消息，不会在前端历史中生成第二条；同一 `input_id` 搭配不同正文会返回冲突错误，前端必须生成新的 `input_id`。断线后以 `/events`、`/messages` 或请求查询核对 `consumed/unapplied`，不能只依据丢失的实时进度帧。

取消帧：

```json
{"type":"chat_cancel","request_id":"正在运行的请求 ID"}
```

`chat_cancel_ack.accepted` 表示取消是否被接受；取消请求与最终终态可能交错。前端应保留请求状态，结合对应 `chat_final` 或后续账本查询确认结果，不能只在点击取消时直接记为已取消。

## 5. 前端推荐时序

```text
登录并取得 Java 凭证
  → GET 会话列表
  → 选择 active 会话；若无会话则 POST 新建
  → GET 历史（必要时按游标翻页）
  → GET 记忆候选 + GET 已保存记忆
  → POST 领取一次性 WS ticket
  → WSS 握手 /ws/v1/sessions/{session_id}
  → chat_start（每轮固定 uav_cax_scene）
  → chat_ack / agent_progress / chat_final 或 chat_error
  → 刷新历史、请求状态或记忆列表（按需要）
```

建议实现细节：

1. 认证用户变化时，立即断开旧 WebSocket、清空旧用户会话/记忆视图，再读取新用户列表；不能只修改页面上的 `user_id` 字符串。
2. 新建会话由服务端生成 ID。会话切换时关闭旧连接、获取新会话票据、恢复新会话历史，再开启交互；迟到的旧 socket 帧必须按连接代次丢弃。
3. 进行中的请求期间禁止切换、删除当前会话，避免页面把旧请求结果显示到新会话；服务端仍会独立校验 `session_busy`。
4. 每次 WebSocket 重新连接都重新向 Java 领票。断线后先查询账本和历史，识别请求是否已终结；天枢不会自动重播旧实时进度帧或旧终态。相同请求重试得到 `chat_ack(created=false)` 时，以账本查询结果恢复界面，不等待本次重试再发 `chat_final`。
5. 以 `session_id + request_id` 关联请求、消息和实时事件；`task_id` 是后端工程任务 ID，不是聊天轮次或会话 ID。
6. `agent_progress` 是实时过程。需要跨断线恢复时查询 `/events`、`/requests/{request_id}` 和 `/messages`，以账本为准。
7. 会话进入 `deleting` 后不再请求票据或发送聊天；显示删除中状态并允许重试。删除成功只在收到 `204` 后从列表移除。
8. 前端恢复的是 session 级可见历史；模型工作集由天枢后端按当前请求的 `scene_id` 恢复。场景任务使用同一用户、会话和场景的任务工作区检查点；无场景普通问答使用同一用户、会话且 `scene_id == null` 的独立工作集。前端不读取、拼接或重建这些工作集。
9. 同一 session 切换场景时，历史仍可完整查看，但后端不得把其他场景的模型工作集混入本轮；基础版前端仍固定发送 `uav_cax_scene`，通用运行时支持其他已授权场景属于后端能力，不改变本节前端约束。
10. 当前登录身份的 SSH 账号若与旧会话创建时的绑定不同，旧会话历史仍按平台归属可见，也可删除；使用该新登录令牌为旧会话领票会返回 `409 session_ssh_binding_changed`。前端应在当前登录态下创建新会话，不向本 v1 链路的聊天帧或公共会话请求提交 SSH 身份。Fake Java 的旧令牌未自动撤销时仍可能为原会话领票；正式 Java 应在会话创建时保存原绑定，并明确旧登录撤销策略。

## 6. 上下文和 TaskState 对前端的含义

前端不直接读取或提交完整 Context。每条 `chat_start` 提供当前页面的 `ui_context`；天枢在请求处理时使用票据身份、当前场景或无场景作用域的模型工作集、同一用户/会话/场景的 TaskState 投影和符合条件的已确认长期记忆，经过相关性选择与预算裁剪后构造模型上下文。可见历史与模型工作集是两个不同的后端对象：前者由 Java 账本按 session 提供，后者由天枢按场景或无场景作用域恢复。

因此：

- 前端不把整段历史拼进 `prompt`，不自行维护另一份“模型上下文”，也不把候选记忆写入请求。
- TaskState、模型工作集、最近及相关历史和记忆召回没有独立的前端读取/写入接口；它们是后端请求时的上下文装配行为。
- 场景任务的模型上下文来自同一 `user_id + session_id + scene_id` 的任务工作区检查点；无场景普通问答来自 `user_id + session_id + scene_id=null` 的独立模型工作集。场景切换不会复用其他场景工作集。
- 新任务在首个模型调用前保存初始工作集；运行中的追加输入只有在带 `source_input_id` 的消息成功写入工作集后才标记为 `consumed`，请求结束前未消费的输入会是 `unapplied`。
- TaskState 按用户、会话、场景读取；场景级事实不会因前端只切换任务标题而跨场景复用。
- 用户长期记忆按用户、scope、场景有效性、过期时间和关键词相关性有限召回；前端不能宣称每轮必然召回或模型必然逐字使用某条记忆。
- 只有 `active` 的已确认记忆可进入召回候选；`pending` 候选绝不进入模型上下文。
- 会话历史 API 用于界面恢复；模型上下文使用的是后端按作用域恢复、筛选和裁剪后的工作集/消息投影，两者不等价。

## 7. HTTP 与 WebSocket 错误处理

Fake Java REST 错误通常采用 JSON `{ "detail": "稳定错误码" }`；参数 Schema 校验失败可能是 FastAPI `422` 结构。开发网关自行拒绝请求时（例如 Origin 或开发密钥错误、上游不可用）可能只返回 HTTP 状态码而没有 JSON body。前端应始终记录 HTTP 状态码，并在 `detail` 存在时再读取它；不要假定每个错误都有错误码 body，也不要将后端内部异常栈或原始服务凭据暴露给用户。

| 传输方式 | 状态/错误码 | 含义 | 建议处理 |
| --- | --- | --- | --- |
| HTTP | `401 login_required` / `login_expired` | 未登录、登录令牌失效或会话已撤销 | 清理登录态，重新走 Java 登录，再重试受保护请求 |
| HTTP | `403 origin_forbidden` / `loopback_required` | 当前来源或网络边界不允许；开发网关也可能只返回无 body 的 `403` | 停止重试，检查开发代理和 Origin 配置 |
| HTTP | `404 session_not_found` | 会话不存在或不属于当前用户；对跨用户访问不泄露所有权 | 刷新当前用户列表，不尝试更换用户或猜测会话 ID |
| HTTP | `404 memory_not_found` / `candidate_not_found` | 记忆或候选不存在/不属于当前用户 | 刷新列表并更新界面 |
| HTTP 删除会话 | `409 session_busy` | 当前会话仍有运行请求，删除未开始 | 等待当前请求终态后重试 |
| HTTP | `409 session_not_active` | 会话正在删除或已不可写 | 查询删除状态并停止该会话聊天 |
| HTTP 领取票据 | `409 session_ssh_binding_changed` | 当前登录 SSH 账号与会话创建时的场景目录身份不同 | 保留旧历史供查看和删除；新建会话后再继续聊天，不重试旧会话领票 |
| HTTP | `409 memory_source_not_completed` | 候选来源轮次尚未完成 | 等待来源请求 `chat_final` 后刷新候选再确认 |
| HTTP 删除会话 | `202` | 会话已冻结，但清理未完成 | 查询删除状态并允许重试；不要标记删除成功 |
| HTTP | `503 memory_unavailable` | Fake Java 到天枢记忆内部端口不可用；开发网关上游不可达时也可能返回无 body 的 `503` | 保留用户输入，提示服务暂不可用并重试查询 |
| WebSocket `chat_error` | `code: session_busy` | 当前会话已有未终结请求，新的 `chat_start` 未受理 | 等待当前请求终态后重试 |
| WebSocket `chat_error` | `code: request_id_conflict` | 相同请求 ID 被用于不同请求内容；此错误不通过 HTTP `409` 返回 | 为新的提交生成新 ID；不要自动复用冲突 ID |
| WebSocket 握手 | close code `4403` / `1013` | 握手被拒或服务暂不可用；经开发网关时上游握手拒绝或超时也可能映射为 `4403` | 按握手失败处理，检查 Origin、票据、子协议和网关服务状态；服务恢复后重新领票 |

WebSocket 握手失败时不会收到 `chat_error` JSON；检查 close code、Origin、票据有效性及代理 Upgrade。握手成功后，`chat_error` 的 `code` 是程序化错误分类；`message` 是安全展示文案。未知错误码按可恢复的通用失败展示，不依赖异常消息文本判断业务状态。

## 8. 安全和实现限制

- 产品前端只访问 Java 公共 REST 接口和配置给浏览器的天枢 WebSocket；不访问 Fake Java `/internal/...`、天枢 `/internal/...`、天枢 `/local/debug/...` 或 SQLite/运行目录。
- Fake Java 的 `token` 是测试令牌；正式 Java 应由平台登录凭证得出可信主体，并在每个公共接口按当前主体验证会话归属。
- 浏览器持有的 Java 凭证和一次性票据不得写入 URL、调试日志、埋点或错误上报。票据只通过 WebSocket 子协议发送。
- 不信任前端传来的 `user_id`、`owner_user_id`、服务器路径、任务状态、场景权限结论或“已完成”标记。当前 `chat_start` 的身份字段来自票据，页面快照只表示当前 UI 可见信息。
- 生产环境不允许启用任意用户 ID 的 `/api/ai/debug-login`。Fake Java 仅用于隔离开发环境并使用虚构测试数据。
- Fake Java 目前回环限制、内存态测试登录和本地账本实现，均不构成生产可用性或生产安全验证。

## 9. 联调验收清单

### 9.1 基本接入

- [ ] 前端登录凭证由 Java 核验；页面不通过用户输入框决定真实身份。
- [ ] 会话列表只显示当前用户会话；新建会话 ID 由服务端产生。
- [ ] REST 的票据、历史和记忆操作都使用当前 Java 身份凭证。
- [ ] 每次 WS 建连先领新票；使用 `tian-shu.v1` 和 `ticket.<ticket>` 子协议连接目标会话。
- [ ] `chat_start` 不含用户身份或会话身份字段，且每次新提交使用新的 `request_id`。
- [ ] 每条自然语言请求都发送 `ui_context.scene_id == "uav_cax_scene"`；没有该场景上下文时前端阻止提交，不走空场景 fallback。
- [ ] 用户输入、ACK、进度、终态按 `session_id + request_id` 正确归属；当前连接的新请求以 `chat_final` 作为正常轮次结束依据，断线或 `created=false` 的重复请求按账本恢复。
- [ ] v1 `agent_command` 和 `chat_steer` 不携带 `user_id`；`chat_steer` 自带新 `input_id`，不复用旧工作流入口的顶层帧示例。

### 9.2 会话恢复与权限

- [ ] 刷新页面后读取会话列表并恢复历史；消息按 `message_id` 和 `revision` 更新，不重复堆叠。
- [ ] 两个用户不能读取彼此的会话、历史或记忆；尝试跨用户访问时 Fake Java 返回 `404`。
- [ ] 缺少登录凭证返回 `401`；错误 Origin 被拒绝；WS 票据重放、过期或绑定错会话时握手失败。
- [ ] 活跃请求期间切换或删除当前会话被前端阻止；后端 `session_busy` 也有正确提示。
- [ ] 删除 `204` 才移除会话；删除 `202` 显示 `deleting`，可刷新状态并重试。删除完成后，该会话来源的候选和记忆证据会被清理；没有其他会话证据的记忆会从活动记忆列表消失。
- [ ] 同一平台用户以 SSH 身份已改变的新登录令牌仍可读取、删除旧会话；该令牌为旧会话领票返回 `409 session_ssh_binding_changed`，新会话能按新身份领票。Fake Java 旧令牌未撤销时的行为与正式 Java 撤销策略分开验收。

### 9.3 长期记忆和上下文

- [ ] 成功请求“请记住：联调测试标记为 CTX41”后，刷新可看到 `pending` 候选；尚未确认时已保存列表不包含 CTX41。
- [ ] 在来源轮次完成后确认候选，已保存列表出现对应记忆；在新会话中能看到同一用户的记忆记录。
- [ ] 在新会话请求回忆时，前端只发送本轮 prompt 和 UI 快照；历史、TaskState、有效记忆由后端装配，不在前端拼接。
- [ ] 同一 session 切换场景时仍可查看完整 session 历史，但模型请求只使用当前场景工作集；不会混入其他场景的检查点。
- [ ] 运行中追加输入的 `queued`、`consumed`、`unapplied` 状态与 `/events`、`/messages` 查询一致；前端只在收到应用事件或账本确认后显示已应用。
- [ ] 同一 `request_id + input_id` 搭配相同正文重试不会生成重复历史消息；同一 ID 搭配不同正文会被拒绝。
- [ ] 不同 session 的无场景模型工作集互相隔离；删除 session 后对应无场景工作集不会残留。
- [ ] 拒绝候选后不出现在 active 记忆列表；删除记忆后刷新消失。
- [ ] 长期记忆区域和场景知识候选区域使用不同数据、状态和操作。

### 9.4 当前 v1 工作流输出边界

- [ ] 不按旧工作流协议期待 v1 `chat_final.response.payload` 中有 `tool_results`、`task_status`、`completion_check` 或 `publish`。
- [ ] 场景写入确认卡所需的差异预览、哈希及刷新恢复来源未补齐前，不将其作为本 v1 票据入口的前端验收项，也不凭进度中的 `operation_id` 直接开放批准按钮。
- [ ] 知识发布结论未获得经核验的结构化返回前，不凭 `response.status`、进度文案或候选摘要宣称发布成功。

## 10. 尚未完成的正式生产工作

Fake Java 人工链路通过，说明简易前端到 Fake Java 再到天枢的回环联调契约已验证；它不等于正式 Java 生产接口已部署。进入真实产品环境前仍需完成：

1. **正式 Java 适配**：接入平台凭证核验、真实用户身份映射、会话归属、票据签发/撤销、公共 REST 代理，以及天枢内部账本/记忆/删除调用。当前 `mock_java` 是本地 Fake 实现。
   会话创建时需持久记录经核验的 SSH 场景目录身份；改绑后历史仍按平台用户归属读取，旧会话不再签发新 SSH 身份的执行票据，删除调用携带会话原绑定而非当前登录映射。旧登录票据的撤销策略也需由正式 Java 明确。
2. **正式天枢适配器**：当前启动代码只允许 `local` 或 `mock_java` 会话账本模式；生产会话模式因缺少正式 Java 票据/账本适配器而拒绝启动。需要实现并注入生产适配器后，再做真实前端到 Java 到天枢联调。
   `ConversationLedger.get_input()` 是 AI 与 Java 账本之间用于追加输入对账的内部契约，不是前端 API；正式 Java 账本适配器必须提供同等查询语义，支持按 `request_id + input_id` 核对正文摘要、状态和归属。
   当前没有向前端公开模型工作集的读取接口，前端仍只使用 session 历史、事件和请求状态接口。
3. **网络部署**：确定 Java API、天枢 WSS 的浏览器可访问域名、HTTPS/WSS、反向代理路由、WebSocket Upgrade、Origin/CORS 和超时配置。不能复用 Fake Java 的回环服务作为外网服务。
4. **场景服务端强约束**：若基础版要求任何调用都不得使用其他场景或无场景模式，天枢需在正式入口校验 `uav_cax_scene` 并覆盖拒绝测试。现有调试页固定发送该场景，但服务端通用能力尚未全局锁定该值。
5. **生产数据与生命周期**：由 Java/平台团队确定正式登录会话、消息和记忆的数据保留、用户注销、账号删除、备份恢复和审计策略；Fake Java 的本地 SQLite 生命周期不代表生产方案。
6. **v1 工作流结果契约**：若正式前端需在票据会话入口完成场景写入审批、知识发布结论和任务详情展示，天枢需提供经过校验的预览及发布结果、可恢复的操作查询来源，并覆盖字段脱敏与恢复测试；当前 v1 白名单输出尚不支持按旧工作流协议直接验收这些交互。

因此，前端现在可以依本文开始实现，并通过上述开发网关对 Fake Java 公共契约进行浏览器联调；启动器已支持显式的产品前端 Origin，但不能接受产品平台 token。真实生产端到端验收必须等上述正式 Java、天枢适配器和网络部署完成后执行。
