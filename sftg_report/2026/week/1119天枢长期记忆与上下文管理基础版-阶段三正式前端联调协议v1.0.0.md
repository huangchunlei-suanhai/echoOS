## 1. 文档目的与适用范围

<span style="color:red">本文供正式产品前端研发人员接入天枢“会话账本、上下文管理、TaskState 投影和用户长期记忆”基础版。本文描述平台登录、入口网关、天枢公共 REST/WebSocket 的调用时序、消息字段、错误处理和三方验收边界。</span>

本文不替代[工作流研发前端正式联调协议 v3.1.0](工作流研发前端正式联调协议v3.1.0.md)。旧协议可用于理解工作流命令的业务字段、页面快照和操作顺序；已接入旧 WebSocket 入口的页面仍按其入口契约联调。但接入本文 `/ws/v1/sessions/{session_id}` 票据入口时，连接地址、顶层消息信封、身份字段和实际返回字段均以本文及当前 v1 代码为准，不能直接复用旧协议的帧示例或完整工作流结果展示。场景文件写入预览与知识发布结论在 v1 的当前输出限制见 4.3 节，相关前端验收须等待输出契约补齐。

<span style="color:red">本文中的 `/api/ai/...` 是天枢正式公共接口路径。Java 只提供平台登录态和 `/api/user/detail` 身份查询；会话、聊天记录、长期记忆、上下文和删除由天枢实现。阶段二 Fake Java 的同名接口只用于开发验证，不能作为阶段三正式接口。</span>

### 1.1 基础版场景约束

本次基础版前端每一条自然语言聊天都必须绑定已有场景 `uav_cax_scene`：

- 每个 `chat_start.ui_context.scene_id` 必须是 `uav_cax_scene`。
- 不显示场景选择、创建或切换到新场景的流程；不发送空 `scene_id`。
- 发请求的已认证用户必须已获准访问该场景。用户没有访问权限时，应显示错误，不应通过改用其他用户、其他场景或无场景模式重试。
- `uav_cax_scene` 是场景标识，不是场景目录路径。前端不拼装服务器文件系统路径。

这部分是本次前端联调的强制验收要求。**当前天枢通用运行时代码尚未全局强制 `scene_id == "uav_cax_scene"`**：它仍支持其他已授权场景，并保留特定页面的无场景普通问答行为。因此，不能把“后端会拒绝其他场景或空场景”当作已经实现的事实。若产品要求服务端也必须强制此基础版范围，需要天枢在正式部署模式增加相应校验并另行验证；前端必须先按本节固定发送 `uav_cax_scene`。

## 2. 链路与职责

<span style="color:red">阶段三正式链路如下。最终正式前端使用入口网关地址；`8091` 是天枢服务端口，只有在网关直连或本机验收时才作为目标地址出现。</span>

```text
正式前端（平台页面 :3008）
  │
  ├─ 平台登录：POST /api/user/loginUser
  │              └─ Java 返回平台 token、用户 ID、SSH 用户名
  │
  ├─ HTTPS REST → 入口网关 → 天枢 :8091 /api/ai/...
  │                         └─ 天枢携带 token 调 Java /api/user/detail
  │                            取得可信 content.id / content.sshUsername
  │                            并负责会话、聊天、记忆、上下文和删除
  │
  └─ WSS → 入口网关 → 天枢 :8091 /ws/v1/sessions/{session_id}
                       └─ 天枢签发并消费一次性 WS ticket
```

<span style="color:red">Java 的现有身份接口是 `http://172.20.163.11:1661/api/user/detail`。请求头使用 `token`；成功响应实际业务码为 `0000`，身份字段为 `content.id` 和 `content.sshUsername`。前端不调用该详情接口来决定归属，前端只把平台登录 token 交给天枢入口；天枢服务端向 Java 查询并校验身份。</span>

<span style="color:red">入口网关必须将 `/api/ai/...` 和 `/ws/v1/...` 转发到天枢，REST 保留 `token` 请求头，WebSocket 保留 `Origin`、HTTP Upgrade 和 `Sec-WebSocket-Protocol`。Java 不需要实现会话、聊天记录、长期记忆或会话删除接口。</span>

<span style="color:red">WebSocket 业务帧不携带 `user_id`、`sshUserName` 或 Java token。用户身份由天枢收到的 `token` 查询结果绑定；WS ticket 只放在 `Sec-WebSocket-Protocol`，不放 URL、聊天 JSON 或日志。</span>

### 3.2 历史分页

首次读取可使用 `GET .../messages?limit=100`。当前实现允许 `limit=1..100`，默认 `50`。响应按消息创建序号从旧到新排列：

```json
{
  "items": [
    {
      "message_id": "msg_...",
      "request_id": "request-1",
      "input_id": null,
      "role": "user",
      "content": "用户输入",
      "status": "final",
      "revision": 1,
      "created_sequence": 1,
      "updated_sequence": 1,
      "created_at": "2026-11-11T02:00:00+00:00",
      "updated_at": "2026-11-11T02:00:00+00:00",
      "display_view": {"version": 1}
    }
  ],
  "creation_watermark": 12,
  "next_before_sequence": null,
  "has_more": false
}
```

需要更早历史时，沿用首屏返回的 `creation_watermark`，并使用 `next_before_sequence` 请求：

```text
GET .../messages?before_sequence=<next_before_sequence>&creation_watermark=<creation_watermark>&limit=100
```

`role` 为 `user` 或 `assistant`。`status` 反映消息状态，可能包括 `pending`、`partial`、`final`、`failed`、`cancelled`、`interrupted`、`queued`、`consumed`、`unapplied`。更新中的同一消息可有更高 `revision`；前端用 `message_id` 识别消息、按更高版本更新，不能把每个 revision 都追加成新消息。`display_view` 是受限的历史展示摘要；当前 v1 执行链路仅填充已核验的 `task_id` 和澄清问题，不填充 `operation_id`。虽然 Schema 定义了 `operation_id` 字段，前端不能据此假设刷新历史后能恢复场景写入确认卡，也不能把展示摘要当作动作授权或完整任务事实。

追加输入也会作为带 `input_id` 的用户消息出现在本页：`queued` 表示已写入账本但尚未确认进入模型，`consumed` 表示已写入模型工作集并完成账本消费，`unapplied` 表示请求在它被模型消费前已经结束。`unapplied` 输入不会自动带入下一条请求。助手的模型工作集检查点、工具观察和内部恢复信息不通过本接口展示。

### 3.3 事件补拉

`GET .../events?after_sequence=<cursor>&limit=100` 查询 `sequence > after_sequence` 的事件；当前 `limit=1..200`，默认 `100`。响应结构：

```json
{
  "items": [{
    "event_id": "evt_...",
    "sequence": 3,
    "request_id": "request-1",
    "input_id": null,
    "event_type": "request_status",
    "message_view": null,
    "status": "completed",
    "created_at": "2026-11-11T02:00:02+00:00"
  }],
  "next_sequence": 3,
  "high_water_cursor": 3,
  "has_more": false
}
```

事件类型包括 `message_created`、`message_updated`、`request_status`、`input_status`。WebSocket 断线后，前端可用历史和事件接口核对持久状态；运行中的实时 `agent_progress` 不等同于持久账本事件，也不会因重连自动重播。

### 3.4 请求状态

`GET .../requests/{request_id}` 返回当前请求账本记录，字段包括：

```json
{
  "request_id": "request-1",
  "kind": "chat",
  "payload_digest": "...",
  "status": "completed",
  "user_message_id": "msg_...",
  "assistant_message_id": "msg_...",
  "created_sequence": 1,
  "task_id": null,
  "side_effect_status": "none",
  "error_code": null,
  "created_at": "2026-11-11T02:00:00+00:00",
  "updated_at": "2026-11-11T02:00:02+00:00"
}
```

`status` 可能为 `accepted`、`running`、`completed`、`failed`、`cancelled`、`interrupted`。该记录用于断线恢复或核对；当前连接的新请求仍以终态帧结束，断线重连或重复提交时则应以该记录及历史、事件确认持久状态，不能等待服务端补发旧终态帧。

### 3.5 用户长期记忆 API

| 方法与路径 | 用途 | 成功响应 |
| --- | --- | --- |
| `GET /api/ai/sessions/{session_id}/memory-candidates` | 读取当前用户的记忆候选 | `{"items":[MemoryCandidate,...]}` |
| `POST /api/ai/sessions/{session_id}/memory-candidates/{candidate_id}/confirm` | 确认候选 | `MemoryRecord` |
| `POST /api/ai/sessions/{session_id}/memory-candidates/{candidate_id}/reject` | 拒绝候选 | 更新后的 `MemoryCandidate` |
| `GET /api/ai/sessions/{session_id}/memories` | 读取当前用户状态为 `active` 的已保存记忆 | `{"items":[MemoryRecord,...]}` |
| `DELETE /api/ai/sessions/{session_id}/memories/{memory_id}` | 删除一条已保存记忆 | `204` |

候选的主要字段：`candidate_id`、`owner_user_id`、`kind`、`scope`、`scene_id`、`subject_key`、`claim`、`applicability`、`evidence_ref`、`evidence_session_id`、`evidence_request_id`、`status`、`created_at`。`kind` 当前取 `user_preference`、`scene_fact`、`decision`、`engineering_lesson`；`scope` 当前取 `user` 或 `user_scene`。候选列表接口最多返回当前用户最近 200 条候选，可能包含 `pending`、`confirmed`、`rejected`；前端待确认区域只展示 `status == "pending"`。

已保存记忆的主要字段：`memory_id`、`revision`、`owner_user_id`、`kind`、`scope`、`scene_id`、`subject_key`、`claim`、`applicability`、`evidence_refs`、`evidence_session_ids`、`status`、`created_at`、`updated_at`、`expires_at`。列表只按 `active` 状态筛选，最多 200 条；它不是本轮模型实际召回的记忆列表，召回还会检查场景、过期时间和相关性。`scope == "user_scene"` 时 `scene_id` 必须有值；`scope == "user"` 时 `scene_id` 为空。

记忆归属是用户级，不是当前会话级：同一用户在新会话中仍能看到其用户级记忆。记忆候选必须由用户显式确认后才成为已保存记忆并有机会进入模型上下文；候选本身不会进入模型上下文。确认时后端检查候选来源请求已完成；来源回合尚未完成通常返回 `409 memory_source_not_completed`。确认和拒绝后刷新候选、记忆列表以显示服务端状态。

当前候选生成范围有限：基础实现只对以准确前缀 `请记住：` 开头、且没有被敏感信息规则拦截的成功自然语言请求生成候选。它不是自动从所有对话提炼记忆的承诺；没有候选时前端应显示空态，不应自行生成或伪造候选。这里的长期记忆候选与工作流协议中的“场景知识候选”完全不同，不得混用接口、状态或按钮。

删除会话也会清理该会话来源的记忆候选和记忆证据。若一条已保存记忆没有其他会话的证据，删除来源会话后该记忆将不再出现在 `active` 记忆列表；若仍有其他会话证据，记忆保留并移除已删除会话的证据引用。会话清理未完成时，删除接口保持 `202`，完成后再按上述规则清理记忆数据。

## 4. WebSocket 连接与消息协议

### 4.1 握手

<span style="color:red">每次新建或重连按以下阶段三步骤执行：</span>

<span style="color:red">1. 前端使用当前平台 token 调用入口网关的 `POST /api/ai/sessions/{session_id}/ws-ticket`；天枢服务端用该 token 调 Java `/api/user/detail`，确认用户和 SSH 身份后签发一次性 ticket。</span>

<span style="color:red">2. 在 ticket 签发后尽快连接入口网关的 WSS 地址：</span>

```text
<tianShuWsBase>/ws/v1/sessions/{session_id}
```

<span style="color:red">3. WebSocket 子协议必须包含：</span>

```text
Sec-WebSocket-Protocol: tian-shu.v1, ticket.<ticket>
```

```javascript
new WebSocket(wsUrl, ["tian-shu.v1", `ticket.${ticket}`]);
```

<span style="color:red">ticket 由天枢签发并一次性消费，默认有效期为 120 秒，部署配置允许的最大值为 300 秒。它不是 Java 平台登录 token。每次重连都重新调用 ws-ticket；不能重放旧 ticket。</span>

<span style="color:red">入口网关必须保留浏览器 `Origin`、HTTP Upgrade 和 `Sec-WebSocket-Protocol`。票据缺失、过期、重放、会话不匹配、Java token 无效或 Origin 不允许时，天枢拒绝握手，常见 close code 为 `4403`；网关不可达可能表现为 `502/503/1013`。</span>

### 4.2 自然语言请求 `chat_start`

```json
{
  "type": "chat_start",
  "request_id": "由前端为本次提交新生成的唯一 ID",
  "prompt": "用户当前输入",
  "access_mode": "restricted",
  "ui_context": {
    "page": "workflow_canvas_page",
    "scene_id": "uav_cax_scene",
    "visible": {
      "page_state": {"button": [], "title": [], "text": []},
      "canvas_detail": {
        "workflow_id": "当前工作流 ID；无则为空字符串或 null",
        "nodes": [],
        "connections": []
      }
    },
    "target": null
  }
}
```

字段要求：

- `type` 固定为 `chat_start`。
- `request_id` 每次新提交生成唯一值，长度 1–100；同一会话不能并发提交新的工作请求。前端生成的 ID 使用 `[A-Za-z0-9_-]{1,100}`；当前入口网关和天枢请求状态路径均建议使用此范围，超出范围的 ID 可能无法通过请求状态 REST 路径恢复。
- `prompt` 去除首尾空白后非空，最长 20,000 字符。
- `access_mode` 可选，值为 `restricted` 或 `full`，省略时为 `restricted`。它影响新任务权限；已有任务不会因前端下一轮改值而重置权限。
- `ui_context` 是当前页面实际可见状态，不是身份或授权凭证。基础版固定 `scene_id: "uav_cax_scene"`；`page` 必须如实反映当前页面，`visible.page_state` 必须存在，并且只上报该页面允许且实际可见的数据组，不把其他页面的数据组混入。上面的 `workflow_canvas_page` 示例对应当前简易前端；正式前端接入其他已支持页面时，应按真实页面和《工作流研发前端正式联调协议 v3.1.0》的 `ui_context` 页面契约构造。
- 不发送 `user_id`、`session_id`、Java token、WebSocket ticket 或自定义身份字段。`session_id` 已在 WebSocket URL 中，用户身份来自票据。
- 顶层未知字段会被拒绝。画布节点、工作流状态或目标对象 ID 只能来自前端真实页面快照，不能从模型回答反向构造。

**基础版发送前校验：** 若当前用户没有已选定的 `uav_cax_scene` 工作上下文，或当前页面无法提供符合 Schema 的 `ui_context`，前端应阻止提交并提示用户回到有权限的该场景页面；不得删除 `scene_id` 后降级成普通聊天。

需要发送工作流结构化命令时，v1 顶层只允许 `type`、`request_id` 和 `command`，例如：

```json
{
  "type": "agent_command",
  "request_id": "本次命令新生成的请求 ID",
  "command": {
    "command": "summarize_knowledge",
    "task_id": "当前真实任务的 ID"
  }
}
```

命令名称及 `command` 内的必需字段仍按工作流协议和后端命令 Schema 校验；上述中文 ID 只是占位说明。v1 顶层不能携带旧协议示例中的 `user_id`，也不能携带 `prompt`、`ui_context` 或 `session_id`。运行中追加输入使用 4.4 节的 `chat_steer`，必须由前端提供新的 `input_id`，同样不能携带 `user_id`。旧协议中的 `/ws/sessions/{session_id}` 路径及其身份字段规则不适用于本 v1 入口。

### 4.3 服务端事件与请求结束规则

| 帧 | 主要字段 | 前端行为 | 是否表示本轮结束 |
| --- | --- | --- | --- |
| `pong` | `session_id` | 连接保活反馈 | 否 |
| `chat_ack` | `request_id`、`session_id`、`status`、`created`、消息 ID | `created=true` 表示新建；`created=false` 表示同 ID 同内容的已有请求，应查账本状态 | 否 |
| `agent_progress` | `request_id`、`stage`、`message`、`payload`、`created_at`、`transient` | 展示进度并按请求 ID 归属；只展示实际收到的字段 | 否 |
| `chat_steer_ack` | `request_id`、`input_id`、`accepted`、`status`、可选 `code` | 展示追加输入是否入队 | 否 |
| `chat_cancel_ack` | `request_id`、`accepted` | 展示取消请求是否被接受 | 否 |
| `chat_final` | `request_id`、`response`，取消时可能有 `cancelled` | 展示正式终态，结束该请求 loading | 是；按对应请求 ID 处理 |
| `chat_error` | 可选 `request_id`、`code`、`message` | 展示错误；只在能唯一关联本次提交时结束该请求 | 可能；连接级错误未必属于某条请求 |

当前连接上新建并开始执行的请求，以对应 `request_id` 的 `chat_final` 为正常终态。重复提交相同 `request_id` 和内容时，服务端返回 `chat_ack(created=false)`，不会因此重新执行或补发旧 `chat_final`；原执行若仍在同一连接上，仍可能发出自己的终态。重连后收到 `created=false`，前端应查询 `/requests/{request_id}`、`/messages` 和必要的 `/events`，按账本状态结束或继续等待本地展示，不要只等终态帧。`agent_progress` 的自然语言 `message`、工具状态或 `payload.status` 不代表请求已完成，也不代表工程任务已经完成。收到相同正文的过程说明和 `chat_final.response.message` 时避免重复显示正式回复。

`chat_final.response` 是 `AgentResponse`，通用字段有 `status`、`message`、`payload`、`needs_clarification`、`clarifying_question`。当前 v1 的 `payload` 是受限展示摘要，主要包含 `version`、可核验的 `task_id` 和澄清问题；符合条件的知识命令还可能带 `candidate`。不能按旧工作流入口的完整工程任务 `payload` 解析。`response.status` 是本轮状态，和 TaskState 中持久化的工程任务状态不是同一概念。

当前 v1 不在 `chat_final.response.payload` 中返回 `task_status`、`tool_results`、`completion_check`、`publish`、场景写入差异或哈希。`agent_progress` 也只转发标量白名单字段：写入工具的 `operation_id` 和状态可能出现，但差异、哈希等预览资料不会出现，绝对路径还会被过滤。历史 `display_view` 不记录该操作 ID。因此，仅凭本 v1 前端接口无法安全完成旧协议要求的场景写入预览与跨刷新恢复，也不能按旧协议的 `payload.publish.status` 判定知识发布成功。相关功能需要后端先补充经过审查的结构化输出、恢复来源与契约测试，再纳入本 v1 前端验收；前端不得从模型文案推断操作内容或发布事实。

业务阻断可能通过 `chat_final` 返回，例如 `response.status == "blocked"`；这不是 WebSocket 协议错误。当前 v1 会裁剪原始业务 `payload`，不保证返回 `payload.issues` 或业务错误码。前端可展示安全文案和本轮状态；需要按具体原因提供操作按钮时，须等待后端补充稳定的结构化字段，不能解析文案猜测。`chat_error` 表示信封校验、请求受理或未预期执行错误，应使用其 `code` 分类。

### 4.4 运行中追加输入与取消

运行中追加输入只向同一 WebSocket 发送，沿用原 `chat_start` 的 `request_id`，并使用新的 `input_id`：

```json
{
  "type": "chat_steer",
  "request_id": "正在运行的原请求 ID",
  "input_id": "本次追加输入新 ID",
  "prompt": "补充条件"
}
```

`chat_steer_ack.accepted == true` 且 `status == "queued"` 只表示追加输入已按 `input_id` 持久写入会话账本；后端会尝试投递到活动请求的输入队列。若活动通道不存在、已关闭或容量不足，当前实现不会自动补投，ACK 仍可能为 `queued`。它既不保证队列已收到，也不表示模型已经使用。后端先把带 `input_id` 的用户消息写入模型工作集，再将账本状态推进为 `consumed`，随后发布 `workflow_agent.user_input_applied`；前端核对 `payload.input_id` 或账本 `consumed` 后才能显示“已应用”。若原请求先结束，账本会把仍为 `queued` 的输入改为 `unapplied`，不会带入下一条请求。相同 `input_id` 重试时 ACK 也可能返回已有的 `consumed` 或 `unapplied` 状态。请求已经结束、ID 冲突或当前状态不允许追加时，新输入的 ACK 返回 `accepted: false`、`status: "rejected"` 和错误码。

同一个 `request_id + input_id` 搭配相同正文可以安全重试，服务端返回原追加消息，不会在前端历史中生成第二条；同一 `input_id` 搭配不同正文会返回冲突错误，前端必须生成新的 `input_id`。断线后以 `/events`、`/messages` 或请求查询核对 `consumed/unapplied`，不能只依据丢失的实时进度帧。

取消帧：

```json
{"type":"chat_cancel","request_id":"正在运行的请求 ID"}
```

`chat_cancel_ack.accepted` 表示取消是否被接受；取消请求与最终终态可能交错。前端应保留请求状态，结合对应 `chat_final` 或后续账本查询确认结果，不能只在点击取消时直接记为已取消。

## 5. 前端推荐时序

```text
平台前端登录
  → 平台 Java 返回 token（请求头名称：token）
  → 以 token 调 aiGatewayBase GET /api/ai/sessions
  → 选择 active 会话；若无会话则 POST /api/ai/sessions
  → GET 天枢历史和记忆接口（按需）
  → POST /api/ai/sessions/{session_id}/ws-ticket
  → WSS /ws/v1/sessions/{session_id}
  → chat_start（基础版固定 scene_id=uav_cax_scene）
  → chat_ack / agent_progress / chat_final 或 chat_error
  → 断线时重新领 ticket，再查 messages/events/requests 恢复
```

<span style="color:red">前端从 8194 切换到阶段三时，主要修改的是 AI REST/WSS 服务地址和认证接入：平台登录成功后复用现有 token，所有 `/api/ai/...` REST 请求加 `token` 请求头，WS 按本协议先领天枢 ticket。前端不再调用 Fake Java 登录、不再发送用户 ID 或 SSH 用户名，也不需要实现 Java 会话、聊天记录和记忆接口。</span>

建议实现细节：

1. 认证用户变化时，立即断开旧 WebSocket、清空旧用户会话/记忆视图，再读取新用户列表；不能只修改页面上的 `user_id` 字符串。
2. 新建会话由天枢生成 ID。会话切换时关闭旧连接、重新领取天枢 ticket、恢复新会话历史，再开启交互。
3. 进行中的请求期间禁止切换、删除当前会话，避免页面把旧请求结果显示到新会话。
4. 每次 WebSocket 重新连接都重新向天枢领票；断线后先查询账本和历史，识别请求是否已终结。
5. 以 `session_id + request_id` 关联请求、消息和实时事件；`task_id` 不是会话 ID。
6. `agent_progress` 是实时过程；跨断线恢复以 `/events`、`/requests/{request_id}` 和 `/messages` 为准。
7. 会话进入 `deleting` 后不再请求票据或发送聊天；收到 `204` 后才从列表移除。
8. 前端只恢复 session 级可见历史；模型工作集、TaskState 和长期记忆由天枢按可信用户、会话和场景装配。
9. 基础版前端固定发送 `ui_context.scene_id == "uav_cax_scene"`，不把场景目录路径放进请求。

## 6. 上下文和 TaskState 对前端的含义

<span style="color:red">前端不直接读取或提交完整 Context。每条 `chat_start` 提供当前页面的 `ui_context`；天枢在请求处理时使用票据身份、当前场景或无场景作用域的模型工作集、同一用户/会话/场景的 TaskState 投影和符合条件的已确认长期记忆，经过相关性选择与预算裁剪后构造模型上下文。可见历史与模型工作集是两个不同的天枢后端对象：前者由天枢会话账本按 session 提供，后者由天枢按场景或无场景作用域恢复；Java 不提供历史账本。</span>

因此：

- 前端不把整段历史拼进 `prompt`，不自行维护另一份“模型上下文”，也不把候选记忆写入请求。
- TaskState、模型工作集、最近及相关历史和记忆召回没有独立的前端读取/写入接口；它们是后端请求时的上下文装配行为。
- 场景任务的模型上下文来自同一 `user_id + session_id + scene_id` 的任务工作区检查点；无场景普通问答来自 `user_id + session_id + scene_id=null` 的独立模型工作集。场景切换不会复用其他场景工作集。
- 新任务在首个模型调用前保存初始工作集；运行中的追加输入只有在带 `source_input_id` 的消息成功写入工作集后才标记为 `consumed`，请求结束前未消费的输入会是 `unapplied`。
- TaskState 按用户、会话、场景读取；场景级事实不会因前端只切换任务标题而跨场景复用。
- 用户长期记忆按用户、scope、场景有效性、过期时间和关键词相关性有限召回；前端不能宣称每轮必然召回或模型必然逐字使用某条记忆。
- 只有 `active` 的已确认记忆可进入召回候选；`pending` 候选绝不进入模型上下文。
- 会话历史 API 用于界面恢复；模型上下文使用的是后端按作用域恢复、筛选和裁剪后的工作集/消息投影，两者不等价。

## 7. HTTP 与 WebSocket 错误处理

<span style="color:red">阶段三错误可能来自平台 Java、入口网关或天枢。前端应记录 HTTP 状态和安全错误码，不向用户暴露 token、内部地址或异常栈。</span>

| 传输方式 | 状态/错误码 | 含义 | 建议处理 |
| --- | --- | --- | --- |
| 平台/天枢 HTTP | `401` | 平台 token 无效、过期，或 Java 用户详情校验失败 | 清理登录态，重新走平台登录；不要改写 user_id 重试 |
| HTTP | `403` | Origin、网关策略或场景权限拒绝 | 检查正式前端 Origin、网关转发和 Java 场景权限 |
| HTTP | `404 session_not_found` | 会话不存在或不属于当前用户 | 刷新当前用户会话列表，不猜测会话 ID |
| HTTP | `409 session_busy` | 当前会话仍有运行请求 | 等待当前请求终态后重试 |
| HTTP | `409 session_ssh_binding_changed` | 当前 Java 返回的 SSH 用户名与会话创建绑定不同 | 保留旧历史；按当前登录态新建会话后继续 |
| HTTP | `202` 删除 | 会话已冻结但清理未完成 | 查询 deletion 状态，不立即显示删除完成 |
| HTTP | `503 ticket_verifier_unavailable` | 天枢无法访问 Java 用户详情接口或入口上游不可用 | 检查 Java 服务、网关和天枢配置后重试 |
| WebSocket | close `4403` | ticket/Origin/会话绑定被拒绝 | 重新获取 ticket，并检查 token、Origin、Upgrade 和子协议 |
| WebSocket | close `1013` | 天枢或网关暂不可用 | 等待服务恢复后重新领 ticket |
| WebSocket | `chat_error` | 请求帧、会话状态或执行过程错误 | 按 `code` 分类处理，不解析异常文案猜测状态 |

<span style="color:red">Java `/api/user/detail` 当前实际成功业务码为 `0000`，天枢已按该值判定成功；无效或过期平台 token 由 Java 返回 401，天枢将其映射为 `401 login_expired`。当前两个测试账号的有效 token 已通过天枢会话列表读取。</span>

## 8. 安全和实现限制

- <span style="color:red">正式前端只访问平台登录接口和入口网关暴露的 `/api/ai/...`、`/ws/v1/...`；不访问 Fake Java、天枢 `/internal/...`、`/local/debug/...` 或 SQLite/运行目录。</span>
- <span style="color:red">前端不信任或提交 `user_id`、`owner_user_id`、`sshUserName` 作为身份凭证。可信值只来自天枢向 Java `/api/user/detail` 查询的结果。</span>

- <span style="color:red">会话、聊天记录、长期记忆和删除由天枢维护，数据根为 `/home/data/tianshu-agent-data`；Java 只维护平台身份和场景权限。</span>
- <span style="color:red">阶段二 Fake Java 和 8194 回环服务不得作为正式前端或生产配置；正式前端构建不得包含开发访问密钥和任意用户 ID 登录入口。</span>
