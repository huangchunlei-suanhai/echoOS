# 天枢长期记忆与上下文管理系统：建设设计草案

> 版本：2026-11-11 认知快照，供 Runtime、Context、Java、前端、知识与 Skill 负责人评审。
> 本文是目标设计及实施路线，不是上线声明或已冻结的跨仓协议。文中“已实现”仅指本次
> 核对到的工作区代码；涉及 AI 后端未提交改动，不能推断已合入或已部署。

## 1. 要建设的到底是什么

天枢面对的是持续演进的 CAX 工程任务。系统需要回答四个不同的问题：**这次会话发生过
什么、当前工程任务实际做到哪一步、哪些经验对未来仍有用、这一轮模型究竟该看到什么**。
它们的来源、寿命和可信度不同，不能合并成一张“聊天记忆”表，也不能把压缩摘要当成
工程事实。

目标是形成一个可追溯的闭环：可信记录过程，依据真实执行结果归约任务状态，从已完成
且有证据的来源提出少量长期记忆候选，经过校验和用户/领域确认后版本化保存；每轮请求
再按身份、场景、当前目标、有效性和模型预算选择内容。模型负责理解和候选表述，程序
负责身份、权限、状态、证据、写入、删除和预算门禁。**记忆是有条件的历史线索，不是
实时场景文件、验证结果或用户本轮要求的替代品。**

成功不以“存了多少条”衡量，而以断线和重启后能否正确续接、错误或过时记忆是否被挡住、
工程结论能否回到证据、用户能否纠错删除、模型输入是否可控来衡量。

| 用户长期记忆 | 精确前缀 `请记住：` 的成功请求生成 `pending` 候选；确认前重查来源账本 `completed`，确认后版本化保存；同用户/场景/有效期及词项交集筛选后有限注入 | 不是持续自动收集；没有通用更正 UI、冲突/过时判定、工程事实验证、向量检索。当前候选按断言散列形成主题键，不能据此声称支持语义更正。 |
| 输入预算 | `PromptContext` 约 4,000 token 的独立估算；工具循环可压缩旧对话；模型出站再计入系统提示和工具 Schema，用配置窗口减输出预留及余量做字符估算门禁 | 不是供应商 tokenizer 的精确硬限；复杂工具观察和压缩质量仍需真实用量回放。 |
| 产品接入 | 11 月 11 日联调协议描述了 Fake Java 公共 API、票据 WS、记忆管理及前端时序 | 当前正式前端仍生成浏览器 `web_session_*`，消息在组件状态，旧 WS 无票据；当前正式 Java 仓库未见 `/api/ai/sessions` 或记忆接口。Fake Java 三进程验证不等于三仓生产联调。 |

还有一个明确的一致性缺口：`RuntimeCoordinator` 在返回给会话服务之前提出显式记忆候选，
而账本终态由会话服务随后提交；终态提交失败时可能留下不可确认的 `pending` 候选。
当前确认接口重查来源，阻止其成为有效记忆。后续应在终态提交后提炼，或用终态扫描和
清理机制收敛。现有敏感词/格式过滤只适合基础版，不能视为完整敏感信息识别。

当前前端联调基础版要求每轮固定 `ui_context.scene_id = uav_cax_scene`；通用运行时仍支持
其他已授权场景和特定页面的无场景问答。这个前端验收范围尚不是服务端全局约束。若产品
要求基础版后端也只能接受该场景，须在正式入口增加校验并覆盖拒绝测试。

本地会话账本在创建时固定经认证映射取得的 SSH 场景目录身份。平台用户改绑 SSH 账号后，
旧会话历史仍按 `user_id + session_id` 可见；新身份无法为旧会话领票或写入，需另建会话。
旧会话删除使用账本保存的原 SSH 身份，防止清理漂移到新目录。正式 Java 应持久记录绑定、
执行同等领票核验并明确旧登录票据撤销策略；Fake Java 自填测试登录不能证明真实改绑核验。
场景目录名与 `scene_id` 不同时，场景解析及知识候选清理共用目录名或场景元数据匹配规则。
本地旧 SQLite 账本若在此字段引入前已创建带场景任务的会话，缺少可信原绑定；不能从
当前登录映射猜测并清理旧目录。该类既有测试数据需要经归属核验后显式迁移或重建，
正式 Java 上线前也需确定已有会话数据的迁移策略。

## 3. 分层、权威来源与模块职责

| 层 | 保存什么，解决什么 | 权威与生命周期 | 不承担什么 |
| --- | --- | --- | --- |
| 当前事实 | 本轮 UI 选中对象、未保存画布，后端身份/权限，当前场景资产与工具验证 | UI 现场按字段保留来源；身份、授权、持久场景版本和执行结果以后端为准 | 不从历史记忆猜测当前场景；UI 自报权限不生效。 |
| 会话账本 | 用户/助手可见消息、主请求和追加输入状态、稳定 ID/序号及安全事件 | 由可信会话服务持久化，供界面恢复和同会话历史选择 | 不保存完整 Prompt、内部思考或全部工具输出。 |
| 任务执行现场 | `task.json`、检查点、工具调用及结果、产物、验证范围 | AI 工作区及正式场景资产为工程事实源；可恢复但须重新核对权限、版本和副作用 | 不直接当用户聊天历史或长期记忆正文。 |
| 任务状态 `TaskState` | 当前目标、工程状态、已验证步骤、阻塞、待回答问题、下一动作与来源水位 | 从账本终态和工作区可信事件派生的可重建读模型，按任务修订 | 不凭模型“已完成”措辞决定工程成功；不替代原始证据。 |
| 长期记忆 | 少量跨会话有用的偏好、决策、场景事实和有条件经验及证据引用 | 经候选、核验、确认、版本/失效控制后保存；用户可见可删 | 不自动发布正式知识，不生成可执行 Skill，不代替实时工具读取。 |
| 模型工作集 | 前端不可见的模型恢复对象：当前请求、必要 UI、TaskState、工作区/会话消息、工具 Schema/观察 | 场景任务作用域为 `user_id + session_id + scene_id`，由 `TaskWorkspace` checkpoint 恢复；无场景普通问答作用域为 `user_id + session_id + scene_id=null`，由 `ConversationWorksetRepository` 持久化；每次模型调用继续按预算选择、裁剪和压缩 | 不作为前端历史接口返回，不跨 scene 复用，不把压缩摘要升格为权威事实，也不要求把全部档案装入 Prompt。 |

进程内 `SessionMemory` 仍可作为活跃请求的短期缓存；在可信账本可用时，session 历史不再
直接作为无场景模型上下文。场景任务工作区检查点用于同一场景工具循环续跑；无场景普通
问答使用独立的持久模型工作集；账本仍负责聊天展示和按 session 的完整历史恢复。两类
工作集都由后端按作用域读取，不能被前端重建或跨场景复用。场景正式 `kb/` 和 Skill 包有
独立的发布、版本与工具权限流程，记忆只可提出引用或候选，不自动提升为它们。

依赖方向维持：

```text
正式前端 -> Java 登录/会话 API -> 可信用户、会话归属、票据、账本
        \-> 天枢 WSS（一次性票据） -> Gateway -> Runtime Coordinator
                                              -> ContextPipeline -> AgentContext
                                              -> Engine -> Workflow Agent Capability
                                                          -> PromptContextBuilder -> 模型/工具

会话账本 + 工作区/场景验证 -> 任务归约器 -> TaskState
已完成且可核对的来源 -> 有界候选提炼 -> 程序校验/用户或领域确认 -> Memory Store
TaskState + 有效记忆 -> Runtime/Context 的受控读模型 -> PromptContextBuilder
```

Java 负责平台登录和产品会话归属；Runtime 负责请求、任务和删除协调；Context 负责采集、
来源标注、选择、裁剪与模型投影；Memory 负责候选/版本/失效及证据边界；Capability 只提供
结构化执行事实；Skill/知识模块保持自己的发布边界。基础设施由应用入口注入，跨模块
使用强类型契约。生产记忆存储建议随 Java 管理的用户数据进入 PostgreSQL，AI 通过受信
端口访问；这仍是待 Java/Runtime 负责人确认的部署方案，本地 SQLite 不是生产决定。

## 4. 写入链路：从过程到可复用记忆

### 4.1 先保存事实，再归约任务

1. Java 认证并创建会话；短时一次性票据绑定用户、会话和登录会话。AI 握手消费票据，
   不接受业务帧自报 `user_id`。`chat_start` 先在账本中持久受理用户消息、请求与助手
   占位，成功后才 ACK 和调用模型；同一 `request_id` 同内容重试返回原状态，异内容冲突。
2. Runtime/Capability 根据可信身份、`session_id` 和当前 `scene_id` 装配模型工作集：场景
   任务读取同场景 `TaskWorkspace` 检查点，无场景普通问答读取
   `ConversationWorksetRepository` 的 `user_id + session_id + scene_id=null` 工作集。
   前端可见 session 历史仍由账本提供，两者不共用展示接口；场景切换不能复用其他场景工作集。
3. 新场景任务在首个模型调用前保存初始消息检查点；后续模型调用、工具结果、资源用量和
   工作区事实继续写入检查点。工具执行经 `ToolPolicy`，工作区记录工具调用、结果、校验
   结论及产物引用。无场景工作集也按同一作用域原子替换保存，并在 session 删除时清理。
4. `chat_steer` 先由账本接受追加输入并写为 `queued`，再使用同一 `input_id` 投递活动请求
   队列。模型循环把追加内容以 `source_input_id` 写入当前工作集；工作集成功落盘后调用
   `consume_input`，随后发布 `workflow_agent.user_input_applied`。`queued` 不代表模型已经
   使用；请求终态前仍未消费的输入转为 `unapplied`，不会自动进入下一请求。
5. 重启或显式续跑时，检查点中的追加输入通过 `source_input_id` 调用账本 `get_input`
   对账，只恢复仍可用的账本状态；`unapplied` 输入被过滤。无跨服务原子事务，因此必须
   依靠稳定 `input_id`、正文冲突校验、幂等 upsert、重试和终态扫描收敛。
6. 请求终态 `completed/failed/cancelled/interrupted` 与工程任务
   `ready/blocked/failed_resumable/completed/unknown` 分开表达。任务归约器未来读取已落盘
   的账本终态、任务元数据、检查点、白名单工具结果和验证记录，以 `task_id` 形成带修订和
   来源水位的 `TaskState`。当前实现仍主要从 Capability 响应投影，不能声称完成全流程归约。
7. 来源事件和投影写入必须可重放：以 `source_id + source_revision + projector_version`
   去重；状态修订与已处理水位在同一事务提交。若投影失败，水位不得推进。可先定时扫描
   终态任务，不必预建常驻 Observer 或队列；积压达到实测阈值后再引入调度组件。

当前第 1 至 5 步已在本地 Runtime、Fake Java 和契约测试中形成可核对基础行为；正式 Java
适配器、完整 TaskState 归约和跨服务收敛仍是后续工作。

### 4.2 候选、核验和版本

候选触发建议从最窄可信范围扩大：先保留用户明确“请记住”的已完成回合；再支持用户
明确更正/删除；最后在工程任务终态从结构化成功与失败证据中提出少量候选。每批按同一
用户、场景和任务分组，有输入长度、事件数、候选数及模型成本上限，允许生成零条。

候选至少记录 `owner_user_id`、`kind`、`scope`、`subject_key`、短断言、适用条件、
类型化证据引用、来源修订、提炼器版本和幂等键。模型生成的断言在通过 Schema、归属、
权限、来源存在性、状态、长度及敏感字段校验之前只是建议。程序无法证明任意自然语言
断言被原文蕴含：用户偏好要展示具体措辞供本人确认；工程经验要人工确认或由专门领域
验证器确认。失败工具、助手自述成功、未应用的追加输入和一次性路径不能自动提升。

`MemoryRecord` 需要稳定 ID、修订、作用域、状态、适用版本、证据集合、更新时间及失效
条件。同一主体/属性/适用范围比较：同一断言补证据；确认的更正产生新修订并使旧版
`superseded`；证据冲突时 `conflicted` 停止注入；依赖的场景文件、求解器或协议版本变化
时 `stale`，重验前不作当前事实。现有代码只有同 `subject_key` 的版本修订；当前显式
候选以断言散列作键，故“更正”和冲突逻辑仍待设计与测试。

首期作用域只用 `user` 和已授权的 `user_scene`。没有可信项目 ID 时不创建“项目级”
假作用域；团队/系统共享记忆需要单独的授权、审核和发布流程。证据引用应逐步由现在的
`ledger:session:request` 字符串升级为带类型、对象 ID、修订/摘要和访问策略的契约，
让删除、版本变化和权限撤销可以精确定位。工程经验若要成为正式知识或 Skill，走各自
审核、验证、发布与回退流程，不能让记忆确认直接授予工具执行权。

## 5. 读取链路：按需构造本轮模型工作集

1. Runtime 确认受信用户、会话及场景权限，固定本轮 UI 快照。实时 UI 目标与未保存
   画布以前端当轮现场为准；身份、权限、工程验收及持久文件版本以后端为准。字段冲突
   按来源规则处理，不能用“后端一律覆盖”或“记忆优先”处理。
2. Java 账本按 `session_id` 保留完整可见历史，供前端分页、断线补拉和会话恢复；它是
   产品历史，不直接作为跨场景模型输入。场景任务模型上下文从同一
   `user_id + session_id + scene_id` 的 `TaskWorkspace` 检查点恢复；无场景普通问答从
   `user_id + session_id + scene_id=null` 的 `ConversationWorksetRepository` 恢复。相同
   session 的其他 scene、其他 session 的 no-scene workset 均不得混入。早期“最近 4 条
   + 相关旧轮最多 4 条”可作为历史选择/兼容基线，但不能替代上述工作集恢复主链路。
3. 当前请求的追加输入只通过活动请求 inbox 进入。工作集保存带 `source_input_id` 的消息
   后才将账本输入推进为 `consumed`；恢复时用 `source_input_id + get_input` 对账，过滤
   `unapplied` 输入。工作集检查点和账本可见消息必须去重，但不能把内部检查点、工具观察
   直接暴露为前端历史。
4. 读取当前任务的最新可信 `TaskState`；若过期或来源不可访问，回退到工作区/账本并
   给出“状态不可用”诊断。长期记忆先按 owner、场景访问、状态、适用版本、到期时间
   过滤，再按对象/词项相关性、证据等级和新鲜度排序，去重并限制条数及字符/token。
   检索失败与“没有相关记忆”要区分。初期普通索引和关键词足够建立基线；语义检索
   可在误召回/漏召回有实测证据时增加，向量相似度不能替代有效性核验。
5. `ContextPipeline` 形成结构化 `AgentContext`，`PromptContextBuilder` 作为唯一受控
   投影入口。模型只看到必要 UI、简短任务状态、工作集中的选中历史与记忆的断言/适用
   条件/来源 ID；若要做工程结论，仍须经受权限控制的工具读取当前场景或原始证据。
6. 最终模型输入门禁计算实际配置窗口减输出预留和安全余量，计入系统与能力指令、当前
   用户请求、UI、任务状态、历史、记忆、工具 Schema 和工具观察。先做确定性白名单与
   分区裁剪，再在阈值触发时压缩旧对话；工具调用与结果须成组保留。保留优先级为
   **安全/权限与本轮请求 > 当前目标及阻塞 > 已验证任务状态 > 近期会话 > 相关旧轮次
   > 有效长期记忆 > 可选列表**。固定内容仍过大时返回明确错误，不发送超预算请求。

当前出站门禁是字符估算，需按模型记录估算与供应商实际输入/输出 token、压缩前后
大小和裁剪原因，用真实 CAX 任务回放校准。压缩摘要只作为临时工作集或检查点续跑
材料，必须说明覆盖水位和未覆盖范围，不产生新的“已验证事实”。

### 一个工程任务如何穿过这些层

用户在画布上选中无人机仿真工作流，请求修改一个节点。账本记录本轮输入和最终可见
回复；工作区记录改动、节点测试与整图运行。若节点测试通过但整图失败，任务状态只能
写“节点测试通过、整图失败、下一步检查接口”，不能由助手回复把工程任务标为完成。
此时若提炼器提出“该参数配置总是正确”，候选因缺少适用范围和最终验证证据不能成为
有效记忆。后续整图通过且用户确认了带求解器版本的经验，才保存有条件的记忆。新会话
遇到相似工作流时，Context 可召回短断言和来源 ID；Agent 仍重新读取当前节点与版本并
运行必要验证。这个过程同时说明了会话记录、执行事实、任务状态、长期记忆和模型工作集
各自的责任。

## 6. 存储、权限、删除与恢复

- **产品数据真源**：建议 Java PostgreSQL 管理可信会话/消息/事件及用户记忆，AI 工作区
  独立保存执行检查点和工程产物；通过受保护内部接口和注入的 `Protocol` 连接。两边
  没有跨服务原子事务，需用终态查询、幂等、扫描和删除状态收敛。本地 SQLite 仅用于
  回环开发与测试；真实适配、迁移、备份和多实例策略待定。
- **模型工作集存储**：`.conversation_worksets` 是 AI 后端内部恢复存储，不是前端产品
  历史。文件作用域由 `user_id + session_id + scene_id` 的长度前缀哈希确定，读取和删除
  还会校验文件内身份，拒绝符号链接和归属不匹配。场景任务 checkpoint 与 no-scene
  workset 分开保存，不能通过历史接口暴露或跨 scene 复用。
- **多用户与场景**：所有读取、候选确认、修改、删除和来源回查都使用可信 owner，
  `session_id` 不能单独授权。场景记忆须再校验当前场景访问与源资产版本。前端只提交
  当前 UI 现场，不提交可采信的用户 ID、权限、TaskState 或服务器路径。
- **故障恢复**：先落来源，再处理派生；只有候选/状态及处理水位一起提交才承认完成。
  重启重放从最后提交水位继续，追加输入以 `input_id` upsert；工作集成功保存后才推进
  `consumed`，请求结束前仍为 `queued` 的输入转 `unapplied`，不会自动流入下一请求。
  账本 `get_input` 对账窗口不是跨服务原子事务，需要重试、扫描和收敛；永久错误隔离并
  给出错误码，不使其他任务无限等待。旧写者要被 writer epoch/独占锁隔离，未知工具副作用
  先核查现场，不能自动重放写操作。
- **用户控制**：提供候选查看、确认/拒绝、已保存记忆查看、更正、删除及关闭自动提炼
  的明确界面。当前本地调试页只覆盖显式候选的确认、拒绝、删除；正式产品前端尚未
  接入。前端历史按 `message_id + revision` 更新，断线用分页/游标补拉；瞬态
  `agent_progress` 不保证完整回放，不能误作持久账本事件。
- **删除**：会话先冻结新写入，工作区与场景产物按权威处置结果清理，删除该会话候选、
  TaskState 和记忆证据；失去全部有效证据的记忆失效或删除。当前本地删除可返回
  `deleting/202`，不等于清理完成；同时清理该 session 的 no-scene model workset，场景
  工作区按任务/场景清理策略处置。任何清理步骤失败都应保留 `incomplete`/错误状态，不能
  静默忽略。异步提炼须检查删除墓碑，防止旧来源复活记忆。
  账号删除、备份保留、审计墓碑和实际擦除时限由产品/数据负责人确定，未定前不宣称
  “彻底删除”。
