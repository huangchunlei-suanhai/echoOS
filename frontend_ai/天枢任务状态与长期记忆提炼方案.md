# 天枢任务状态与长期记忆提炼方案

> 方案草案，2026-11-04。面向“先向领导讲清楚摘要算法与长期记忆如何构建”的评审；不是已上线功能或跨仓接口定稿。本文依据两个 AI 后端工作区的当前代码、同目录既有调研及下列 coding agent 资料。`develop_updata` 的相关实现含未提交改动，以下“现状”只代表本次核对到的工作区，不代表已提交或部署版本。

## 1. 一句话方案与术语

**天枢先把执行过程还原成可验证的任务状态，再从已确认的过程和结果中筛出少量跨任务有用的长期记忆；每次请求只注入当前任务状态和少量相关记忆，原始证据按需读取。** 来源：任务交接摘要借鉴 [Cline]，有限索引与按需读取借鉴 [Claude Code]，活动历史压缩参考 [Codex-本地源码调研]，长期记忆分阶段整理参考 [Codex-领导源码核查摘要]；三层数据流及具体规则均为 [天枢拟议]。

| 层 | 回答的问题 | 保存内容与寿命 | 模型使用方式 | 来源 |
| --- | --- | --- | --- | --- |
| 对话历史 | “这次会话发生了什么？” | 用户输入、助手回复、工具调用及结果的原始记录/引用；按会话保留 | 选择相关原文或作临时压缩，供恢复和追溯 | [Codex-本地源码调研] 的活动历史/压缩分层；[天枢现状] 的会话账本 |
| 任务状态 | “现在要做什么，做到哪了，下一步是什么？” | 当前目标、约束、阶段、已验证进展、待回答问题、阻塞和证据水位；任务结束后归档 | 每次继续任务时注入简短状态；需要细节再读来源 | [Cline] `/newtask` 与 Memory Bank 的进度记录；字段、状态归约和持久化为 [天枢拟议] |
| 长期记忆 | “未来相关任务中，哪些稳定信息值得复用？” | 经筛选的用户偏好、项目事实、已确认决策及适用条件明确的经验；跨会话、有版本和失效规则 | 先检索再按预算投影，详细证据按需读 | [Claude Code] 自动记忆索引/主题文件；[Codex-领导源码核查摘要] 的异步提炼与合并；结构化校验为 [天枢拟议] |

此处的“长期记忆”特指第三层。旧[《首版跨仓契约草案》](天枢长期记忆与上下文管理-首版跨仓契约草案-2026-10-30.md)将“长期记忆”用于**同会话历史恢复**；那项工作在本文归入“对话历史”，不能据此宣称第三层已经完成。长期记忆也不是工程知识库、Skill 或任务检查点；知识发布和 Skill 晋升各有独立校验与权限流程。来源：[天枢现状与拟议]。

这三种 coding agent 的材料展示了可借鉴的机制，**没有一个现成算法可以直接替代天枢的证据校验**。尤其“工具成功”只表示调用完成，不自动证明 CAX 工程结果验收通过。此判断与下面的证据规则均为 [天枢拟议]。

## 4. 过程如何提炼成任务状态

### 4.1 输入与触发

以可信的 `user_id / session_id / task_id / request_id` 绑定一次任务，按序采集五类材料：用户目标及后续修正、模型计划或决策、实际工具调用及 observation、文件/场景/报告等产物引用、程序确认的阶段及终态。用户输入只证明“用户这样要求”，助手文字只证明“助手这样说过”；执行结果要由工具记录和产物验证。来源：[天枢拟议]；过程导向交接字段受 [Cline] `/newtask` 启发。

在**受理目标、阶段切换、工具形成关键结果、收到用户更正、进入阻塞/澄清、请求结束**时增量更新状态；在即将压缩模型历史或恢复任务时读取最近已落盘状态。频繁的普通对话可批量更新，避免每轮都调用模型摘要。任务状态更新不依赖长期记忆管线是否成功。来源：[天枢拟议]。

### 4.2 两段式归约

1. **程序归约事实。** 按事件序号/检查点版本读取增量，校验身份与任务归属，将目标修正、工具结果、产物和状态迁移写入结构化 `TaskState`；记录最后消费的水位，重复事件幂等。程序决定 `completed/blocked/failed/unknown` 等状态，不能从助手措辞猜成功。来源：[天枢拟议]；可靠恢复的需求与 [Cline] 交接字段有关，但具体归约算法为天枢设计。
2. **模型写可读交接。** 仅从已归约的事实和有界证据摘录生成简短过程摘要：用户要做什么、天枢做了什么、观察到什么、结果及验收范围、仍缺什么、下一步；输出结构化字段并带来源引用。程序检查 Schema、来源 ID、长度、状态一致性后才保存；不通过则保留旧状态及事实列表，标记摘要待重试。来源：[天枢拟议]；交接形式参考 [Cline] `/newtask`，有界摘要与原历史分离参考 [Codex-本地源码调研]。

建议 `TaskState` 至少包含：`goal`、`constraints`、`stage/status`、`completed_steps`、`observations`、`result_and_validation_scope`、`artifacts`、`pending_questions`、`blockers`、`next_actions`、`source_refs`、`event_watermark`、`revision/updated_at`。每个“已完成步骤”和“结果”需挂对应证据；没有验证的内容标为 `reported` 或 `pending_validation`。这是一份**拟议字段清单**，不是当前公共协议。来源：[天枢拟议]。

### 4.3 交接摘要示例

> 用户目标：为齿轮箱算例补全入口边界条件并运行网格检查。天枢已生成边界草稿（产物 `task:T1:artifact:...`），网格检查工具返回失败（观察 `task:T1:tool:7`），原因是入口速度未指定。当前未完成求解，等待用户提供入口速度及单位；随后重跑网格检查。`status=needs_clarification`，`event_watermark=42`。

这段是 [天枢拟议] 的**示意数据**，不对应真实已执行任务。关键是同时写清目标、动作、观察、结果与待办，且每条结果能回查来源。旧历史仍保留；摘要只是恢复时的读模型视图。

## 5. 从任务状态产生长期记忆

### 5.1 候选生成，不直接入库

任务达到终态、用户明确纠正偏好/项目事实、或一组任务出现重复稳定规律时，异步读取**任务状态+必要原始证据**生成候选；不要在每条消息后直接追加长期记忆。一次任务允许零条候选，且应限制数量与输入规模。任务中的临时进度、未回答问题和一次性路径继续留在任务状态。来源：分阶段整理受 [Codex-领导源码核查摘要] 启发；触发条件、候选限制与分类为 [天枢拟议]。

| 候选类型 | 可保留的例子 | 不应提升的例子 | 来源 |
| --- | --- | --- | --- |
| 用户偏好 | 用户明确说“后续报告默认用 SI 单位”，且无后续撤销 | 一次请求中临时指定“本题用毫米” | [Claude Code-官方] 记录纠正/偏好；筛选规则为 [天枢拟议] |
| 项目事实 | 项目配置或已验证文件证明的坐标系、工具版本、稳定目录规范 | 模型猜测的坐标系、尚未核对的路径 | [Cline-官方] Memory Bank 的项目背景；证据门槛为 [天枢拟议] |
| 已确认决策 | 用户确认的求解器/数据来源选择，附适用项目和原因 | 尚在讨论的候选方案 | [天枢拟议] |
| 有效经验 | 某类网格错误的成因、修复和**验证范围**，注明软件版本与适用条件 | “曾经失败一次，所以以后都这么做” | [天枢拟议]；与 Skill/知识库的发布能力不同 |

候选建议字段：`memory_id`、`owner_scope`（用户/项目及其授权边界）、`kind`、`claim`（一句可检验的断言）、`applicability`、`evidence_refs`、`evidence_level`（用户明确/程序验证/推断待确认）、`confidence`、`created_at/last_verified_at/expires_at`、`status`、`version`、`supersedes`、`extractor_version`。`confidence` 仅用于排序与复核提示，**不能替代证据与权限**。这些均为 [天枢拟议]，当前代码没有此 Schema。

### 5.2 验证、合并、更新

1. **先校验候选。** 校验 Schema、引用确实存在、来源归属与可见范围、证据能否支持断言；剔除凭助手自述、未受理的追加消息、失败工具输出推断出的“成功事实”。密钥、Token、密码、无必要的个人资料和大段原文不得进入记忆。项目事实优先从原文件/产物重新核对，用户偏好优先以用户明确表述为证。来源：[天枢拟议]。
2. **再按语义键合并。** 同一用户/项目、同一对象与属性、相同适用范围的候选才比较：相同则补证据/更新时间；更正则产生新版本并标旧版 `superseded`；互相冲突且无法判定时标 `conflicted`、不注入模型并请求确认。显式用户更正优先于旧推断；新的文件证据优先于过期摘录，但不能自动覆盖用户明确偏好。去重键含来源任务/水位/提炼版本，重试幂等。来源：整理阶段受 [Codex-领导源码核查摘要] 启发；优先级与版本规则为 [天枢拟议]。
3. **控制体积与遗忘。** 单条断言短小、来源分离；按用户/项目设条数和检索预算，旧候选定期复核，项目版本变化时标记 `stale`，到期或被否定时停止召回。用户可查看、更正、删除与关闭自动提炼；删除会话时清除仅由该会话支撑的记忆或移除其证据并重新判断有效性，留下无正文审计墓碑。删除与备份保留需在正式部署前确定实际策略。来源：[Claude Code-官方] 的有限索引启发体积控制；生命周期、用户控制与级联为 [天枢拟议]。

模型可建议候选和可读措辞；**程序**决定身份/权限、状态迁移、证据引用有效性、版本和删除。对无法机器证明的工程经验，首版标“待人工确认”而非自动提升为事实。来源：[天枢拟议]。

## 6. 什么时候读回、读多少

每次新请求先装入**当前任务状态**，再按同会话历史选择近期原文；只有任务语义命中时才跨会话检索记忆。检索先按用户/项目权限和 `active` 状态过滤，再结合任务对象、关键词/语义相似度、证据等级、新鲜度排序；同一事实去重，按可配置 token 预算只投影少量“断言+适用条件+来源 ID”。需要检查细节时，通过受权限控制的读取工具回到具体记忆及原始证据。来源：[Claude Code-官方] 索引加按需主题文件、[Codex-领导源码核查摘要] 的受限摘要与检索；过滤、排序与投影规则为 [天枢拟议]。

召回内容作为**低信任资料**，不能覆盖当前用户输入、系统规则或真实工具观察；发现过期/冲突时不注入，并允许任务中重新核验。检索失败、记忆服务不可用或候选为空时，任务继续使用当前状态和原始历史，不把空检索解释为“事实不存在”。来源：[天枢拟议]。

上下文预算应分别记录：任务状态、近期历史、长期记忆、工具目录/结果的实际或估算 token；预算紧张时先缩短记忆投影并保留来源 ID，不删除权限约束、当前用户目标或未解决阻塞。首版预算值通过真实任务回放测量后配置，不直接沿用其他 agent 的行数/字节数。来源：[天枢拟议]；预算思想参考 [Claude Code-官方] 与 [Codex-本地源码调研]。

## 7. 先做什么、怎样证明有效

| 阶段 | 交付及责任边界 | 最小验证 |
| --- | --- | --- |
| A. 任务状态 | Runtime 记录可信事件和任务水位；Context 消费结构化 `TaskState`；模型只写可读摘要 | 中断/重启后目标、已做、真实结果、阻塞和下一步不丢；重复事件不重复进度；助手自称成功不能覆盖失败工具 |
| B. 候选提炼 | 完成任务后异步生成带来源的结构化候选，程序校验，失败可重试 | 无证据候选被拒；用户更正覆盖旧推断；同一任务重试不产生重复记忆；敏感值不落盘 |
| C. 合并和检索 | 建版本/失效/删除与本人更正；Context 只按身份、相关性和预算注入；提供按需证据读取 | 两用户及两个项目隔离；相关任务召回正确事实，不相关任务不注入；删除/过期后不再召回 |
| D. 回放评测 | 固定多轮任务样本：成功、失败、澄清、纠错、重启、项目文件变更、工具部分结果 | 逐项核对“目标/动作/观察/结果/下一步”保真、错误记忆率、召回相关性、token 开销及来源可回查率；与仅用最近 4+4 轮的基线比较 |

上述阶段和验收均为 [天枢拟议]。首个可给领导演示的切片建议选**一个完整工程任务的过程摘要**：展示原始事件、结构化任务状态、可读交接摘要及对应来源；然后选两条候选，一条因证据充分入库、一条因只是模型推断被拒绝；最后用新任务演示有限召回和按需追溯。这样直接回答“怎么提炼”，不依赖先完成 Java 接口。来源：[天枢拟议]。

实施前需由 Runtime/Agent 负责人确认事件权威和任务状态归属，Context 负责人确认注入与预算，持久化/身份负责人确认记忆归属及删除，必要时由 Skill/知识负责人确认经验与知识发布边界。相关公共 Schema、生命周期和新持久化属于架构变更；本文件仅提出方案，尚未修改协议或代码。来源：[天枢项目协作规范与拟议]。
