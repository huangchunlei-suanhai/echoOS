# Codex 的上下文管理

本质就是**一套专门管 Agent 任务状态的系统**。它负责收集各种信息、保存对话历史、打包成给大模型看的输入、控制内容总量、太长就压缩旧内容；如果会话中断，还能把之前的工作状态重新搭起来。

核心设计思想：**底层程序负责保存真实、可靠的业务事实；大模型只看整理好的信息。模型能看到的上下文窗口，只是整套系统全部状态里的一小部分。**

> 官方代码仓库：https://github\.com/openai/codex，提交版本 [`be5296d`](https://github.com/openai/codex/tree/be5296d4672f59205c1b8a76f46e74eae4f10d51)
>

## 核心管理器：ContextManager（上下文管理器）

它就是这套系统的总管家，里面分好几块数据，各司其职：

```Rust
struct ContextManager {
    items:** Arc<Vec**<ResponseItemEnvelope>>,
    retained_context: Arc<RetainedContext>,
    token_info: Option<TokenUsageInfo>,
    reference_context_item: Option<TurnContextItem>,
    world_state_baseline: Option<WorldStateSnapshot>,
    history_version: u64,
}
```

> https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/context\_manager/history\.rs\#L94
> 
> 

`Arc` 是 Rust 的**共享所有权容器**。读取历史快照时，可以先共享同一份数据；需要修改时再通过 `Arc::make_mut` 获得可变版本。好处：每次准备给模型的输入，不用完整拷贝超长历史，节省性能。



**历史记录分成两层**：

```Plain Text
ResponseItemEnvelope
├── item: ResponseItem
└── metadata: CodexHarnessMetadata
```

> https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/history/src/lib\.rs\#L59
> 
> 

ResponseItemEnvelope：外层包裹 

- item：模型协议中的内容，即模型能看懂的内容（消息、推理条目、函数调用、工具调用、工具返回结果、压缩摘要）

- metadata：程序自己用的附加信息，比如这条信息来源、有没有截断、长度预算。**它不等于需要发给模型的正文。**

tip：这使“供模型理解的内容”和“供程序管理的证据”能够**分别演进**（分开维护，互不干扰）。

## 会话 → 单次任务 → 单次模型调用（三层任务生命周期）

Codex 划分了三级：

```Plain Text
Session：整个会话
    └── TurnContext：一次用户任务的运行上下文（比如：修复代码 + 跑测试），**一次用户任务可能需要调用模型很多次**
            └── StepContext：一次模型采样请求使用的上下文快照
```

tip：**StepContext**：单独一次大模型调用，专属快照。

> https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/client\_common\.rs\#L23
> 
> 

它捕获本次请求使用的模型配置、环境、MCP 连接、工具路由器和 `AGENTS.md` 等信息。模型看到的工具目录与执行工具时使用的工具路由器，**来自同一个请求快照**。 保证两件事：准备请求时能用的工具，和真正执行工具调用时用的工具清单，是同一套。

但也要注意，快照并不意味着所有运行条件永远冻结。源码明确保留了与原始任务关联的实时授权访问机制，实际执行**仍需要程序进行权限判断**。



主流程（run\_turn）简化版：

> https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/history/src/lib\.rs\#L59
> 
> 

```Plain Text
收到用户输入
    ↓
先判断要不要压缩历史，必要时进行轮前压缩
    ↓
记录环境、配置和指令变化
    ↓
执行输入相关 hooks，记录用户输入
    ↓
进入循环
    ├── 接收允许在当前边界进入的补充输入
    ├── 捕获本次 Step 快照 StepContext
    ├── 记录本次**世界状态**变化
    ├── 将活动历史投影为模型输入
    ├── 添加基础指令、工具定义和输出约束
    ├── 调用模型
    ├── 记录模型输出，执行工具并记录结果
    └── 判断是否继续，以及是否需要压缩
    ↓
任务完成
```



每次模型调用前，源码里都有这个关键动作：

```Rust
sess.clone_history()
    .await
    .for_prompt(&step_context.settings.model_info.input_modalities)
```

它表示：取得当前历史快照，然后根据本次模型支持的输入模态，整理成模型输入。

随后 `build_prompt()` 把这些输入和其他请求条件组合起来。`Prompt` 中不仅有 `input`，还有：

> https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/client\_common\.rs\#L23
> 
> 

```Plain Text
base_instructions       基础指令
tools                   工具定义
parallel_tool_calls     是否允许并行工具调用
output_schema           输出结构约束
output_schema_strict    是否严格校验输出结构
```

因此，排查“为什么模型知道这个工具”或者“为什么模型遵守这个格式”时，**不能只检查聊天消息列表**。

## 信息是怎么进入上下文的？

Codex 不会上来就把整个代码仓库一次性全塞给模型。信息都是按需获取：



- 代码仓库里的大部分知识，是通过工具执行逐步获得的：

    ```Plain Text
    任务提出需求
        ↓
    模型选择搜索或读取
        ↓
    工具返回相关内容
        ↓
    运行时限制输出规模
        ↓
    结果进入后续模型请求
    ```

    这是一种**按任务获取信息**的方式。也解释了为什么“模型之前看过文件”不意味着后面永远记得：工具结果可能被截断，随后还可能被压缩为摘要，或者退出当前窗口。

    

- 对于 `AGENTS.md`，源码做的是**受路径和预算约束**的发现：

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/agents\_md\.rs\#L58
    > 
    > 

    1. 确定项目根目录；

    2. 沿项目根目录到当前工作目录的路径逐级查找；

    3. 同一目录优先选择 `AGENTS.override.md`，然后是 `AGENTS.md`，再考虑配置的其他文件名；

    4. 受项目文档总字节预算限制；

    5. 同时考虑项目是否可信。

    它不是递归读取整个仓库里所有的 `AGENTS.md`。

    这里还出现了一个容易忽略的问题：有些系统构造的上下文片段，在模型协议里使用 `user` 角色，例如项目指令和环境信息。

    所以，`role == "user"` 不能直接等价为“真实用户刚刚发出的请求”。Codex 在压缩和回滚等操作中，还需要区分真正的用户消息与上下文消息。



- Skill 则体现了另一层**按需加载**：

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/ext/skills/src/catalog\_prompt\.rs、https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/ext/skills/src/render\.rs\#L126
    > 
    > 

    ```Plain Text
    先给模型：
        Skill 名称、说明、位置
            ↓
    识别需要使用的 Skill
            ↓
    加载对应的主指令
            ↓
    按需读取引用材料
    ```

    显式提到的 Skill 有相应加载路径；模型也可以通过工具读取相关指令。不能据此推断系统总有一个确定性的语义路由器替模型选择所有 Skill。

    目录和正文也有各自的预算。在这个版本的相关路径中，Skill 目录默认预算可按模型窗口的 2% 计算；配置预算设有上限，主指令注入也存在字节上限。这些是具体实现限制，不能推广成所有 Codex 场景都采用的固定参数。



- 世界状态（WorldState）：上下文中的环境和配置也不是只在会话开始时写一次。

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/context/world\_state/mod\.rs\#L321
    > 
    > 

    - `WorldState`，包含项目指令、环境、权限、协作模式、工具与扩展目录等部分。每个部分可以拥有：

        ```Plain Text
        稳定的 section ID
        结构化 snapshot
        完整渲染逻辑
        差异渲染逻辑
        ```

    - 首次建立上下文时，程序生成完整投影。后续请求前，则比较当前状态与基准状态：

        ```Plain Text
        上次状态 ─┐
                  ├── 比较 → 有变化的部分 → 模型可读的更新片段
        当前状态 ─┘
        ```

    tip：结构化快照（程序用来对比、保存）≠渲染后的文字（模型读取）

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/session/mod\.rs\#L4822
    > 
    > 

    - 就算程序保存了一份结构化补丁，并不代表模型会自动理解它；仍需要合适的模型输入投影。

        另外，差异注入通常是在历史里追加变化说明，不意味着此前的旧文本立即从历史里物理删除。因此，它减少重复注入，但不能消除历史增长。

    - 历史被压缩或回滚后，程序还必须检查基准是否仍然有效。否则可能出现：程序以为已经把规则发给模型了，但对应的历史已经被压缩删掉，后续模型没有这条规则。

        `reference_context_item` 和 `world_state_baseline` 的生命周期，正是在处理这类一致性问题。新实现主要依赖结构化状态，同时仍存在一些旧文本识别兼容路径，不能理解成仓库已经彻底消除了所有文本识别逻辑。

## 工具返回内容的处理：截断 \+ 保证消息配对

工具输出进上下文（rollout、history、prompt），两套处理：



- 长度限制截断

    工具结果进入历史时，会生成供活动历史使用的处理版本：

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/context\_manager/history\.rs\#L519、https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/utils/output\-truncation/src/lib\.rs\#L18
    > 
    > 

    ```Plain Text
    工具输出及其 envelope
        ├── 当前活动历史：按策略截断后的版本
        └── 持久化路径：保留该层收到的原始 envelope
    ```

Tip:

- 工具输出截断只作用于活动历史，保留 rollout payload。

- 原始完整结果存在磁盘；但是，“原始”只针对这一层而言。工具自身可能已经限制输出，其他持久化事件类型也有大小限制，不能理解为系统无限保存所有原始数据。



文本截断的典型策略是**保留头尾，截去中间**

这对终端日志比较实用，因为开头常有命令和启动信息，末尾常有错误或最终结果。但它也有明显限制：位于中间的重要信息可能丢失。

相关路径使用近似 token 估算，而不是对每段文本调用精确模型 tokenizer；还有序列化开销补偿。因此，它是一套工程预算策略，不能当作精确的全局 token 求解器。



- 保证协议配对完整

    模型输入中有这样的关系：

    ```Plain Text
    FunctionCall(call_id="c1") 模型发起工具调用
        ↕
    FunctionCallOutput(call_id="c1") 工具返回结果
    ```

    如果历史裁剪只留下其中一端，模型请求就可能无效，或者产生错误理解。

    

    因此，`for_prompt()` 会进行规范化：

    > https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/context\_manager/history\.rs\#L603、https://github\.com/openai/codex/blob/be5296d4672f59205c1b8a76f46e74eae4f10d51/codex\-rs/core/src/context\_manager/normalize\.rs\#L21
    > 
    > 

    1. 检查工具调用是否有对应输出；

    2. 对部分缺失输出补充 `aborted` 等结果；

    3. 移除不符合协议要求的孤立输出；

    4. 去掉当前模型不支持的图片；

    5. 去掉当前模型不支持的音频。

    部分外部工具输出有允许独立存在的协议形式；某些不一致在严格调试路径下也会触发报错，不能概括成“所有异常都被静默修复”。

    删除最旧条目时，代码同样会考虑关联的调用和输出。



- 这说明上下文裁剪有两层正确性：

    ```Plain Text
    内容是否有用
    协议关系是否完整
    ```

    裁剪历史不能只看字数，**既要控制长度，还要保证消息之间的关联关系不被破坏**。

## 什么时候触发压缩？怎么判断上下文超量

Codex 综合使用服务端用量反馈和客户端增量估算。主要思路近似为：

> 
> 
> 

```Plain Text
当前活动上下文占用
≈ 最近**一次模型**请求反馈的总 token（模型服务会返回精确统计，这是最准的基准）
 + 此后新增、尚未被服务端统计的条目估算
 + 必要时补计的历史推理占用
```

Tip：

- 这里的“最近一次用量”很关键。判断窗口大小使用的不是整个会话累计花费了多少 token（该会话所有调用模型的 token 全部加起来）。

- 例如，一个任务连续调用模型十次，累计用量可能很大，但累计用量不能直接表示第十次请求的上下文长度。这里的“第十次请求”才是“最近**一次模型**请求”



压缩阈值也有不同口径：

Tip：

- `BodyAfterPrefix` 对初始工具和指令目录较大的场景有意义：可以分别看待固定前缀和任务过程中增长的历史。

- Total 口径 ≠ 完整窗口限制，二者统计的内容范围一样（Prefix \+ BodyAfterPrefix，全部活动上下文），但是用途、数值大小完全不是一回事。

- 这个版本中，模型元数据的默认有效窗口比例为 95%；已知窗口大小时，自动压缩限制通常不会高于窗口的 90%。

- 90k /95k 是Total 口径下的数值，包含前缀 Prefix；BodyAfterPrefix 是扣掉 Prefix 后的单独计数，二者不能直接划等号。

- 假设窗口为 100,000 token，没有其他配置改变行为，则可能在约 90,000 token 时考虑自动压缩，并以约 95,000 token 作为运行时有效上限。实际还会受到模型元数据、阈值口径和缓冲配置影响。

    触发时机包括显式压缩、轮前检查、任务继续执行时的检查，以及可配置的轮后检查。

    

    源码明确承认的缺口：轮前检查发生在新用户消息和本次上下文更新入库之前。代码里的 TODO 提出，需要进一步预估这些待进入条目，提前触发压缩。因此不能说当前实现已经对所有即将输入的信息完成了完整预算。



三条不同的压缩路线

- Tip

    - 分发时优先检查 `TokenBudget`，然后根据 provider 的远端压缩能力选择后两种传统压缩路径。

    - TokenBudget 不会自动开启，只能由使用者主动手动配置打开；一般在下面业务场景时，打开：

        - 长时间、多轮迭代的超长任务（最典型），本质是放弃把全部历史塞进上下文，改用**外部存储 \+ 按需读取**代替摘要压缩，避免摘要信息丢失。

        - 对摘要失真零容忍的场景，本质是用外置持久化记录作为可信信息源。

        - 上下文容易反复触顶，不想频繁做摘要消耗 token



- local 本地压缩流程

    ```Plain Text
    复制当前历史
        ↓
    加入总结请求
        ↓
    调用模型生成交接摘要
        ↓
    选取预算内的近期真实用户消息
        ↓
    重新构建当前环境和指令
        ↓
    安装替换历史，记录压缩检查点
    ```

    - 一句话：**客户端自己组织，叫模型写一份「交接文档」，删掉老内容，保留最近消息 \+ 交接摘要**

    - 这里的 local 表示客户端组织压缩流程，不表示离线执行，也不表示使用本地模型。

    - 整套压缩的调度逻辑、判断逻辑、裁剪逻辑，全部写在本地这个 Agent 程序里面，由本地程序来编排、控制整个压缩流程；压缩的决策是本地程序做的，核心代码在`codex-rs/codex-core`中。

    - 摘要提示词要求模型保留已经完成的工作、关键决策、约束和偏好、未完成事项，以及重要引用。这很像把工作交给另一个执行者时写的交接说明。

    - 替换历史的组成可以概括为：

        ```Plain Text
        当前规范环境与指令
        + 预算内保留的用户消息
        + 交接摘要
        ```

        但实际顺序更细：窗口前缀有独立位置，普通初始上下文会插入到最后一条真实用户消息或摘要附近，**不能简单认为所有指令永远排在所有消息之前**。

        这一分支为保留用户消息设置了约 20,000 token 的预算，优先保留较新的消息，再恢复时间顺序。部分多模态用户输入会退化为文本版本。

        如果连总结请求本身都超出窗口，代码会尝试移除较旧条目及关联项，再重试总结。这也意味着，压缩并不保证完整回忆；可能发生摘要遗漏，也可能有原始内容在总结之前就被移除。



- Remote Compaction V2 远端加密压缩

    - 一句话：**压缩逻辑交给服务端黑盒处理，客户端拿到一块看不懂的加密压缩块，不拿到明文摘要**

    - 客户端发一个特殊标记 `CompactionTrigger`，交给服务端内部去压缩，返回一个加密不透明条目 `encrypted_content`。

        ```Plain Text
        ResponseItem::CompactionTrigger {}
        
        ResponseItem::Compaction {
            encrypted_content: ...
        }
        ```

    - 这个产物对客户端是不透明的。开源代码可以告诉我们如何请求、保存、保留相关消息和恢复，但不能告诉我们服务端究竟采用什么内部算法。

    - 留策略（预算 64k token，比 local 大方很多）：

        - 优先保留：新的用户原始消息、钩子提示、符合条件的 Agent 消息 

        - 一般不留：助手之前输出的大段回答、工具调用过程日志（部分工具输出是否保留由开关控制） 

        - 拼装：基础环境 \+ 保留的消息 \+ 这块加密压缩条目。



- TokenBudget 新开上下文窗口（换工作台方案）

    - `TokenBudget` 路径更不一样：它可以直接跳过摘要，调用 `start_new_context_window()`。

    - 新窗口主要由重新构建的初始上下文组成，并可在功能开关允许时保留部分客户端消息或工具输出。它不会自动把全部原始用户历史搬到新窗口。

    - 因此，这种运行方式要想持续完成长任务，就需要把**关键进度外置到可再次获取的信息中**，例如笔记、文件或结构化任务状态。

    - 这是从“不断压缩当前工作台”转向“换一个工作台，重新读取保存的工作成果”。

    - 不过，`TokenBudget`、增量工具声明和部分保留功能，在这个版本中属于受配置与模型条件影响的特性。功能注册表里默认关闭，不代表任何配置都无法自动启用；也不能把它们描述为所有 Codex 会话的统一默认行为。

## 会话恢复与回滚

持久化日志存的不是纯文本，是带类型的 JSONL 记录，包含：

```Bash
ResponseItem # 响应项
Compacted  # 压缩检查点
TurnContext # 切换上下文
WorldState # 世界状态
TokenUsageRecord # 令牌使用记录
其他生命周期与保留状态
```

恢复会话流程：读取日志 → 找到压缩备份点 → 恢复替换后的历史 → 追加备份点之后新增记录 → 重建环境基准 → 重新做截断、消息规整。 不是把完整日志一股脑丢进模型。 回滚任务也不能简单删掉最后几条对话，要连带环境、配置基准一起回退。

> 注意：日志写入和内存状态更新，不能当成数据库事务，持久化失败会有边界风险，不是绝对万无一失。
