## 2. 当前入口、身份和两种连接

| 模式 | 本地联调示例 | 用途 |
| --- | --- | --- |
| 真实 | `ws://127.0.0.1:8091/ws/sessions/{session_id}` | 处理任意合法用户自然语言；真正运行模型/工具与场景确认 |
| 录制回放 | `ws://127.0.0.1:8093/ws/sessions/{session_id}` | 严格按九轮样本重现界面；不产生真实业务副作用 |

8091 和 8093 只是本次机器上的联调端口；前端应使用环境配置或开发代理注入地址，不把端口写死在产品代码里。`127.0.0.1` 只对同机浏览器可直接访问；异机开发需通过受控代理或隧道提供 WS 地址。当前回放服务以 `--speed 0` 启动，帧会很快送达；要演练可见进度，可重启并设置 `--speed 20`。端口当前可用不构成以后持续在线的保证。

本次 8091 是以隔离场景目录启动的真实服务。重新部署时必须确认该服务对当前用户和页面中的 `scene_id` 确实可访问；仅传入样本 `user_id` 或照抄 `gearbox_e2e` 不会自动创建或授权场景。`session_id` 在 WS URL 中，当前两类请求信封都不包含顶层 `session_id` 字段。

本次样本 `user_id=2113153353906343938`，录制会话为 `frontend-gearbox-bb52501c67ee4efeb30bc34936558773`，录制任务为 `adf7a1b1ce4648a8b636b5f0622fbcba`。浏览器开始一轮新演练时应生成新的**回放** `session_id`；转真实模式时再生成不同的**真实** `session_id`。每次用户操作都生成新的 `request_id`。正常交互期间保持各自模式内的 `user_id + session_id` 稳定，并按 `request_id` 关联消息。服务端返回的 `task_id` 是任务身份，不是本轮 `request_id`。

### 2.1 固定回放的现有行为

当前 8093 服务按其内存中的会话游标依次期望 `01_discuss` 到 `09_readback_from_workflow_list`。它要求 `user_id` 一致、`request_id` 非空、消息 `type` 一致；`chat_start.prompt` 必须与样本**逐字符相同**，`agent_command.command` 必须与样本 JSON 值相同。请求 ID 可重新生成，返回帧中的关联 ID 会重映射。它**不校验** `ui_context`，所以回放成功不能证明前端页面快照能通过真实后端校验。

不匹配时，8093 自己返回 `chat_error`，游标不前进；该错误是回放服务的拒绝，**不是**真实后端对用户问题的回答。浏览器应在发送前完成匹配和路由，避免把自由输入先发给回放服务。回放服务不实现应用层 JSON `ping`、`chat_cancel` 或任意新 `agent_command`；前端在回放模式关闭这些应用层操作的自动发送。WebSocket 协议层 ping 与应用层 `{"type":"ping"}` 不是同一件事。

同一回放会话断线重连时，服务进程仍在则继续内存游标；换新会话 ID 从第一步开始，URL 可用 `?start_step=04_publish_request` 显式跳到一个样本步骤。服务进程重启会丢失游标，不能把回放游标视为持久业务状态。

### 2.2 用户偏离样本时的真实接管规则

**前端需要实现**下列路由；两个 WS 服务均不会替前端完成它：

1. 用户输入的 `chat_start.prompt` 与当前样本完全一致，且仍处于回放模式：发送到 8093，并持续显示“录制回放”标记。
2. 用户首次输入就不匹配，或在回放任一步输入了不同自然语言：**不要发送到 8093**；创建新的真实 `session_id`，使用当前真实页面 `ui_context` 和新 `request_id`，把该用户原文作为 `chat_start` 送往 8091。此后该会话保持真实模式，不再把真实回复与回放帧拼接成同一任务。
3. 已经展示过回放历史后才偏离：保留此前消息，但给历史和新消息分别标注“录制回放”“真实会话”。真实后端并没有执行前面的回放轮次，也没有对应的工作区、记忆或审批状态。因此接管是**新真实任务**，不能宣称“原回放任务无缝续接”。用户若只输入“把刚才结果改成……”等依赖历史的短句，真实 Agent 可能需要重新澄清；页面应提示用户补充背景。若产品提供“携带已确认需求开启真实任务”，应先向用户展示将发送的需求全文；仍然是新任务，不是导入旧 `task_id`。
4. 回放中的确认按钮只向 8093 发送样本 `agent_command`。用户自定义的命令、错位的确认操作或点击“进入真实模式”时，**不能**把录制的 `task_id`/`operation_id` 转发 8091。真实确认必须等待 8091 在该真实会话中生成新的待确认操作；没有该操作时先从真实自然语言任务开始。
5. 回放第九步结束后继续提问也按第 2/3 条进入新的真实会话。不能把“样本已结束”伪装为 Agent 回答。

| 当前模式 | 用户操作 | 前端应发送到 | 结果身份 |
| --- | --- | --- | --- |
| 回放 | 与下一样本完全一致的自然语言或确认命令 | 8093 | 录制回放 |
| 回放 | 任意不同的自然语言 | 8091 的新会话 | 新真实任务 |
| 回放 | 与样本不同的确认命令 | 不直接转发旧命令；先在真实会话产生新的待确认操作 | 不得冒充已批准 |
| 真实 | 后续合法自然语言或该真实会话产生的确认命令 | 8091 的同一真实会话 | 真实任务 |

回放服务不可用时也不能静默拿旧响应充当实时结果；页面可明确进入新的真实会话，或显示连接失败。

这项边界是现有实现决定的：8093 从未创建真实工作区，8091 也没有“从回放导入任务状态”的 API。若未来业务要求无感延续同一工作区，需要后端明确设计状态导入或在回放期间同步真实执行；本协议不假设这些能力已存在。

## 3. 浏览器发送的消息契约

当前真实 Gateway 入口为 `<BACKEND_ROOT>/src/shaofeng_ai_backend/presentation/fastapi_gateway/application.py`，请求信封在 `presentation/fastapi_gateway/ws_protocol.py`，命令在 `contracts/agent_command.py`。前端主链以**自然语言 `chat_start`**为主，逐文件确认使用独立 `agent_command`。

### 3.1 自然语言 `chat_start`

`chat_start` 顶层只允许 `type`、`request_id`、`user_id`、`prompt`、`ui_context`。第一轮的最小页面快照示例：

```json
{
  "type": "chat_start",
  "request_id": "本轮新生成的唯一ID",
  "user_id": "2113153353906343938",
  "prompt": "我想在当前机械测试场景里做一个两齿轮传动计算工作流：输入两齿轮齿数和主动轮转速，输出传动比与从动轮转速。现在只讨论需求，不写文件。哪些定义需要我确认？",
  "ui_context": {
    "page": "workflow_canvas_page",
    "scene_id": "gearbox_e2e",
    "visible": {
      "page_state": {"button": [], "title": [], "text": []},
      "library_nodes": [],
      "canvas_detail": {
        "workflow_id": "frontend_joint_debug",
        "nodes": [],
        "connections": []
      }
    },
    "target": null
  }
}
```

`ui_context` 是**本轮浏览器所见页面的索引快照**，不是授权事实，也不能把机械命令塞进去。非“场景中心”“账户管理”页面必须有 `scene_id`；`visible.page_state` 必须存在；`workflow_list_page` 只携带当前列表的 `workflows`，`workflow_canvas_page` 可携带 `library_nodes` 与 `canvas_detail`。如果 `target` 指向一个工作流或画布节点，其 ID 必须确实存在于该页面 `visible` 中。第九轮的真实发送示例见录制目录 `capture/ui_context_after_publish.json`，其页面快照由真实资产构造，仍属于模拟前端输入。

浏览器在真实模式应采集**当前**页面，而不是照抄本次空画布样本。当前 Gateway 的信封校验通过，也不意味着 `ui_context` 的领域校验通过；非法页面现场可能以 `chat_final.response.status=blocked` 返回。

### 3.2 控件命令 `agent_command`

`agent_command` 顶层只允许 `type`、`request_id`、`user_id`、`command`，不得附带 `prompt`、`ui_context`。以下为**仅供回放的第一次确认示例**；实时请求必须使用实时服务新返回的任务和操作 ID：

```json
{
  "type": "agent_command",
  "request_id": "45413eec247441cc95fece574159ea56",
  "user_id": "2113153353906343938",
  "command": {
    "command": "approve_scene_write",
    "task_id": "adf7a1b1ce4648a8b636b5f0622fbcba",
    "operation_id": "090244939cfd39a9c7c5b4fbceb9057a"
  }
}
```

当前命令模型只接受 `start_workflow_agent`、`resume_workflow_agent`、`approve_scene_write`。本次首次页面只需实现最后一种；澄清、修订和发布请求均为自然语言。审批命令不能附带 `goal`、`scene_id` 或 `access_mode`。服务端写入快照绑定用户、会话、任务、场景和旧文件哈希；同一审批 ID 是一次性的。页面“暂不确认”可以是本地关闭卡片，但当前协议没有配套的“拒绝写入”命令，不能声称已通知服务端拒绝。

### 3.3 实时服务另外支持的操作

真实 Gateway 还支持应用层 `{"type":"ping"}`，返回 `pong`；支持 `chat_cancel`，返回 `chat_cancel_ack`，受理时还可能返回顶层 `cancelled=true` 的 `chat_final`。本次九轮录制没有这些事件，8093 回放服务也没有实现这些分支；首次回放验收不能宣称心跳、取消或恢复已验证。取消终态的 `response` 可能没有完整 `payload`。

## 4. 浏览器接收消息与状态归并

全部帧先按 `session_id + request_id` 关联；`agent_progress.request_id` 允许为空，`chat_error.request_id` 在某些网关错误中也可能为空。只有带关联 ID 的 `chat_error` 才结束对应请求；无关联 ID 的错误应作为连接级提示，不能猜测是哪一轮失败。不要因为同一 WebSocket 上的其他请求或 Debug 事件而结束当前请求。

| 类型 | 关键字段 | 页面处理 | 业务终态 |
| --- | --- | --- | --- |
| `chat_ack` | `request_id`、`status=accepted` | 标记网关已受理，继续等待 | 否 |
| `agent_progress` | `stage`、`message`、`payload`、`created_at` | 进度时间线；可按 `call_id`/`stage` 合并同类事件 | 否 |
| `agent_debug` | `trace_id`、`seq`、`event`、`payload` | 仅 Debug 抽屉与问题定位；部署未启用时也必须正常工作 | 否 |
| `chat_final` | `response.status`、`response.message`、`response.payload` | 保存正式回答，结束本轮 loading；按结果决定下一张卡片 | 是 |
| `chat_error` | `message`、可能的 `request_id` | 显示传输/信封或未捕获错误 | 有关联 ID 时结束对应请求 |
| `chat_cancel_ack` | `accepted`、`task_cancelled` | 真实服务的取消反馈；不代表外部副作用已回滚 | 否 |
| `pong` | `session_id` | 真实服务应用层心跳反馈 | 否 |

真实录制恰有 9 个 `chat_ack`、348 个 `agent_progress`、471 个 `agent_debug`、9 个 `chat_final`，没有 `chat_error`。`AGENT_DEBUG_MODE=full` 参与了本次录制；真实环境可能完全不发 `agent_debug`。`workflow_agent.assistant_text` 过程事件可能包含与最终回答重复的文字，普通聊天区以 `chat_final.response.message` 为准，避免显示两遍。

### 4.1 区分本轮状态与任务状态

本次 `01_discuss` 返回 `response.status=ready`、`payload.task_status=active`；`02_implement` 和 `03_revise` 返回 `completed/completed`；发布申请与四次确认后多为 `ready/completed`。`ready` 只表示本轮回答正常结束，不能翻译成“整个工程未完成”。校验结果位于 `payload.completion_check.data.valid`，仅在本轮完成工作区校验时出现；普通对话或发布申请可能是 `null`。

`chat_final.response.payload.tool_results` 是**任务累计工具结果**，不是本轮增量。修订轮中有旧、新两次 `run_cgraph_workflow`；结果卡应使用当前最新成功运行的 `data.workflow_output`，并保留“上次运行”与“本次运行”时间语义。后续发布轮即使再次带有历史运行结果，也不表示它重新执行了图。`workspace_files` 可能列出测试依赖与缓存，不可原样当作交付文件展示。

### 4.2 待确认写入的识别和按钮时机

`agent_progress.stage=workflow_agent.tool_completed`、`payload.tool_name=write_scene_file` 且 `payload.status=requires_confirmation` 时，过程事件可先展示 `operation_id`、`path`、`diff` 的预览。**不要仅凭过程事件启用确认按钮**：最后一个 `graph.json` 申请的过程帧只含前 20,000 字符差异，没有 `diff_truncated`。同一轮 `chat_final.response.payload.tool_results` 中对应 `operation_id` 的 `data` 才含 `diff_truncated`、`sha256`、`old_sha256` 等完整元数据。终态到达后，选取本轮新出现、尚未确认的操作 ID，定稿确认卡。

批准时按钮置为处理中，发送新的 `agent_command`。`workflow_agent.scene_write_approved` 过程事件会提供 `operation_id`、`path`、`status=applied`；同一请求仍应等待 `chat_final`。最后的 `tool_results` 仍保留历史 `requires_confirmation` 工具记录，不能据此重新弹出已批准的卡片。当前 `chat_final.payload` 没有独立的结构化“本次已应用”回执；浏览器刷新后若要验证真实资产状态，需要场景资产读取来源。审批被拒时真实 Capability 可返回 `response.status=blocked`、`payload.error_code=SCENE_WRITE_REJECTED`，不可把它与 `chat_error` 混为一类。

第 4/4 份 `workflows/external_gear_pair/graph.json` 的差异确实被截断，`diff_truncated=true`，完整待写入内容哈希为 `7a8222d50a86c720e64a14b2ff31b7b949ffa44a64b5605845aa649174700cdb`。回放页面须标“预览已截断”。本次隔离测试在后端审计缓存核对完整内容后批准；正式用户若需在批准前阅读全文，当前 Gateway 尚缺完整待确认内容读取接口，不能把本次缓存副本伪装为该接口。

## 6. 首次页面设计与数据归属

建议页面保留四个独立区域，避免把工具日志、聊天和业务确认混成同一种气泡：

| 区域 | 用户看到什么 | 可靠来源 |
| --- | --- | --- |
| 对话与输入 | 用户原文、Agent 的澄清、修订答复、最终说明 | 用户 `prompt` 与 `chat_final.response.message` |
| 进度时间线 | 场景检索、模型轮次、文件操作、测试与图执行的简短阶段；支持折叠重复步骤 | `agent_progress`；调试原文另放开发抽屉 |
| 结果与资产 | 四项数值和单位、校验状态、节点/工作流清单、可见画布 | 最新成功的 `run_cgraph_workflow.data.workflow_output`、`completion_check`，以及独立资产读取来源 |
| 写入确认弹窗 | 单文件路径、差异、旧/新哈希、是否截断、确认按钮与处理状态 | 同一操作 ID 的 `chat_final.payload.tool_results`；用户点击后发送结构化命令 |

不要把 `agent_debug` 默认展示给用户；它只辅助按 `trace_id` 定位问题。不要把 `assistant_text` 过程事件当作另一条正式回复。待确认操作的计数“第 1/4”在样本回答中出现，但当前没有独立结构化总数契约；通用 UI 应按**实际出现的操作**逐份展示，不对所有任务硬编码“必定四份”。

当前 AI Gateway 只提供 `/ws/sessions/{session_id}`，没有供浏览器按 ID 列出/读取节点 manifest、工作流 manifest、`graph.json` 的 HTTP 接口。首次页面可以明确标记为“样本预览”并使用本次静态资产设计外观；切到真实业务页面后，应与现有场景资产服务约定授权列表/详情/画布读取接口，并在写入终态后刷新。不能从 `chat_final.message` 解析出权威画布，也不能把 `.var` 文件系统路径当成浏览器 API。

## 7. 前端联调步骤和验收

1. 配置两套独立 WS 地址和显眼的模式标识；用新的回放 `session_id` 从 `01_discuss` 开始。每一步从 `replay_bundle.json.steps[].request` 取**准确**输入，替换新 `request_id`，在同一会话里串行发送；等待相同请求 ID 的 `chat_final` 或 `chat_error` 后再进入下一步。
2. 检查 9 轮 `chat_ack`、全部 `agent_progress`/`agent_debug` 和 9 个终态都被接收。页面可以合并展示进度，但底层接收器不能丢事件或用 `client_wait` 造假。调试模式关闭时页面仍须可用。
3. 在第 4–8 步确认 `operation_id` 去重、逐份确认、按钮防重复点击；第 7 步终态标示 graph 差异截断。第 9 步发送合法列表页 `ui_context`，展示“上次实测”，不得误标为本轮新运行。
4. 分别在第 1 步与已播放若干步后输入**不同**自然语言，验证前端在发送前切换到 8091 的**新真实会话**，新请求只到真实服务，历史回放清晰标记。检验真实服务不可用、场景不可访问、UIContext 不合法等情况均显示实际错误，不能回退用固定录制回答冒充实时结果。
5. 试着在回放批准按钮处偏离样本，确认前端不会把样本任务 ID 或一次性操作 ID 转给 8091。要验收真实批准，需要先在真实会话产生新的待确认写入，再用该会话返回的 ID。
6. 在真实模式测试模型结果时，比对**语义和结构化证据**，不要求文案、耗时、进度条数与录制相同。当前录制未覆盖取消、应用层心跳和跨重启恢复，它们应另设用例。

首次通过的最低口径：用户能分辨录制/真实模式；九轮回放完整、类型齐全、关联正确；自由输入确实走真实服务且新会话边界可见；四份确认不重复也不串号；结果卡引用结构化执行输出；场景列表与画布预览明确区分“样本文件”与“在线权威资产”。

## 8. 已知限制与待前后端明确的接口

- **回放不支持任意对话。** 它只匹配九个录制动作；回放返回的 `chat_error` 不能当真实 Agent 错误用例。
- **回放无法无缝继承到真实任务。** 真实后端没有回放任务的工作区或已批准操作；新真实会话若要理解历史需求，应由用户提供或审核后发送完整上下文。
- **完整资产读取尚未由此 Gateway 提供。** 节点库、工作流列表、画布与刷新状态需要独立授权读取接口；本次 `.var` 是联调证据，不是长期产品接口。
- **完整审批差异尚未可读。** graph 申请已截断；正式审批页需明确是否先补全量预览能力。
- **批准成功缺独立终态回执字段。** 实时可见 `scene_write_approved` 过程事件，长期状态应由资产读取接口回查；历史 `tool_results` 仍保留 `requires_confirmation` 记录。
- **错误、取消、断线重连未由此样本证明。** 设计中需要分支，但验收须另测。
