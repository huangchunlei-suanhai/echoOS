# 天枢长期记忆与上下文管理：三仓现状核查与待决策项

核查日期：2026-10-29  
核查范围：前端 `sftg-frontend` 的 `v2.0.1`、Java 后端 `cax-java-backend` 的 `feat-2026-10-19`、AI 后端 `sftg_ai_backend` 的 `develop_updata`。三个工作区核查时均无未提交改动。

## 结论摘要

三仓已经分别具备聊天 UI、Java 登录身份和场景权限、AI WebSocket 与任务检查点等基础，但“长期记忆与上下文管理”目前没有端到端持久化链路：浏览器消息只存在组件状态；AI 后端的通用会话 Memory 是进程内存；Java 的可信登录身份没有传递到当前直连的 AI WebSocket。前端正式联调协议也明确记载没有会话历史读取接口。

当前可复用的基础：

- Java 后端认证后能从 Token 解析可信用户 ID，并已使用 PostgreSQL 和 Redis；另有按计算任务持久化事件、支持游标回放的实现模式。
- AI 后端有按 `user_id + session_id` 隔离的 Memory 协议、Context 投影、任务检查点和对话压缩，但这些能力目前不能替代产品级会话历史。
- 前端已有会话面板、请求关联、过程事件呈现和新建会话交互的基础，但当前 session ID 由浏览器生成，历史消息未回读。

进入实现前，最重要的三个待决策点是：**身份如何可信地跨 Java 到达 AI 服务、聊天数据由哪个服务和数据库负责、删除会话时如何处置任务检查点与工程产物**。还需明确部分回复和工具事件的持久化语义、游标重放契约、保留期及模型上下文预算策略。

## 端到端差距

| 能力 | 当前实现 | 目标需要补齐 |
| --- | --- | --- |
| 会话创建与归属 | 前端本地生成 session ID，AI 请求体带客户端 user ID | 认证后由服务端生成全局唯一 session ID；所有读取、事件回放和删除校验可信用户与会话归属 |
| 聊天持久化 | AI 进程内短期 store；前端组件内存 | 先持久化用户消息和请求状态，再记录助手可见结果及安全进度；服务重启可恢复 |
| 历史 API | 无通用会话列表、历史分页、删除或事件补拉接口 | 增加会话管理、消息分页、游标高水位和删除接口，并定义前端刷新时序 |
| 用户身份 | Java HTTP 认证有效；AI WS 的 `user_id` 与 Java Token 未绑定 | 定义浏览器到 Java/网关/AI 的受信身份传递和授权链路 |
| 事件生命周期 | WS agent_progress 即时广播；request_id 关联，连接断开无回放 | 持久 event_id、会话内 sequence/cursor、断线补拉、跨消息与进度事件去重 |
| 长期记录与模型上下文 | 最近轮次短期注入；工程检查点另存完整工具现场 | 保留完整聊天展示记录；模型只从本会话按相关性和近期性选取/压缩，且统一预算 |
| 删除 | 没有会话删除流程 | 明确聊天记录、事件、幂等记录、检查点、审批快照和工程产物分别如何删除 |

## 建议的实施分段

1. **冻结跨服务边界**：确定认证入口、身份传递、历史 API 所属服务、数据库真源、迁移责任和部署路径。
2. **冻结公共协议**：定义 session/message/request/event 数据模型、状态迁移、唯一键、会话内 sequence、分页 cursor、高水位和 WS/HTTP 补拉方式。
3. **建立持久存储**：实现会话和消息/事件存储；确保 `(trusted_user_id, session_id, request_id)` 幂等；用户消息落盘成功后才 ACK/进入模型；助手终态和请求完成状态原子更新。
4. **改造请求与事件生命周期**：串联 `accepted -> running -> completed/failed/cancelled`；助手消息用稳定 `message_id` 更新 partial/terminal 状态；工具事件只保存白名单字段和安全摘要；持久化成功后再广播。
5. **增加会话 API 和前端恢复**：后端创建 ID；前端保存当前会话和列表；打开会话加载正序历史及高水位，再从高水位之后补事件；旧消息向上分页；按 ID 更新和去重。
6. **实现同会话记忆选择与预算**：完整历史仍保存在存储，不整体放入 prompt；近期消息加当前会话内相关旧消息；将系统规则、页面事实、消息、工具定义及输出预留纳入模型配置驱动的统一预算，保护工具调用与结果配对，记录脱敏诊断。
7. **实现删除与验收**：按确认的语义协调数据库和任务工作区；测试服务重启、双用户越权、重复 request_id、失败/取消、断线补拉、分页并发和超预算裁剪。

## 待三方决策的问题

### P0：进入实现前必须确定

1. **认证与身份桥（Java + 前端 + AI 后端）**：浏览器现有 Java Token 通过何种受信方式到达 AI WS 和历史 API？由 Java/Nginx 在握手认证并传递可信 user ID、改为 Java 代理 AI 流量，还是由 Java 签发短时、限定会话范围的 AI 访问票据？Python 如何验证、如何阻止绕过代理直连伪造身份？前端消息体中的 `user_id` 是否从正式协议移除或只作为非权威提示？
2. **数据真源和服务所有权（坚哥主答，三方确认）**：聊天 API、写入事务和数据库由 Java PostgreSQL 统一负责，还是由 AI Python 服务在 `DATA_ROOT` 下使用 SQLite？若选 PostgreSQL，Python 是访问共享 DB 还是调用 Java 内部服务？若选 SQLite，备份、恢复、持久卷、迁移工具和未来多实例限制由谁负责？Java 已有 PostgreSQL，不应以 Python 仓库当前无 DB 推导整个系统无 DB。
3. **会话删除语义（我方 + 坚哥，瑶姐确认交互）**：删除是否硬删会话、展示消息、进度事件、request 幂等记录？对应任务检查点和审批快照是否删除？场景 `agents/` 中的工程产物是否保留？删除时有运行中的请求，是拒绝删除、先取消并等待终态，还是立即逻辑删除并阻止后续写回？必须覆盖删除后的备份/软删除可见性边界。

### P1：公共契约定稿前确定

4. **部分回复是否要求真实流式持久化（我方 + 瑶姐）**：当前模型适配器取得整轮 HTTP 响应后才返回文本，前端最终文案再做本地动画；没有真实 token delta 流。[model_dispatcher.py](/home/huangchunlei/workspace/echo/sftg_ai_backend/src/shaofeng_ai_backend/application/runtime/model_dispatch/model_dispatcher.py:93) 首期 `partial` 是仅表示请求中占位/按模型轮次已返回的可见文字，还是要新增真实模型流式输出并逐步更新同一 message？刷新后恢复 partial 的精确语义是什么？
5. **持久化哪些进度（我方 + 瑶姐）**：历史打开后是否重放并显示工具进度时间线，还是只保留状态摘要？需要明确哪些 `agent_progress` stage 和工具状态入库、用户可见的安全摘要字段、工具调用与结果的关联 ID；明确禁止保存的 payload/日志类别。
6. **事件 cursor 的定义（瑶姐 + 我方 + 坚哥）**：`sequence` 是只给消息排序，还是对消息与所有持久事件共用的会话单调序号？partial/final 对同一 message 的更新是否产生独立 event sequence？消息历史的 `high_water_cursor` 与 `events after cursor` 是否保证同一快照？重连采用 WS `resume_after` 回放，还是 REST 事件补拉，或两者都支持？
7. **同一会话并发规则（瑶姐 + 我方 + 坚哥）**：同会话可在多个标签页共享，是否允许多个请求同时运行？若允许，后端按受理顺序分配序号，但上下文读取哪个水位；若不允许，采用会话级串行队列还是返回冲突？重复 `(user, session, request_id)` 内容相同应回放已有状态；内容不同是否返回冲突错误？
8. **相关历史检索与 4,000 token（我方主答）**：确认首期使用“近期轮次 + 当前会话内相关旧轮次”；旧轮次是否采用约 4,000 tokens 的硬上限，还是仅初始目标并受模型总预算约束？检索只用 SQLite FTS/PostgreSQL 全文检索与 recency 排序，还是另有既定检索组件？工具进度摘要是否参与检索？跨会话记忆维持不在本期。
9. **统一模型预算配置（我方主答）**：每个部署使用的模型上下文上限、输出预留和安全余量由谁配置，能否通过模型配置显式提供？确认输入优先级为系统规则/当前用户请求/必要页面事实、近期消息、相关旧消息；工具 schema 计入总输入；压缩或估算失败时按优先级确定性丢弃旧历史，仍不得超限。现有 262,144 与 4,000 都不应被误当作完整统一预算。
10. **保留期限与数据保护（坚哥 + 我方）**：首期数据不自动过期，还是保留一周？若过期，是按创建还是最后活动计算？是否要求数据库加密、备份保留同步删除、用户消息/助手回复允许完整落盘的产品或合规确认？
11. **会话列表字段（瑶姐）**：会话列表用首条用户消息生成标题、时间标题，还是需要重命名？排序是否按最后活动时间倒序？删除确认和空会话是否出现在列表？
12. **请求受理与存储故障（坚哥 + 我方）**：若用户消息尚未持久化，是否一律不发送 `chat_ack`、不调用模型？若过程事件写入失败但模型仍可完成，是否中止本轮，还是完成回复并标记事件不完整？建议至少把“用户消息未落盘不得开始执行”定为硬规则。

### 建议三方共同确认

- 首期仍为单 AI 网关实例，预计并发会话数、每会话典型/最大消息量和分页大小；该信息用于选择 SQLite/PostgreSQL 并验证 event sequence 写入锁的容量。
- 全链路以服务端身份派生 `trusted_user_id`；以全局唯一 session ID 标识会话；所有查询、写入、重放和删除必须同时验证可信用户和会话归属。
- 历史记录与工作区 checkpoint 分开保存；不保存系统提示、内部推理、密钥、完整工具参数或未经白名单处理的大型工具输出。
- 共同验收以重启恢复、双用户同 session ID 越权拒绝、重复 request_id、并发/失败/取消、游标无遗漏无重复、删除语义和总输入预算为准。
