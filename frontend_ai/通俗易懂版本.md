# 一、总场景地图：天枢系统 = 一家餐厅

先记住这张“谁是谁”的对照表，后面所有例子都用它。

| 专业术语 | 生活对象 | 在系统里干什么 |
|---|---|---|
| 前端 `sftg-frontend` | 顾客点餐屏 + 服务员记事本 | 显示聊天、发消息、显示进度 |
| Java 后端 `cax-java-backend` | 前台 / 账房先生 | 验会员卡、管账本、发通行证 |
| AI 后端 `sftg_ai_backend` | 厨房 / 厨师 | 真正生成回答、决定先看哪张单 |
| PostgreSQL | 前台大账本柜 | 长期存聊天、消息、事件 |
| SQLite | 厨房小本子 | 单机试验可用，但不推荐 |
| Redis | 前台刷卡机缓存 | 快速校验会员卡 |
| Token | 会员卡 | 证明“你是谁” |
| WebSocket（WS） | 厨房后门 + 喊号喇叭 | 浏览器直连 AI，实时传消息和进度 |
| `session_id` | 桌号 | 标识一次会话 |
| `user_id` | 会员号 | 标识用户 |
| `request_id` | 点餐单号 | 标识一次请求 |
| `message_id` | 菜品牌上的稳定菜号 | 更新同一条消息 |
| `event_id` | 每条进度录音的编号 | 事件去重 |
| `sequence` / `cursor` | 排队叫号流水号 / 读到第几号 | 排序和断线补拉 |
| `high_water_cursor` | 你已经读到第几号 | 历史读取的高水位 |
| checkpoint（检查点） | 厨房施工半成品档案 | 任务恢复用，不是聊天账本 |
| 工程产物 | 已经做好的菜 / 工程图纸 | 场景里生成的文件 |
| Prompt / Context | 厨师面前的备菜台 | 模型一次能看的输入 |
| token budget | 备菜台承重 / 容量 | 模型总输入预算 |
| `partial` | 已经端上桌的阶段性菜 | 阶段性助手文字 |
| 前端打字动画 | 服务员端上桌后的表演 | 本地动画，不是模型流式 |
| 幂等 | 同一张小票重复提交只做一次 | 防重复 |
| 内部接口 | 传菜窗口 | Java 给 AI 的受保护读写通道 |
| 认证桥 | 前台发临时通行证，厨房读卡器验证 | 身份从 Java 传到 AI |

**一句话地图**：顾客在点餐屏点菜 → 前台验会员卡 → 厨房做菜 → 账房记大账本。现在的问题是：**厨房后门不验卡、小票只写白板、喊号没录音、删单没规矩、备菜台容量没统一算。**

# 二、现状链路图：哪里断了

## 现状 1：身份链路断了——厨房后门不验会员卡

```
顾客 → [点餐屏] 自己写 user_id → [厨房后门 WS] 直接信 → 厨房开火
                ↑
        前台有会员卡验证，但厨房后门没接上
```

| 生活对象 | 专业术语 | 现在的问题 |
|---|---|---|
| 顾客自己喊“我是VIP 001” | 前端把 `user_id` 编码进 `chat_start` / `agent_command` | 客户端可改写 |
| 厨房后门不查卡 | AI WS 直接接受 `user_id` | 没和 Java Token 绑定 |
| 前台刷卡机 | Java `TokenInterceptor` + Redis | 只对 HTTP 有效 |
| 后门没装读卡器 | Python 网关默认 `ENABLE_AUTH=false` | 绕过代理可伪造身份 |

**生活例子**：前台能刷会员卡，但厨房有个后门，顾客直接进后门喊“我是VIP”，厨房就信了。正式协议说明书自己也承认：`user_id` 未与登录凭据绑定，后门默认不查证件。

## 现状 2：聊天持久化断了——小票只写白板

```
顾客点菜 → [服务员白板 customMessages] 显示 → 刷新页面 → 白板擦掉，历史没了
                    ↓
            [厨房白板 InMemorySessionMemoryStore] 只记最近几轮 → 重启全丢
```

| 生活对象 | 专业术语 | 现在的问题 |
|---|---|---|
| 服务员临时白板 | 前端 `customMessages` 组件状态 | 刷新即丢 |
| 厨房白板 | `InMemorySessionMemoryStore` | 进程重启即丢 |
| 顾客自己编桌号 | 前端生成 `web_session_*` 存 `sessionStorage` | 不是服务端发的全局唯一 ID |
| 没有历史订单查询窗口 | 无通用会话列表 / 历史分页 / 删除接口 | 不能回读 |
| 施工半成品档案 | 工程任务 checkpoint | 不是聊天账本，且可能含工具结果 |

**生活例子**：顾客点完菜，服务员把菜名写在临时白板上；厨房把最近几桌要求写在厨房白板上。刷新页面 = 擦掉服务员白板；厨房关门 = 擦掉厨房白板。前台大账本柜明明有，但没人把小票记进去。顾客想查“我上次点了啥”，没有查询窗口。

## 现状 3：事件回放断了——喊号没录音

```
厨房喊“3号桌炒菜中” → [喇叭 WS 广播] → 顾客没听见就没了
                              ↓
                      广播失败只记告警，不阻断
                      没有持久序号，不能回放
```

| 生活对象 | 专业术语 | 现在的问题 |
|---|---|---|
| 厨房喊号 | `agent_progress` 通过 WS 临时广播 | 即时广播，断线无回放 |
| 点餐单号 | `request_id` | 只按请求关联，不是消息稳定 ID |
| 没有录音编号 | 无持久 `event_id` / `sequence` / cursor | 不能补拉、不能去重 |
| 服务员口头去重 | 前端 reducer 只在内存去重终态 | 跨刷新去重未接入 |

**生活例子**：厨房用喇叭喊“3号桌正在炒菜”，你没听见就没了；没有录音，也不能按号补听。同一道菜重复喊，服务员只在脑子里记“这个听过了”，一换班就忘。

## 现状 4：上下文预算没统一——两个秤各称各的

```
[PromptContextBudget] 托盘 4,000 tokens，预留 800 → 只估算 PromptContext
[ConversationCompression] 冰箱 262,144 上下文，约 220K 触发 → 未从具体模型配置取上限
                ↓
        没有一个“整桌食材总重量”的统一硬限制
```

| 生活对象 | 专业术语 | 现在的问题 |
|---|---|---|
| 托盘 4 公斤 | `PromptContextBudget` 默认 4,000 tokens | 只估算 PromptContext，超了只压缩页面可见列表 |
| 冰箱 262 公斤 | 对话压缩器默认 262,144 窗口 | 约 220K 触发，未从模型配置取上限 |
| 备菜台总承重 | 统一模型总输入预算 | 不存在 |
| 只按时间近拿单 | 默认取最近 6 轮 | 没有当前会话内相关历史检索 |

**生活例子**：一个规则说“托盘最多 4 公斤”，另一个说“冰箱有 262 公斤空间”，但没人统一算“这顿饭所有食材一共多少”。结果只收拾了桌面，没收拾柜子，还是超重。而且厨师只看最近 6 张单，不会翻“这个顾客上次也问过类似问题”。

## 现状 5：删除没规矩——删单时不知道删什么

```
顾客说“删单” → 没有删除流程
                ↓
    聊天正文？事件？幂等记录？检查点？审批快照？工程产物？
    运行中的菜还在炒怎么办？备份里还留着算不算？
```

**生活例子**：顾客说“把这桌订单删了”，服务员不知道是只撕前台小票，还是连厨房施工半成品、审批单、仓库材料一起扔；菜还在炒时能不能删也没规矩。

# 三、推荐方案链路图：把断点接上

## 目标 1：身份链路——前台发临时通行证，厨房装读卡器

```
顾客 [点餐屏] --现有 token--> [前台 Java] 验会员卡
                                  ↓ 发短时、限定会话用途的 AI 连接票据
顾客 [厨房后门 WS] --带票据--> [厨房读卡器] 向 Java 验证票据
                                  ↓ 取得可信 user_id
                            厨房开火；消息体 user_id 不再被信任
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 前台继续管会员卡 | Java 继续作为登录身份权威 | 坚哥定认证契约 |
| 临时通行证 | 短时、限定会话用途的 AI 连接票据 | 前端向 Java 申请 |
| 厨房读卡器 | AI 在 WS 握手时向 Java 校验票据 | 我方接入 |
| 通行证过期 | 每次新请求前确认仍有效 | 防重放 |
| 顾客自报会员号不作数 | AI 不再信任消息体 `user_id` | 移除或只作非权威提示 |
| 服务员改送客路线 | 前端改连接流程 | 瑶姐负责 |

**生活例子**：前台还是唯一能刷会员卡的地方。顾客要进厨房后门，先到前台换一张“只限这桌、只限这顿饭”的临时通行证；厨房后门装读卡器，读出来才知道真实会员号。顾客自己在点菜单上写“我是VIP”，厨房一概不认。

## 目标 2：数据链路——账本放前台大柜，厨房走传菜窗口

```
[顾客点餐屏] --会话 API--> [前台 Java] --写事务--> [PostgreSQL 大账本柜]
                                  ↑
                          [传菜窗口 内部接口]
                                  ↑
                          [厨房 AI] 读写受保护内部接口
                                  ↓
                          厨房保留“哪些历史进模型”的选择权
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 前台大账本柜 | Java 现有 PostgreSQL | 存会话、展示消息、可回放事件 |
| 顾客查历史找前台 | Java 对前端的会话 API | 坚哥负责 |
| 传菜窗口 | Java 对 AI 的受保护内部写入/读取接口 | AI 不直接连表乱写 |
| 厨房决定先看哪张单 | AI 保持对“哪些历史进入模型”的选择权 | 我方负责运行时接入 |
| 不要两个记账员同时写 | 不让 Java 和 AI 同时直接写同一组表 | Java 负责持久化事务 |
| 小本子不推荐 | SQLite 单实例可用，但另建备份/迁移/授权边界 | 本期不选 |

**生活例子**：所有订单账本统一放前台大账本柜（PostgreSQL）。顾客查历史找前台（会话 API）。厨房要读单、回填进度，不能自己伸手进账本柜乱翻，而是通过前台设的传菜窗口（内部接口）递单和回填。但厨房仍有权决定“这顿饭先看哪几张单、哪些旧单相关”。

**为什么不用 SQLite 小本子**：前台本来就有正规大账本柜，有锁、有备份、能多人同时记账。厨房另买小本子试验方便，但谁备份？被水泡了怎么办？多人同时写会不会打架？以后开分店怎么共享？小本子还没接前台会员卡授权。本期要求“关店重启能查账、不同会员互相看不到、订单状态一次写清、进度按顺序回放”，所以用大账本柜更稳。

## 目标 3：删除链路——聊天记录删，工程产物留，半途不能算成功

```
顾客说“删单”
   ↓
有请求运行中？ --是--> 拒绝删除，提示先结束请求
   ↓ 否
清除：聊天正文 + 事件 + 含对话正文的任务检查点
保留：已生成的场景工程产物 + 必要归属与审计标识
   ↓
跨数据库和文件清理 → 可重试的删除状态 → 不能把部分清理当成成功
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 菜还在炒先别删 | 有请求运行时先拒绝删除 | 瑶姐确认提示 |
| 撕前台小票、删聊天正文 | 清除展示消息 | 我方与坚哥共同定义 |
| 删进度录音 | 清除可回放事件 | 同上 |
| 删含对话的施工半成品 | 清除含对话正文的任务检查点 | 同上 |
| 已做好的菜和图纸保留 | 已生成的场景工程产物保留 | 只留归属与审计标识 |
| 删到一半停电不算成功 | 可重试的删除状态 | 不能部分清理当成功 |
| 要不要留最小审计小纸条 | 最小审计记录 | 评审时确认 |

**生活例子**：顾客说“把这桌订单删了”。菜还在炒，服务员先说“请先等这道菜结束或取消”。删的时候：前台小票、聊天正文、进度录音删掉；厨房里含对话内容的施工半成品档案也删掉；但已经做好的菜、已经生成的工程图纸保留，只留“这道菜属于哪桌、谁点的”的归属标签和审计编号。删到一半停电，不能算删成功，要有一个“待继续删”的状态，来电后接着删干净。

## 目标 4：上下文链路——账本全存，备菜台有限，总算总重量

```
[PostgreSQL 大账本柜] 完整历史全存
          ↓ AI 选择
[厨师备菜台 Prompt/Context]
   ├─ 近期轮次
   ├─ 当前会话相关旧轮次（约 4,000 tokens 初始上限）
   ├─ 工具定义（菜刀砧板说明）
   ├─ 系统规则（店规）
   └─ 页面事实（当前桌备注）
          ↓
[统一模型总输入预算] 总承重硬限制；超了按优先级丢旧历史
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 账本全存 | 完整历史留在存储 | 不整体塞进 prompt |
| 先看最近几单 | 近期轮次 | 我方负责 |
| 再翻相关旧单 | 当前会话相关旧轮次 | 我方负责 |
| 相关旧单托盘约 4 公斤 | 约 4,000 tokens 初始上限 | 不是完整统一预算 |
| 备菜台总承重 | 模型总输入预算 | 硬约束 |
| 菜刀砧板说明也算重量 | 工具定义计入总量 | 我方负责 |
| 店规、当前桌备注也算 | 系统规则、页面事实计入总量 | 我方负责 |
| 超重先丢最不重要的旧单 | 按优先级确定性丢弃旧历史 | 仍不得超限 |
| 跨桌记忆这期不做 | 跨会话记忆不在本期 | 文档明确 |

**生活例子**：账本柜里所有订单都留着，但厨师面前的备菜台就那么大。先放最近几单，再从旧单里挑“和这单相关的”放上来。相关旧单先按“大约 4 公斤”的托盘上限，但整个备菜台还有总承重限制；菜刀、砧板、调料说明（工具定义）、店规（系统规则）、当前桌备注（页面事实）都要算进总重量。不能只看托盘 4 公斤，就忘了整个台面已经超重。现有 262,144 和 4,000 都不应被误当作完整统一预算。

## 目标 5：事件与恢复链路——排队流水号 + 录音编号 + 稳定菜号

```
会话内统一递增 sequence（排队叫号流水线）
   ├─ message_id：同一道菜从半盘到整盘，用同一个菜号更新
   ├─ event_id：每条进度录音一个编号，重复送到能认出
   └─ high_water_cursor：打开历史时告诉你“已读到 105 号”
          ↓
前端按 cursor 从 106 号补拉；WS resume_after 或 REST 补拉
          ↓
不重不漏；partial/final 更新同一 message
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 所有消息和进度共用一个流水号 | 会话内统一递增 `sequence` | 评审拍板 |
| 稳定菜号 | `message_id` 更新同一消息 | 不另开新菜 |
| 进度录音编号 | `event_id` 事件去重 | 重复送到不重复显示 |
| 你已经读到第几号 | `high_water_cursor` 历史高水位 | 历史读取返回 |
| 从 106 号开始补 | 前端按游标补拉 | 瑶姐负责 |
| 断线后按号补听 | WS `resume_after` 回放 / REST 事件补拉 | 评审确认 |
| 半盘到整盘算同一道菜 | `partial` / `final` 更新同一 `message_id` | 不产生新菜号 |

**生活例子**：整个会话像一条排队叫号流水线，所有消息和进度共用一个不断递增的号。打开历史时，前台告诉你“你已经读到 105 号”（高水位），之后你按“从 106 号开始补”去补拉。同一道菜从半盘到整盘，用同一个 `message_id` 更新，不另开新菜；同一条进度重复送到，用 `event_id` 认出“这个号我听过了”，不重复显示。

## 目标 6：partial 的含义——不是边炒边端，是整盘端出后的阶段记录

```
现在：厨师炒完整盘才端出 → 服务员端上桌后做“一个字一个字蹦”的表演
                                  ↑
                         这是前端打字动画，不是模型流式

首期 partial：只保存“已实际展示的阶段性助手文字”
              不把打字动画当作模型部分回复
```

| 生活对象 | 专业术语 | 推荐做法 |
|---|---|---|
| 厨师炒完整盘才端 | 模型适配器取得整轮 HTTP 响应后才返回文本 | 现状 |
| 服务员端上桌后表演 | 前端最终文案本地打字动画 | 不是模型流式 |
| 已经端上桌的阶段性菜 | 首期 `partial`：已实际展示的阶段性助手文字 | 评审确认 |
| 不把表演当出菜 | 不把打字动画当作模型部分回复 | 我方建议 |
| 刷新后半盘菜算不算 | 刷新后恢复 partial 的精确语义 | 需定义 |

**生活例子**：厨师不是边炒边一小勺一小勺端，而是炒完一整盘才端。前端那个“一个字一个字蹦出来”的打字动画，只是服务员端上桌后表演给你看的，不是厨房真的在分批出菜。所以首期 `partial` 只记“实际已经端上桌的阶段性文字”，不把打字动画当成模型的部分回复。

# 四、五个拍板事项：评审会上的五张场景卡

## 卡 1：身份和数据所有权——先举手确认“谁管卡、谁管账”

| 要拍板 | 生活例子 | 专业术语 |
|---|---|---|
| 接受 Java 身份权威 + PostgreSQL 数据真源 | 前台继续管会员卡，账本放大柜 | 身份权威 + 数据真源 |
| 指定 Java 内部接口认证方式 | 传菜窗口怎么证明“我是厨房的人” | 内部接口认证 |
| 指定部署地址 | 传菜窗口开在哪个地址 | 部署地址 |
| 指定故障处理 | 窗口坏了是重试还是报警 | 故障处理 |

**生活例子**：会上先举手确认：前台继续管会员卡、账本放前台大柜子。然后定细节：传菜窗口怎么证明“我是厨房的人”、窗口开在哪个地址、窗口坏了怎么办。

## 卡 2：删除语义——聊天记录删，工程产物留，审计要不要留

| 要拍板 | 生活例子 | 专业术语 |
|---|---|---|
| 运行中先拒绝 | 菜还在炒，先别删 | 有请求运行时拒绝删除 |
| 清除聊天正文、事件 | 撕前台小票、删进度录音 | 展示消息 + 可回放事件 |
| 清除含对话正文的检查点 | 删含对话的施工半成品档案 | 任务检查点 |
| 工程产物保留 | 已做好的菜、工程图纸保留 | 场景工程产物 |
| 保留必要归属与审计标识 | 留“哪桌点的”标签和审计编号 | 归属 + 审计标识 |
| 是否保留最小审计记录 | 要不要留一张“某桌删过单”的小纸条 | 最小审计记录 |
| 可重试删除状态 | 删到一半停电不算成功，来电接着删 | 可重试删除状态 |

**生活例子**：会上确认：删订单时，聊天正文和含对话的施工半成品删掉，已经做好的菜和工程图纸保留；要不要留一张“某年某月某桌删过单”的最小审计小纸条，也要定；删到一半停电不能算成功。

## 卡 3：partial 含义——别把服务员表演当厨房出菜

| 要拍板 | 生活例子 | 专业术语 |
|---|---|---|
| 首期 partial 只存已实际展示的阶段性文字 | 只记已经端上桌的菜 | 已展示的阶段性助手文字 |
| 不把打字动画当模型部分回复 | 服务员表演不算厨房分批出菜 | 前端本地动画 ≠ 模型流式 |
| 刷新后恢复 partial 的精确语义 | 刷新后半盘菜算“已上菜”还是“作废” | partial 恢复语义 |

**生活例子**：厨师炒完整盘才端，前端打字动画只是服务员端上桌后的表演。首期 `partial` 只记实际端上桌的阶段性文字，不把表演当出菜；刷新后半盘菜怎么算，会上要定清楚。

## 卡 4：事件 sequence——一条排队流水线，菜号、录音号、读到第几号

| 要拍板 | 生活例子 | 专业术语 |
|---|---|---|
| 会话内统一递增 sequence | 所有消息和进度共用一个排队号 | 会话内统一 `sequence` |
| 历史读取返回高水位 | 前台告诉你“已读到 105 号” | `high_water_cursor` |
| 前端按游标补拉 | 从 106 号开始补 | cursor 补拉 |
| message_id 更新同一消息 | 同一道菜从半盘到整盘用同一个菜号 | `message_id` |
| event_id 事件去重 | 同一条录音重复送到能认出 | `event_id` |
| 不重不漏 | 补单不重复上菜、不遗漏 | 游标无遗漏无重复 |

**生活例子**：整个会话像一条排队叫号流水线，所有消息和进度共用一个不断递增的号。打开历史时告诉你“已读到 105 号”，之后从 106 号补拉；同一道菜用同一个菜号更新；同一条进度用录音编号去重。要保证补单不重不漏。

## 卡 5：保留期限——先别搞“一周自动碎纸”

| 要拍板 | 生活例子 | 专业术语 |
|---|---|---|
| 首期不自动按一周过期 | 先别搞小票满一周自动碎纸 | 不自动过期 |
| 先完成用户主动删除 | 顾客说删才删 | 用户主动删除 |
| 自动过期需单独定义一致清理规则 | 聊天、检查点、备份要一起碎，规则另定 | 对话/检查点/备份一致清理 |
| 按创建还是最后活动计算 | 从开单算还是最后动过算 | 过期计时基准 |

**生活例子**：先别搞“小票满一周自动碎纸”。因为自动过期很麻烦：聊天正文过期了，施工半成品要不要一起过期？备份里的副本要不要同步碎？碎了一半账对不上怎么办？所以首期先做“顾客主动说删才删”，自动过期以后单独定规则。

# 五、一页契约长什么样：装修交底图

评审产物是一页“接口与状态契约”，相当于装修交底图。它要列明：

| 契约栏目 | 生活例子 | 专业术语 |
|---|---|---|
| HTTP/WS 字段 | 点菜单上每栏写什么 | 接口字段 |
| 身份来源 | 会员号从哪张卡读出来 | 身份来源 |
| 状态迁移 | 订单：已接单→制作中→完成/失败/取消 | 状态机 |
| 幂等键 | 同一张小票重复提交只做一次 | 幂等键 |
| 游标规则 | 排队号怎么编、从第几号补 | cursor / sequence 规则 |
| 删除范围 | 删单时撕哪些、留哪些 | 删除范围 |
| 三方各自确认 | 水电、泥瓦、木门各自签字 | 三方责任确认 |

**生活例子**：开完交底会，产出一张“装修交底图”：水管走哪、插座高度、门框尺寸、谁买材料、谁验收、出了事找谁。三方各自在自己负责的那一栏签字。这张图就是后面施工和验收的依据。

# 六、实施顺序图：先地基，再厨房，再服务员，最后全家演练

```
第 1 步：Java 身份与存储
  前台装新门锁、发临时通行证、大账本柜建聊天表
        ↓
第 2 步：AI 生命周期和预算
  厨房装读卡器、订单状态机、备菜台总承重规则
        ↓
第 3 步：前端恢复与去重
  服务员查历史、往上翻页、按号补单、同菜号更新、录音号去重
        ↓
第 4 步：三方联调验收
  模拟：关店重启能查账 / 别人拿你桌号看不了 / 重复小票不重复做 /
        退单失败都记账 / 断线补单不重不漏 / 删单按约定删干净 / 备菜台不超重
```

| 阶段 | 生活例子 | 专业术语 |
|---|---|---|
| 第 1 步 | 先装门锁、发通行证、建大账本表 | Java 身份与存储 |
| 第 2 步 | 厨房装读卡器、定订单状态、算备菜台总承重 | AI 生命周期和预算 |
| 第 3 步 | 服务员学会查历史、补单、去重 | 前端恢复与去重 |
| 第 4 步 | 全家一起演练各种异常 | 三方联调验收 |

**为什么这个顺序**：身份和存储是地基，AI 和前端都依赖它。地基没定，上面先做就会返工。就像装修先定门锁和账本柜，再让厨房和服务员按这个标准干活，最后全家演练。

# 七、一张总图收尾

```
【现状】
顾客自报会员号 → 厨房后门直接信
小票只写白板 → 刷新/重启全丢
喊号没录音 → 断线不能补
两个秤各称各的 → 备菜台没统一承重
删单没规矩 → 不知道删什么

【目标】
前台发临时通行证 → 厨房读卡器验 → 可信 user_id
前台大账本柜 PostgreSQL → 厨房走传菜窗口内部接口
聊天正文/事件/含对话检查点删，工程产物留，可重试删除
统一排队 sequence + 高水位 + 补拉 + message_id 更新 + event_id 去重
账本全存，备菜台按总预算选近期+相关旧单，4,000 只是初始上限
首期不自动一周过期，先做主动删除

【顺序】
Java 身份存储 → AI 生命周期预算 → 前端恢复去重 → 三方联调验收
```

**一句话总结**：这份补充说明就是“装修交底会”的会议纪要草案——先把身份、账本、删单、排队号、备菜台容量五件事拍成有负责人、有结论的一页契约，再按“地基→厨房→服务员→全家演练”的顺序施工，避免三家各干各的、最后门框对不上。
