# Code Flow Observatory 页面设计与功能规划

> 版本：v0.1（设计讨论稿）  
> 目标：把仓库源码、可复用的解释卡片和一次真实运行记录组织到同一个可浏览、可复习、可展示的网页中。

## 1. 产品定位

这个网页不是在线运行代码的聊天窗口，而是一个**代码链路学习与运行复盘工作台**：

1. 选择一个代码仓库和代码版本。
2. 浏览仓库的源码解释卡片库。
3. 打开一个场景的一次历史运行。
4. 沿着实际执行步骤查看源码、解释和运行证据。
5. 保存笔记或把这条链路以只读形式展示给别人。

核心体验可以概括为：**先运行并记录一次，之后通过“流程步骤 → 解释卡片 → 固定版本源码”反复学习。**

## 2. 页面中的对象关系

```text
仓库
├── 仓库级解释卡片库（卡片按源码版本保存修订）
├── 代码版本 A（固定提交和源码快照）
├── 代码版本 B（固定提交和源码快照）
└── 学习场景
    ├── 运行记录 A → 绑定代码版本 A
    │   └── 执行步骤 → 卡片修订 → 对应版本源码
    └── 运行记录 B → 绑定代码版本 B
        └── 执行步骤 → 卡片修订 → 对应版本源码
```

建议将网页中的“代码分支”明确成**代码版本/快照**：Git 分支会移动，历史运行却必须永远指向当时的源码。界面可以显示分支名作为说明，但每次运行实际绑定固定 commit、文件内容哈希和必要的环境摘要。

需要区分三个容易混在一起的概念：

- **场景**：要学习或验证的流程定义，例如“普通对话入口”。
- **运行记录**：这个场景某一次真实执行，包含输入、事件、结果和时间。
- **流程步骤**：从运行事件整理出的可读链路；一个步骤可以引用一张或多张解释卡片。

解释卡片属于仓库的共享资料。不同场景和运行记录引用卡片修订，不各自复制一份说明；同一张逻辑卡片在不同源码版本下可以有不同源码和说明修订。

## 3. 推荐的信息架构

### 全局框架

- **顶部栏**：产品名称、仓库选择器、代码版本选择器、全局搜索、当前页面路径、演示/导出入口。
- **左侧导航**：仓库总览、流程与运行、代码解释卡片、版本对比、学习笔记。
- **主工作区**：根据当前任务显示概览、运行时间线、源码卡片或版本差异。
- **右侧详情区**：在流程页面显示当前步骤的解释和证据；在卡片库显示选中卡片的解释与源码。

建议首屏以“最近学习的场景”和“最近运行记录”为主，并展示源码覆盖、解释审核进度等学习状态。不要把首页做成单纯的统计仪表盘，用户应能直接回到上次阅读的流程。

### 页面导航

```text
仓库选择
├── 总览
├── 流程与运行
│   └── 场景
│       └── 某次运行详情
├── 代码解释卡片库
├── 代码版本对比
└── 学习笔记
```

### 关键页面：运行详情

桌面端建议使用三栏布局：

```text
┌──────────────────┬──────────────────────────┬──────────────────┐
│ 流程步骤/时间线  │ 固定版本的源码            │ 当前步骤解释     │
│                  │ VS Code 风格，只读代码区  │ 输入、输出、证据 │
└──────────────────┴──────────────────────────┴──────────────────┘
```

页面顶部显示场景名、用户输入、运行状态、运行时间、代码版本和最终结果。左侧按时间显示步骤，选中一步后，中间代码区跳到对应文件、符号和行号并高亮相关源码；右侧显示“这一步做什么、为什么执行、输入/输出、调用关系、关联卡片”。窄屏改为“步骤 / 源码 / 解释”切换页签。

主流程默认简洁可读；重试、分支、并行任务和子调用可以展开查看。这样既保留真实执行结构，也不会让初学者一打开就面对一大团调用图。

### 关键页面：代码解释卡片库

桌面端建议使用“文件树 + 卡片列表 + 卡片详情”布局：

- 文件树按仓库目录组织，也可切换到按模块职责分组。
- 卡片列表可搜索文件名、符号名、源码和解释，并按语言、卡片类型、审核状态筛选。
- 卡片详情并排展示说明与源码；源码支持语法高亮、行号、文件路径、符号路径和版本信息。
- 用户可以从某张卡片看到它被哪些流程和运行记录引用。

## 4. 代码解释卡片设计

### 卡片粒度

卡片应足以让人理解一段有意义的源码，不要把每一行拆成一张卡。建议支持：

- **文件/模块卡**：保留完整文件视图，并覆盖模块级代码、常量和无法细分的逻辑。
- **类卡、函数卡、方法卡**：按语法结构定位源码范围，是流程步骤最常引用的卡片。
- **路由、配置、数据结构、外部调用等卡片**：用于解释重要边界和项目约定。
- **导入依赖卡**：可以合并重复导入的说明，但保留每个实际源码位置。

文件卡和符号卡可以重叠引用源码；它们服务于不同阅读方式。页面需显示源码定位，而不是把卡片数量当成覆盖率。

### 卡片内容

每张卡片至少包含：

- 稳定卡片身份、卡片类型和所属仓库。
- 固定代码版本、文件路径、符号全名、起止行和源码内容哈希。
- 只读源码快照；源码内容由选定代码版本读取，不靠手工粘贴作为唯一来源。
- 说明：**一句话作用**、职责、输入、输出、关键状态变化、依赖/调用关系、错误或边界条件。
- 证据来源、审核状态、说明修订历史、被哪些流程步骤引用。

说明文字与源码快照分开保存。改解释不会改变历史源码；代码变化会生成对应的新源码版本，旧流程仍显示旧源码和当时的说明修订。

### 全仓覆盖与质量状态

“几乎涵盖整个仓库源码”应落实为可检查的源码覆盖，而不是生成很多卡片就算完成：

1. 建立仓库文件清单，并为每个纳入范围的源码文件提供文件卡或符号卡。
2. 通过语法解析定位类、函数和方法；没有可识别符号的代码也由文件卡覆盖。
3. 明确列出排除目录和文件类型，例如依赖目录、构建产物或生成代码，并说明排除原因。
4. 分开展示“源码已索引”“已有解释草稿”“人工审核通过”的比例。
5. 新索引卡默认标为“待解释/待审核”；自动提取源码不代表解释内容已经正确。

覆盖率按文件和源码范围计算。导入语句、模块初始化、配置和其他不在函数体内的代码也需要有可追溯入口。

## 5. 一次运行如何变成可学习的流程

网页本身无法仅凭源码准确知道某次请求实际走过哪个分支。要实现“跑一次、以后复习”，运行时需要保存结构化事件，并把事件映射到固定代码版本中的源码符号。

每条运行记录建议保存：

- 场景版本、输入摘要、运行结果、开始/结束时间和状态。
- 仓库 ID、固定代码版本、源码哈希，以及影响复现的配置/依赖摘要。
- session/request/trace 标识，以及 WebSocket 收发消息或等价入口/出口记录。
- 有序事件：阶段名、事件时间、耗时、状态、父子关系、错误摘要。
- 每个事件对应的文件、符号、行号和解释卡片 ID。
- 必要的输入/输出摘要；按规则脱敏，避免保存密钥或不应展示的原始内容。

流程详情应清楚区分证据类型：

- **运行事件**：本次采集器实际记录到的事实。
- **源码定位**：事件关联到固定版本源码中的位置。
- **静态关系**：从代码分析得到的潜在调用或依赖，不能冒充本次实际执行。
- **人工解释**：供学习的说明，应有待审核/已审核状态。

如果采集器没有记录某个函数，界面可以显示相关源码卡片作为补充阅读，但不能把它插入真实运行时间线并称作“已执行”。对于没有逐函数事件的阶段，应如实标成阶段级证据。

为兼顾完整性和可读性，建议提供两个层级：

- **学习时间线**：按 Gateway、协调器、上下文、路由、能力、响应等业务阶段组织。
- **源码细节**：展开当前阶段，查看实际采集到的函数/事件和关联源码。

用户所说的“debug”在首版可定位为**运行后的链路复盘**：浏览运行时保存的事件、代码和摘要。它不会自动包含未采集的局部变量或完整进程状态；这些内容应在采集设计中明确范围。

## 6. 视觉与交互风格

- 整体使用明亮底色和清爽留白，主色可选青绿/亮蓝，搭配少量橙黄、紫色用于强调状态和重点；保持青春活力，但避免大面积高饱和霓虹色。
- 代码区使用接近 VS Code 的深色编辑器配色、等宽字体、语法高亮、行号、缩进和清晰的选中行背景。
- 解释卡片把“作用、输入、输出、证据、注意点”做成固定信息区块；**关键符号和结论加粗**，关键词可用颜色标签突出。
- 运行状态使用文字加颜色/图标共同表达，例如成功、失败、取消、采集不完整；不能只靠颜色区分。
- 点击步骤后同步定位源码和解释卡片；从源码卡片也能反向查看关联步骤。
- 提供“专注阅读/演示模式”，隐藏编辑操作，保留步骤导航、代码、解释和必要版本信息。

## 7. 推荐功能优先级

### 第一阶段：完成学习闭环

1. 仓库选择器；首版可只配置一个仓库，但数据结构不写死仓库名称或路径。
2. 固定代码版本选择和源码索引。
3. 全仓文件/符号卡片目录、源码搜索、类型筛选和解释审核状态。
4. 普通对话场景及其运行记录列表。
5. 运行详情时间线；步骤可以打开对应源码和解释卡片。
6. 明确显示运行事件、静态关联和人工解释的证据类型。
7. 运行记录、源码和解释修订均可离线回看；历史记录绑定当时版本。
8. JSON/Markdown 导出或只读演示模式，便于展示和备份。

### 第二阶段：提高学习和维护效率

- 学习笔记、收藏、已读进度、卡片批注。
- 同场景多次运行筛选，比较成功/失败、耗时和步骤差异。
- 相同场景跨代码版本比较源码、事件和解释变化。
- 卡片待审核队列、缺少说明/未覆盖文件清单。
- 快捷键：上一步/下一步、打开源码、展开调用详情。

### 第三阶段：扩展适用范围

- 接入更多仓库、语言和运行采集适配器。
- 支持更多业务场景以及分支、重试、并行任务视图。
- 对代码版本和运行环境做更完整的可复现记录。

## 8. 推荐实现边界与验收条件

页面与采集/索引能力需要共同完成目标：源码索引负责“有哪些代码”，解释卡片负责“这段代码是什么意思”，运行事件负责“这一次实际发生了什么”，页面负责把三者连起来。仅完成前端页面无法自动生成可信链路。

第一阶段可以按下面条件验收：

- 可以选择仓库和固定代码版本，且将来增加仓库时无需改变核心页面层级。
- 仓库文件清单中的源码均能找到对应文件卡或符号卡；排除项有清单和原因。
- 可以搜索源码/符号/解释，并识别待解释、待审核、已审核状态。
- 打开一条已保存运行后，可以按步骤复习，并从每个有源码证据的步骤打开正确版本的文件、符号和行号。
- 运行事件与静态代码关系在视觉和文字上明确区分；不存在的事件不会由静态调用关系补造。
- 更新代码或解释后，历史运行仍能打开原源码和原说明修订。
- 无需重新启动被观察程序，即可浏览已保存运行记录；演示模式可隐藏编辑功能。

## 9. 对《验证普通对话入口.md》的整理建议

现有文档适合作为第一条场景链路的学习素材，不宜直接充当网页的最终数据格式。建议后续把其中内容拆成三类：

1. **流程步骤**：例如入口校验、ACK、请求协调、读取会话记忆；只记录真实执行或明确标注为静态关联。
2. **源码卡片**：保存文件、符号、行号和代码版本引用；源码从仓库快照加载。
3. **解释与证据**：每步解释为什么出现、输入输出是什么，并说明信息来自运行记录、源码分析还是人工说明。

当前草稿到“读取会话记忆”附近就中断了，尚未覆盖后续上下文构建、路由、能力执行、响应发送和异常/取消路径。它也包含多段手工粘贴源码；网页应以固定版本中的源码为准，让手工说明引用源码位置，避免行号和代码逐渐过期。

在补完普通对话链路前，建议把场景输入、运行记录和源码版本分别固定下来。输入文本相似不代表是同一次运行，也不代表经过相同分支。
